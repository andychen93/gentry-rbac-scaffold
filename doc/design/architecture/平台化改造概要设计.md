# 平台化改造概要设计（Starter 化 + 前端共享层）

> 状态：待评审
> 日期：2026-08-30
> 关联文档：[AGENTS.md](../../../AGENTS.md) ｜ [全局基础设施架构设计.md](./全局基础设施架构设计.md)

---

## 1. 背景与问题

本仓库是多租户 RBAC 脚手架，定位是「所有新项目的起点」。当前消费方式是 **fork 整仓**：

- 平台仓库在迭代（租户提权修复、菜单收归平台级……）；
- fork 出的项目也在迭代自己的业务；
- 同一个平台 bug 要修 N 遍，三个月后两边长成不同项目，cherry-pick 都合不动。

**fork 只在「模板冻结」时成立，而本仓库是活的。**

## 2. 目标 / 非目标

### 目标

1. 平台能力（横切基础设施 + RBAC + 监控）收敛为**可依赖的 jar**，新项目引依赖而不是 fork；
2. 平台成为**唯一迭代源**：bug 修复、安全增强只改一处，发版后各项目升版本；
3. 本仓库自己（gentry-start）成为第一个消费者（**狗粮**），starter 不好用当场暴露；
4. 前端共享层（Pro 组件 / 主题 / 请求封装）抽为**单仓 workspace 包**，消除组件拷贝；
5. 保留演进到微前端的口子（菜单驱动挂载契约不变），但现在不上微前端。

### 非目标

- 不拆微服务、不上注册中心（维持模块化单体）；
- 不做运行时换肤 / 暗色模式；
- 不搭建 Maven 私服 / npm 私服（本地 `mvn install` / workspace link 起步，私服等第二个消费项目出现再补）；
- 不迁移已有 Flyway 迁移内容（只挪 classpath 位置，checksum 不变）。

## 3. 总体架构

```
┌─ 平台仓库（rbac，唯一迭代源）───────────────────────┐
│ 后端                                                     │
│   gentry-core-spring-boot-starter   横切基础设施          │
│   gentry-rbac-spring-boot-starter   RBAC + 通知 + 迁移    │
│   gentry-monitor-spring-boot-starter  Redis 监控          │
│   gentry-bom                       版本收口               │
│   gentry-start                     狗粮（组装 + IT）      │
│ 前端                                                     │
│   packages/@gentry/kit             共享包（组件/主题/请求）│
│   src/                             狗粮应用（页面/菜单）  │
└─────────────────────────────────────────────┬───────────┘
                                              │ 引依赖（后端 jar / 前端 workspace 或私有 npm）
                     ┌────────────────────────┼─────────────┐
                     ▼                        ▼             
                项目 A（CRUD 业务）        项目 B …          
                自己的业务模块 + 迁移      V1000+ 版本段     
```

**迭代流向单向**：平台修复 → 发版 → 项目升版本；项目业务永远在自己的仓库。项目对平台的定制走扩展点（`@ConditionalOnMissingBean` 覆盖 / 关闭 Controller 暴露），不 fork 平台代码。

## 4. 后端设计

### 4.1 模块划分

| 新模块 | 来源 | 职责 | 依赖 |
|--------|------|------|------|
| `gentry-core-spring-boot-starter` | `gentry-core` 更名 | 异常/多租户/自动填充/数据权限/限流/防重/TraceId/JWT 黑名单/i18n/Jackson | 无（对外只依赖 Spring Boot + Sa-Token + MyBatis-Flex） |
| `gentry-rbac-spring-boot-starter` | `gentry-business` 改造 | `com.gentry.rbac` 全部 + `com.gentry.notification` + Mapper XML + **Flyway 迁移 + flyway-core/flyway-mysql 依赖** | core-starter |
| `gentry-monitor-spring-boot-starter` | `gentry-monitor` 更名 | Redis 监控 | core-starter |
| `gentry-bom` | 新建 | 三个 starter 的 dependencyManagement，供消费项目引版本 | 无 |
| `gentry-start` | 保留 | 狗粮：主类 + application.yml + 14 个 IT + 将来的演示业务包 | 三个 starter |

`gentry-business` 模块删除：rbac 部分进 starter，notification 随 rbac starter 分发（见 4.6）。

### 4.2 自动装配

现状的问题：`GentryApplication` 在 `com.gentry` 根包，靠包扫描兜住所有 `@Configuration`；core 没有 `AutoConfiguration.imports`。消费项目主类在 `com.xxx`，直接引 jar 扫不到 Bean。

| starter | 自动装配类 | 内容 |
|---------|-----------|------|
| core | `GentryCoreAutoConfiguration` | `@AutoConfiguration` + `@EnableScheduling` + `@ComponentScan("com.gentry.core")`（core 内约 21 个配置/组件类，逐个转 `@Bean` 收益低、churn 大，定向扫描是务实选择；`@EnableScheduling` 从主类迁入，使 `LogCleanTask` 等平台定时任务随 starter 生效，消费方免声明） |
| rbac | `GentryRbacAutoConfiguration` | `@ComponentScan("com.gentry.rbac", "com.gentry.notification")` + `@MapperScan("com.gentry.rbac.**.mapper", "com.gentry.notification.**.mapper")` + `@ConditionalOnProperty(prefix="gentry.rbac", name="enabled", havingValue="true", matchIfMissing=true)` |
| monitor | `GentryMonitorAutoConfiguration` | 扫描 + `@ConditionalOnProperty(gentry.monitor.enabled, matchIfMissing=true)` |

均注册到各自 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`。

**core SPI 不变**：`UserDataScopeResolver` / `DeptChildrenProvider`（core 定义接口、rbac 提供实现）的缝隙已经存在，starter 化后由扫描自动装配，消费项目可自己实现并 `@ConditionalOnMissingBean` 覆盖。

### 4.3 主类瘦身

`GentryApplication` 从 `com.gentry` 移到 `com.gentry.start`，删掉 `@MapperScan`（职责移入 rbac starter 自动装配）。目的：

- 消费项目不再需要 `@ComponentScan("com.gentry")` 这种脏写法；
- 消除「主类根包扫描 + 自动装配」双重注册的歧义。

### 4.4 Flyway 约定（本设计最关键的契约）

**现状**：迁移全部在 `gentry-start/src/main/resources/db/migration/{common,mysql,postgresql,sqlite}`，V1–V15。

**改造后**：

| 流 | classpath 位置 | 版本段 | 归属 |
|----|---------------|--------|------|
| 平台流 | `db/migration/gentry-rbac/{common,mysql,postgresql,sqlite}` | **V1–V999（平台保留段）** | rbac starter jar 携带 |
| 项目流 | `db/migration/{common,mysql,postgresql,sqlite}` | **V1000 起** | 消费项目自己 |

- 消费项目 `spring.flyway.locations` 同时列两组（平台 2 条 + 自己 2 条），yml 注释里给模板；flyway-core/flyway-mysql 依赖随 rbac-starter 分发（消费方免声明，平台不该让消费方知道厂商细节）；
- Flyway 合并扫描所有 location 成一个版本流，**版本段保留**是防撞的唯一手段，写进 AGENTS.md 硬约束；
- 迁移只挪目录不改内容，`flyway_schema_history` 的 checksum 不变，已初始化的库无感；
- 「已发布的迁移文件不可修改」规则不变，且升级为跨项目契约：平台发版后，消费项目库里的平台段迁移由 starter jar 提供，项目侧不得复制。

### 4.5 配置命名空间

`gentry.*` 命名空间已存在（i18n / captcha / login-security / password / log），全部保留。新增：

| 键 | 默认 | 说明 |
|----|------|------|
| `gentry.rbac.enabled` | true | false 时不装配 RBAC Bean（只引 core 做纯横切的项目用） |
| `gentry.monitor.enabled` | true | false 时不装配 Redis 监控 |

### 4.6 notification 的去向

通知（SSE 推送 + 短信网关 SPI，15 个文件）依赖方向是 notification → rbac（查管理员），从不反向。两个选项：

- A. 随 rbac starter 分发 —— V11 建表迁移留在共享流，新项目开箱有通知能力；
- B. 留狗粮业务层 —— V11 必须从共享流摘出，版本流出现空洞，且新项目要用通知时无路可走。

**选 A**。理由：V11 无法干净摘除（已发布迁移），通知是通用平台能力（登录告警等），新项目直接受益。代价是 rbac starter 略胖，可接受；将来通知独立成 starter 时再拆（包名 `com.gentry.notification` 已天然隔离）。

### 4.7 测试布局

| 类型 | 去向 |
|------|------|
| core 单测（~130） | 随 core-starter |
| rbac 单测（~70，纯 Mockito） | 随 rbac-starter |
| 14 个 `*ApiIT`（@SpringBootTest 全栈） | 留 gentry-start，继续起完整狗粮验证装配 |
| starter 自动装配测试 | 新增：imports 登记 + 扫描包/条件注解契约 + `gentry.{rbac,monitor}.enabled=false` 时不装配（ApplicationContextRunner 断言装配类未注册）。不用 runner 做全栈冒烟——core/rbac Bean 依赖 Redis/数据源，排除后可断言面太小，全栈行为由 14 个 IT 把关 |

### 4.8 BOM 与发版

`gentry-bom`（pom 打包）收口三个 starter 版本。消费项目：

```xml
<dependencyManagement>
  <dependency>
    <groupId>com.gentry</groupId><artifactId>gentry-bom</artifactId>
    <version>X</version><type>pom</type><scope>import</scope>
  </dependency>
</dependencyManagement>
```

当前阶段 `mvn install` 到本地即可；第二个消费项目出现时再搭私服与 CI 发版流水线。

## 5. 前端设计

### 5.1 单仓 workspace 共享包 `@gentry/kit`

`frontend/package.json` 增加 `"workspaces": ["packages/*"]`，新建 `packages/gentry-kit`（包名 `@gentry/kit`），**源码包模式**（`main`/`types` 直指 `src/index.ts`，不构建产物，由消费方 vite/tsc 编译）。

**进 kit**（平台语义、无业务依赖）：

| 内容 | 说明 |
|------|------|
| `components/pro/*` | ProTable / QueryForm / CrudFormModal / RowActions / StatusSwitch / PageSelect / SweetAlert（含各自测试）+ `permission.ts` 权限注入点（见下） |
| `theme/*` | argonColors / argonTheme / argonLessVars（含测试；**颜色守卫测试留应用侧**，它守的是应用侧 `argon.less`） |
| `hooks/usePagedList.ts` | 分页 hook（含测试） |
| `types/api.ts` | ApiResult / PageResult / PageQuery（含测试） |

**前置解耦**（pro 组件现有三处应用层隐式依赖，抽取前先剪断）：

1. `RowActions` 直接 import `stores/userStore` 取 `hasPermission` → 改为 Context 注入（`PermissionProvider`/`usePermission`），应用在根部包 Provider；不包默认放行。
2. `QueryForm`/`CrudFormModal` 的 `type: 'dict'` 分支 import `common/DictSelect`（拖 dictApi/locales）→ 该分支**全仓零使用（死代码）**，直接删除。

**留在应用层**（应用语义）：

| 内容 | 为什么 |
|------|--------|
| `services/request.ts` + 各 `*Api.ts` | request 依赖应用层 `locales`（i18n 实例）做错误消息本地化，且 API 层本就每项目各一份；kit 侧 `types/api.ts` 已提供类型契约 |
| `utils/menuMapper.ts` | 页面注册表 = 应用的菜单契约，每个项目不同（微前端预留的关键，见 5.3） |
| `stores/*` | userStore 持登录态、layoutStore 持 UI 状态，应用级 |
| `pages/**`、`locales/**`、`App.tsx` | 狗粮自己的 |
| `hooks/useLocale.ts` | 依赖应用的 i18next 实例初始化 |

### 5.2 构建与测试影响

- `vite.config.ts`：`additionalData` 从 `@gentry/kit/theme` 读 `argonLessVars`（workspace link 后按包名导入）；
- `services/request.ts` 不动（留在应用层），但 `types/api.ts` 入 kit 后应用内 11 处 `types/api` 导入与 API 文件里的 `ApiResult/PageResult` 引用改从 `@gentry/kit` 导入；
- `tsconfig`（单工程，noEmit）：`include` 扩为 `["src", "packages/gentry-kit/src"]` + `paths` 加 `@gentry/kit`；不引入 project references（composite 与 noEmit 冲突）；
- `vite.config.ts` 与 `vitest.config.ts` **两份都**加 `@gentry/kit` alias（vitest 是独立配置，不继承 vite 的 resolve）；vitest 的 include **不需要动**（现无 include 字段，默认 glob 天然覆盖 packages/ 下测试，误设 include 反而会把 src 测试挤出）；
- kit 的 `package.json` 声明 peerDependencies（react/antd/@ant-design/icons/@tanstack/react-query/react-i18next，与根版本对齐）——狗粮靠 hoisting 无感，第二个消费项目装包时 npm 校验；
- `noHardcodedText.test.ts` 的扫描根从 `src` 扩到 `['src', 'packages/gentry-kit/src']`（pro 组件是 t() 重度用户，不扩就是防线漏洞）；
- e2e（15 个 spec）按 DOM/label 断言，不受包结构影响（helpers 只读 `src/locales`，不迁）。

### 5.3 微前端演进预留（只留口子，不实施）

现在的挂载链是：后端 `sys_menu.component` → 前端 `COMPONENT_MAP` 懒加载。把它固化为**平台契约**：子应用页面一律通过注册表挂载，不直接写死路由。未来切 micro-app/qiankun 时，把 map 的 value 从 `import()` 换成远程加载函数，`sys_menu` 数据、权限渲染、布局全不动。

## 6. 阶段划分

| 阶段 | 内容 | 交付判据 |
|------|------|---------|
| P1 | core 自动装配 + 更名 core-starter | `mvn clean test` 全绿；狗粮行为不变 |
| P2 | business → rbac-starter（含 notification、Mapper XML、flyway 依赖、Flyway 迁移） | 全量 IT 绿；Flyway 对已初始化库无感升级 |
| P3 | 主类移包 + monitor-starter + gentry-bom + 脚本/文档 + /tmp 冒烟消费项目 | `mvn clean install` 全 reactor 成功；E2E 绿；冒烟项目能起能登录 |
| P4 | 前端解耦（权限注入/删死分支）+ workspace 抽 kit | `npm test` + `tsc -b` + `vite build` + E2E 全绿 |

P1–P3 是后端一条计划，P4 是前端一条计划，各自独立可交付。

## 7. 风险与对策

| 风险 | 对策 |
|------|------|
| 主类移包后漏扫（某 Bean 只被根包扫描兜着） | 14 个 IT 全栈起真实上下文，天然回归网；P3 单独验证 |
| 自动装配与组件扫描双重注册 | 过渡期（主类仍在根包）Spring 按配置类/bean 名去重，已核实无冲突；Task 5 移包后彻底消除 |
| Flyway 版本撞车（项目写了 V16 平台也发 V16） | 版本段保留（平台 ≤V999，项目 ≥V1000）写进 AGENTS 硬约束 + yml 注释 |
| 消费方忘配 application.yml 必需面（messages.basename / mapper-locations / sa-token）起不来 | Task 8 /tmp 冒烟项目给出最小完整 yml 模板并实测；模板沉淀进 AGENTS「新项目接入」 |
| 模块更名后旧 ~/.m2 产物 / 残留 target 毒害构建 | 全程 `mvn clean test`；更名任务显式 rm 旧 target |
| 前端 pro 组件对应用层的隐式依赖（userStore / DictSelect） | P4 前置解耦任务：权限 Context 注入 + 删 dict 死分支（全仓零使用已核实） |
| 颜色守卫测试硬路径引应用侧 argon.less | 守卫测试留应用侧不随迁；kit 只带走源文件与其余测试 |
| vitest include 被误改导致 src 测试假绿 | 计划明示「不动 include」并写明错误写法的后果 |
| 前端 import 路径大规模重写引入笔误 | `tsc -b` + `vite build` 双闸门 + 全量单测 + CSS 产物 diff |
| `mvn -pl <module>` 模块名变更导致文档/习惯失效 | AGENTS 九章的模块名同步更新；强调全 reactor `mvn clean test` |

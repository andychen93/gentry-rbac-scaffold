# 一、设计目标（What & Why）

## 是什么（What）

数据权限拦截器是基于角色的行级数据过滤机制。在 RBAC 权限模型基础上，根据用户角色的数据权限范围（`data_scope`），在 SQL 执行前自动追加部门或用户级别的过滤条件，实现"同一接口、不同角色看到不同数据范围"的效果。

核心职责：

1. **行级数据过滤**：根据角色的 `data_scope` 配置，自动在 SQL 中追加 `dept_id IN (...)` 或 `create_by = ?` 条件
2. **部门树查询**：当数据范围为"本部门及子部门"时，递归查询部门树获取所有子部门ID
3. **自定义范围**：支持按部门列表灵活配置数据可见范围
4. **注解驱动**：通过 `@DataScope` 注解标记需要数据过滤的 Mapper 方法，按需生效
5. **缓存优化**：部门树结构缓存到 Caffeine，避免频繁的递归查询

## 为什么（Why）

1. **业务需求**：车队管理场景中，部门经理只能看到本部门及下属部门的车辆，普通员工只能看到自己的数据。这种行级数据过滤无法通过菜单权限（`@SaCheckPermission`）实现
2. **数据安全**：没有数据权限拦截，所有用户看到全公司的车辆、设备、报警数据，存在信息泄露风险
3. **代码简洁**：如果不使用拦截器，每个查询方法都需要手动判断用户角色和数据范围，拼接 SQL 条件，代码量大且容易遗漏
4. **架构要求**：CLAUDE.md 第四章明确定义了 5 种数据权限范围（全部/本部门及子部门/本部门/仅本人/自定义），需要集中实现
5. **灵活性**：通过注解标记，只有需要的查询才触发数据过滤，不影响系统级查询

# 二、定位与上下文（Where & When）

## 在哪里（Where）

位于 `gentry-core` 模块的 `com.gentry.core.data` 包中，作为 MyBatis-Flex 的 SQL 拦截器，在多租户拦截器之后、SQL 执行之前生效。

在权限控制链路中的位置：

```
请求进入
  → Sa-Token 拦截器 → 功能权限校验（@SaCheckPermission） ← 你能访问这个接口吗？
  → Controller → Service → Mapper
  → [多租户拦截器] → WHERE tenant_id = ?                ← 只看本租户数据
  → [数据权限拦截器] → AND dept_id IN (...)              ← 只看有权限的数据
  → SQL 执行 → Database
```

依赖关系：

- **被依赖方**：所有需要行级数据过滤的业务模块（车辆管理、设备管理、报警管理等）
- **依赖方**：
  - MyBatis-Flex 拦截器机制
  - `UserContext`（获取当前用户ID和部门ID）
  - `StpInterfaceImpl`（获取当前用户的角色和数据权限范围）
  - `DeptMapper`（查询部门树结构）
  - `@DataScope` 注解（标记需要数据过滤的方法）
  - Caffeine 缓存（部门树缓存）

## 在何时（When）

触发场景：

| 触发场景 | data_scope | SQL 追加条件 | 说明 |
|----------|------------|--------------|------|
| 平台管理员查询 | 1（全部数据） | 无追加 | 可看全租户数据 |
| 部门经理查询 | 2（本部门及子部门） | `AND dept_id IN (100, 101, 102)` | 递归查部门树 |
| 部门主管查询 | 3（本部门） | `AND dept_id = 100` | 仅本部门 |
| 普通员工查询 | 4（仅本人） | `AND create_by = 42` | 仅自己创建的数据 |
| 自定义范围 | 5（自定义） | `AND dept_id IN (100, 103, 105)` | 按配置的部门列表 |

不触发场景：

- Mapper 方法未标注 `@DataScope` 注解
- 系统级查询（无用户上下文）
- 超级管理员角色（`super_admin`）跳过数据过滤

# 三、主要用户与交互方（Who）

## 面向谁（Who）

| 角色 | 关注点 |
|------|--------|
| **后端开发** | 在 Mapper 查询方法上加 `@DataScope` 注解，无需手动拼 SQL 条件 |
| **系统管理员** | 通过角色管理配置 data_scope，控制各角色的数据可见范围 |
| **业务用户** | 自动看到权限范围内的数据，无需手动筛选 |
| **安全审计** | 验证行级数据过滤无遗漏，无越权访问 |

| 交互组件 | 交互方式 | 说明 |

| 多租户拦截器 | 协作 | 两者共存，先租户隔离再数据过滤 |

# 四、实现思路（How）

## 核心技术方案

### 4.1 @DataScope 注解设计

```java
/**
 * 数据权限注解
 * 标注在 Mapper 方法上，启用行级数据过滤
 */
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
@Documented
public @interface DataScope {

    /**
     * 部门ID字段名
     * 默认 "dept_id"，如果实体类中部门字段名不同可自定义
     */
    String deptField() default "dept_id";

    /**
     * 用户ID字段名（用于 "仅本人" 场景）
     * 默认 "create_by"
     */
    String userField() default "create_by";
}
```

使用示例：

```java
@Mapper
public interface VehicleMapper extends BaseMapper<Vehicle> {

    @DataScope(deptField = "dept_id", userField = "create_by")
    default Page<Vehicle> selectPage(VehicleQuery query) {
        return QueryChain.of(Vehicle.class)
            .where(Vehicle::getPlateNumber).like(query.getPlateNumber(),
                 query.getPlateNumber() != null)
            .page(new Page<>(query.getPageNum(), query.getPageSize()));
    }
}
```

### 4.2 数据权限处理流程

```
Mapper 方法执行
  → 检查是否有 @DataScope 注解
    → 无注解：跳过，直接执行 SQL
    → 有注解：
      → 获取当前用户角色列表
      → 取最高权限角色的 data_scope（值最小的，即范围最大的）
      → 根据 data_scope 追加 SQL 条件：

        data_scope = 1（全部数据）：
          → 不追加条件

        data_scope = 2（本部门及子部门）：
          → 获取用户 dept_id
          → 从缓存获取部门树，递归获取所有子部门ID
          → 追加 AND dept_id IN (deptId, childId1, childId2, ...)

        data_scope = 3（本部门）：
          → 获取用户 dept_id
          → 追加 AND dept_id = #{deptId}

        data_scope = 4（仅本人）：
          → 获取用户 userId
          → 追加 AND create_by = #{userId}

        data_scope = 5（自定义）：
          → 查询 custom_data_scope 表获取配置的部门ID列表
          → 追加 AND dept_id IN (customDeptId1, customDeptId2, ...)
```

### 4.3 部门树缓存策略

部门树结构在短时间内变化极少，使用 Caffeine 缓存可大幅减少数据库查询：

```java
// 缓存配置
Cache<Long, List<Long>> deptTreeCache = Caffeine.newBuilder()
    .maximumSize(1000)           // 最多缓存 1000 个租户的部门树
    .expireAfterWrite(30, TimeUnit.MINUTES)  // 写入后 30 分钟过期
    .recordStats()               // 记录缓存统计
    .build();

// 缓存 Key: tenantId
// 缓存 Value: Map<deptId, childDeptIds>
```

缓存失效策略：

| 场景 | 失效操作 |
|------|----------|
| 新增部门 | 清除该租户的部门树缓存 |
| 删除部门 | 清除该租户的部门树缓存 |
| 移动部门（修改 parent_id） | 清除该租户的部门树缓存 |
| 修改部门名称 | 不影响树结构，不清除 |

### 4.4 多角色数据权限合并

一个用户可能有多个角色，数据权限取"最大范围"：

| 角色A data_scope | 角色B data_scope | 最终 data_scope | 说明 |
|------------------|------------------|-----------------|------|
| 1（全部） | 3（本部门） | 1 | 取最大范围 |
| 2（部门及子部门） | 3（本部门） | 2 | 取最大范围 |
| 4（仅本人） | 3（本部门） | 3 | 取最大范围 |

合并规则：取所有角色中 `data_scope` 值最小的（范围最大的）。

### 4.5 自定义数据范围存储

当 `data_scope = 5` 时，需要查询自定义的部门列表：

```sql
-- role_custom_scope 表
CREATE TABLE role_custom_scope (
    id BIGINT PRIMARY KEY,
    role_id BIGINT NOT NULL,      -- 角色ID
    dept_id BIGINT NOT NULL,      -- 授权的部门ID
    tenant_id BIGINT NOT NULL,    -- 租户ID
    create_time TIMESTAMP DEFAULT NOW()
);

-- 查询某角色的自定义部门列表
SELECT dept_id FROM role_custom_scope WHERE role_id = #{roleId}
```

```
┌──────────────────────────────────────────────────────────────┐
│                   数据权限处理流程                              │
│                                                               │
│  Mapper.selectPage(query)                                     │
│     │ + @DataScope 注解                                       │
│     ▼                                                         │
│  ┌───────────────────────────────────────────────────────┐   │
│  │ DataScopeHandler                                      │   │

│  │                                                        │   │
│  │  ③ 根据 data_scope 生成 SQL 条件                        │   │
│  │     ┌─────────────────────────────────────────┐       │   │

│  │  ④ 追加条件到原始 SQL                                    │   │

```

# 五、预期效果与验收标准

## 性能指标

| 指标 | 目标值 | 说明 |
|------|--------|------|
| 拦截器处理耗时 | < 5ms | 含缓存查询和 SQL 条件拼接 |
| 部门树缓存命中率 | > 95% | 部门树变化频率低 |
| SQL 追加条件不影响索引 | dept_id 有索引 | 追加的 IN 条件走索引 |

## 功能验收标准

| 编号 | 验收项 | 验证方式 |
|------|--------|----------|
| D-001 | 全部数据（data_scope=1）不追加条件 | 管理员查询，验证 SQL 无 dept_id 条件 |
| D-002 | 本部门及子部门（data_scope=2）正确追加 IN 条件 | 部门经理查询，验证 SQL 包含所有子部门 |
| D-003 | 本部门（data_scope=3）正确追加等值条件 | 部门主管查询，验证 SQL 仅包含本部门 |
| D-004 | 仅本人（data_scope=4）正确追加 create_by 条件 | 普通员工查询，验证 SQL 包含 create_by |
| D-005 | 自定义（data_scope=5）正确追加配置的部门 | 自定义角色查询，验证 SQL 包含配置的部门列表 |
| D-006 | 无 @DataScope 注解不触发过滤 | 未标注注解的查询方法，验证 SQL 无额外条件 |
| D-007 | 超级管理员跳过数据过滤 | super_admin 角色查询，验证无额外条件 |
| D-008 | 多角色取最大范围 | 用户有多个角色，验证取范围最大的 data_scope |
| D-009 | 部门树缓存生效 | 连续查询，验证数据库查询仅执行一次 |
| D-010 | 部门变更后缓存失效 | 新增子部门后，验证下次查询获取新部门树 |
| D-011 | 与多租户拦截器共存 | 同时启用两个拦截器，验证 SQL 同时包含 tenant_id 和 dept_id 条件 |

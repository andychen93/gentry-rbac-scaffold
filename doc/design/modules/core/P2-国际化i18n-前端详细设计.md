# 一、模块概述

## 1.1 模块功能描述

前端承担 i18n 的**大头**：531 条去重词条的界面文案，加上后端下发的 92 个 B 类 key 的译文。

四件事：

1. **装配 react-i18next**：namespace 划分、懒加载、类型生成，与 antd `ConfigProvider locale` 联动
2. **翻译 B 类 key**：菜单树与字典项由后端下发 `i18nKey`，前端渲染时 `t(i18nKey) ?? name`
3. **语言切换**：纯前端切换（零 API 往返完成 UI 重渲染）+ 持久化 + 异步落库
4. **防线**：ESLint 拦新增硬编码、对账测试防语言包与库脱节

## 1.2 模块边界与职责

| 归前端 | 归后端 |
|--------|--------|
| 界面写死文案（按钮/表头/提示/占位符） | ErrorCode 消息 |
| 菜单名译文（`menu.*` key 的 value） | 校验失败提示 |
| 字典标签译文（`dict.*` key 的 value） | `@Log` 的 module / title |
| antd 组件文案（经 ConfigProvider） | Excel 表头与单元格枚举 |
| 日期/数字格式（dayjs locale） | 通知 / 短信模板 |
| 语言选择器 UI 与持久化 | `i18nKey` 的**派生**（前端只消费不计算） |

**明确不做**：

- 不翻译 C 类用户录入数据。英文界面显示用户昵称「张三」、租户自建部门「华东分公司」是**正确行为**
- 不自己派生 `i18nKey`。`MenuNavItem` 现状**不含 `permission` 字段**（只有 id/parentId/name/path/component/icon/type/sort/visible/children），前端没有派生所需的输入，必须由后端下发
- 不翻译 `src/pages/dev/**`（`/dev/style` 样式对照页，AGENTS.md 已特批可写死，实测 226 串 / 180 去重全部排除）

## 1.3 现状基线

| 接口 | 方法 | 用途 | 时机 |

## 2.3 请求头约定

`services/request.ts` 的请求拦截器统一带上 `Accept-Language`，取自当前 i18next 语言（BCP47 格式）：

```ts
config.headers['Accept-Language'] = i18n.language;   // 'zh-CN' / 'en-US'
```

这条是**登录前唯一的语言通道**——此时后端拿不到 `sys_user.language`，只能靠这个头。后端 `GentryLocaleResolver` 同时接受 `zh-CN` 与 `zh_CN` 两种写法。

```
│   ├── tenant.json           pages/tenant
│   ├── dept.json             pages/dept
```

namespace 与 `pages/` 子目录一一对应，唯两处改名：`pages/menu` → `menuMgmt`、`pages/dict` → `dictMgmt`，因为 `nav`（菜单名译文）与 `dict`（字典项译文）已占用了 menu/dict 的语义。`components/` 的词条并入 `common`——Pro 组件与布局组件的文案本质就是通用词条。

## 3.2 key 命名与分隔符

**采用扁平 key + 关闭 keySeparator。**

```ts
// locales/index.ts
i18n.init({
  keySeparator: false,      // 关键：key 里的点不再表示嵌套
  nsSeparator: ':',
  ...
});
```

原因：后端派生的 B 类 key 形如 `menu.system.user`、`dict.sys_user_gender.1`，若开启 `keySeparator`，i18next 会把它当成三层嵌套路径去查，而 `dict.sys_user_gender.1` 里的 `1` 作为对象键更是自找麻烦。关掉之后 JSON 是扁平的，key 原样命中：

```json
// zh-CN/nav.json
{
  "menu.system": "系统管理",
  "menu.system.user": "用户管理",
  "menu.system.tenant.list": "查询",
  "menu.monitor.redis.info": "Redis 监控"
}
```

```json
// zh-CN/dict.json
{
  "dict.sys_data_scope.1": "全部数据",
  "dict.sys_user_gender.1": "男",
  "dict.sys_user_post.CEO": "首席执行官",
  "dict.type.sys_user_gender": "用户性别"
}
```

Ant Design Pro 也是扁平 key（`'menu.list.table-list'`），这不是权宜之计。

页面 namespace 的 key 命名约定 `{区域}.{语义}`：

```json
// zh-CN/user.json
{
  "title": "用户管理",
  "table.username": "用户名",
  "table.nickname": "昵称",
  "form.username.placeholder": "请输入用户名",
  "form.username.required": "用户名不能为空",
  "action.resetPwd": "重置密码",
  "confirm.disable": "确定要禁用该账号吗？"
}
```

## 3.3 「同词不同境」的处理

实测 `操作` 出现 13 次，在表格表头是 Action，在操作日志语境是 Operation。**这是必须靠 key 区分的，不能共用一条 common 词条**：

```json
// common.json
{ "action": "操作", "status": "状态", "edit": "编辑", "delete": "删除" }
// log.json
{ "table.operation": "操作" }
```

规则：**只有语义确定唯一的词才进 `common`**。拿不准就放页面 namespace，重复几条译文远比选错语义便宜。

## 3.4 类型安全

```ts
// locales/types.d.ts —— 由 json 结构自动推导，key 写错编译期报错
import type common from './zh-CN/common.json';
import type nav from './zh-CN/nav.json';
// ...
declare module 'i18next' {
  interface CustomTypeOptions {
    defaultNS: 'common';
    keySeparator: false;
    resources: {
      common: typeof common;
      nav: typeof nav;
      dict: typeof dict;
      user: typeof user;
      // ...
    };
  }
}
```

Soybean Admin 用的是同一思路（`App.I18n.I18nKey` 联合类型），是这个方案相对「后端译好成品下发」的一项净优势：**key 拼错在 `npx tsc -b` 阶段就红，不用等到运行时看见裸 key**。

四个包，版本按 AGENTS.md 的要求**锁定精确版本或谨慎范围**，不用 `latest`。

**刻意不引入的两个常见包**：

| 包 | 不用的理由 |
|----|-----------|
| `i18next-browser-languagedetector` | 检测逻辑只有「localStorage → navigator → 默认」三步，`resolveInitialLocale()` 十行写完，且我们的优先级还要让服务端 `UserInfoVO.language` 插队。引入它反而要配一堆 `order`/`caches` 去关掉它的默认行为 |
| `i18next-http-backend` | 语言包随前端构建产物走，不从 HTTP 拉。用 `resourcesToBackend` + 动态 `import()` 让 Vite 天然做代码分割，比运行时 HTTP 请求更快且无额外失败路径 |

`dayjs` 与 `antd/locale/*` 已在现有依赖中，无需新增。

## 4.1 i18next 装配

```ts
// locales/config.ts
export const SUPPORTED_LOCALES = ['zh-CN', 'en-US'] as const;
export type AppLocale = (typeof SUPPORTED_LOCALES)[number];
export const DEFAULT_LOCALE: AppLocale = 'zh-CN';
export const LOCALE_STORAGE_KEY = 'gentry_locale';

/** 'zh-CN'(前端/BCP47) → 'zh_CN'(后端/Java) */
export const toBackendLocale = (l: AppLocale): string => l.replace('-', '_');

/**
 * 任意来源的语言串 → 受支持的 AppLocale，不受支持返回 null。
 * 接受 'zh-CN' / 'zh_CN' / 'zh' / 'ZH-cn' 等写法。
 */
export const toAppLocale = (raw?: string | null): AppLocale | null => {
  if (!raw) return null;
  const normalized = raw.trim().replace('_', '-').toLowerCase();
  // ① 精确匹配（大小写无关）
  const exact = SUPPORTED_LOCALES.find((l) => l.toLowerCase() === normalized);
  if (exact) return exact;
  // ② 仅语言码匹配：'zh' → 'zh-CN'，'en' → 'en-US'
  const lang = normalized.split('-')[0];
  return SUPPORTED_LOCALES.find((l) => l.toLowerCase().split('-')[0] === lang) ?? null;
};
```

② 分支与后端 `GentryLocaleResolver.matchHeader` 的语言退化逻辑对称——两边都要能把 `en` 收敛到 `en-US`，否则「浏览器只发 `en`」时前后端会得出不同语言，界面英文而错误提示中文。这种前后端不一致是最难查的一类 i18n bug，由 U-05 与后端 U-07 分别锁住。

```ts
// locales/index.ts
const NAMESPACES = ['common', 'nav', 'dict', 'user', 'role', 'tenant', 'dept',
  'menuMgmt', 'dictMgmt', 'config', 'log', 'monitor', 'profile', 'home', 'login'] as const;

export function resolveInitialLocale(): AppLocale {
  // ① localStorage（上次选择，登录前唯一可用来源）
  const stored = toAppLocale(localStorage.getItem(LOCALE_STORAGE_KEY));
  if (stored) return stored;
  // ② 浏览器语言
  const nav = toAppLocale(navigator.language);
  if (nav) return nav;
  // ③ 兜底
  return DEFAULT_LOCALE;
}

await i18n.use(initReactI18next).use(resourcesToBackend(
  (lng: string, ns: string) => import(`./${lng}/${ns}.json`)   // 按需懒加载
)).init({
  lng: resolveInitialLocale(),
  fallbackLng: DEFAULT_LOCALE,
  ns: ['common', 'nav', 'dict'],        // 启动只加载这三个
  defaultNS: 'common',
  keySeparator: false,
  nsSeparator: ':',
  interpolation: { escapeValue: false },  // React 自身已转义
  returnNull: false,
  // 生产环境不打印缺 key 警告，但保留控制台可见性用于开发
  missingKeyHandler: import.meta.env.DEV ? (lng, ns, key) => {
    console.warn(`[i18n] missing key: ${ns}:${key} (${lng})`);
  } : undefined,
});
```

`nav` 与 `dict` 必须随启动加载——侧边栏和字典标签在首屏就要渲染，懒加载会闪。其余页面 namespace 由页面组件自己声明 `useTranslation('user')` 触发按需加载。

## 4.2 应用启动流程

```
index.html
  └→ main.tsx
       ├─ await setupI18n()                     ← 必须 await，否则首屏闪原文
       │    └─ resolveInitialLocale(): localStorage → navigator → zh-CN
       ├─ <ConfigProvider locale={antdLocale} theme={argonTheme}>
```

## 4.3 antd 与 dayjs 联动

```ts
// locales/antd.ts
import zhCN from 'antd/locale/zh_CN';
import enUS from 'antd/locale/en_US';
import 'dayjs/locale/zh-cn';
import 'dayjs/locale/en';
import dayjs from 'dayjs';

const ANTD_LOCALES = { 'zh-CN': zhCN, 'en-US': enUS } as const;

export function getAntdLocale(lng: string) {
  return ANTD_LOCALES[toAppLocale(lng) ?? DEFAULT_LOCALE];
}

export function syncDayjsLocale(lng: string) {
  dayjs.locale(toAppLocale(lng) === 'en-US' ? 'en' : 'zh-cn');
}
```

三者必须同步：i18next（自有文案）、antd `ConfigProvider`（分页「共 X 条」、日期选择器、表格空态）、dayjs（日期格式化）。漏掉 dayjs 的典型症状是界面全英文但日期还是「2026年8月17日」。

# 五、语言切换流程设计

## 5.1 切换流程

```
用户在个人中心或顶栏选择 English
    │
    └→ useLocale().setLocale('en-US')
         ├─ ① await i18n.changeLanguage('en-US')
         │      └─ 懒加载 en-US 的已注册 namespace
         │      └─ 所有 t() 触发重渲染（含侧边栏菜单，因未预算 label）
         ├─ ② syncDayjsLocale('en-US')
         ├─ ③ ConfigProvider locale 随 i18n.language 变化自动切换
         ├─ ④ localStorage.setItem('gentry_locale', 'en-US')
         │      └─ 保证下次打开登录页就是英文
         └─ ⑤ 已登录？→ PUT /api/v1/users/me/language { language: 'en_US' }
                └─ **异步、不 await、失败只 toast 不回滚**
                   界面已经切好了，落库失败只影响下次登录与后端场景
```

## 5.2 为什么切换不需要重新请求菜单接口

因为菜单树在 store 里存的是**原始数据** `{ name, i18nKey }`，label 在渲染时才计算。语言变化触发 `useTranslation` 重渲染，label 自然变。

Soybean Admin（Vue）为此专门写了 `updateLocaleOfGlobalMenus()` 遍历内存菜单树重算 label——因为它把 `label` 算好存进了 store。**React 的渲染模型让我们不需要这个函数，前提是绝不把 label 提前算进 store。**

这是本设计里最容易被无意破坏的一条约束，必须写进 frontend-conventions。

## 5.3 useLocale Hook

```ts
// hooks/useLocale.ts
export function useLocale() {
  const { i18n } = useTranslation();
  const locale = (toAppLocale(i18n.language) ?? DEFAULT_LOCALE);

  const setLocale = useCallback(async (next: AppLocale) => {
    if (next === locale) return;
    await i18n.changeLanguage(next);
    syncDayjsLocale(next);
    localStorage.setItem(LOCALE_STORAGE_KEY, next);
    if (useUserStore.getState().isLoggedIn) {
      updateMyLanguage(toBackendLocale(next)).catch(() => {
        message.warning(i18n.t('locale.persistFailed'));
      });
    }
  }, [locale, i18n]);

  return { locale, setLocale, supported: SUPPORTED_LOCALES };
}
```

# 六、组件设计与调用规范

## 6.1 菜单渲染（B 类核心）

```tsx
// components/layout/MenuList.tsx
const { t } = useTranslation('nav');

function labelOf(item: MenuNavItem): string {
  // i18nKey 为 null（permission/path 皆空，如派生项目新增的菜单）→ 回退库里的 name
  // i18nKey 有值但语言包缺 key → t 的 defaultValue 兜底为 name
  return item.i18nKey ? t(item.i18nKey, { defaultValue: item.name }) : item.name;
}
```

与 Soybean Admin 的 `const label = i18nKey ? $t(i18nKey) : title!` 同构，额外加了 `defaultValue` 兜底，保证**语言包缺 key 时显示中文而不是裸 key**（对应验收项 A-5）。

## 6.2 面包屑：消除重复真源

现状 `components/layout/AppHeader.tsx` 有一份 `BREADCRUMB_MAP`，它是**菜单名的第二份拷贝**。i18n 之后若保留，就要维护两处译文且必然漂移。

改造：面包屑名称改为复用 `nav` namespace，key 由当前路由 path 按后端同一规则派生：

```ts
// utils/navKey.ts —— 与后端 MenuI18nKeyResolver 的 path 分支保持一致
export const navKeyFromPath = (path: string) => 'menu' + path.replace(/\//g, '.');
```

优先从 `userStore.menus` 里按 path 匹配到节点直接取其 `i18nKey`（权威）；匹配不到（非菜单子页面，如 `system/roles/:id/permissions`）才用 `navKeyFromPath` 派生，并在 `nav.json` 里补对应 key。`BREADCRUMB_MAP` 随之删除。

## 6.3 字典标签

```tsx
// components/DictTag.tsx
const { t } = useTranslation('dict');
const label = item.i18nKey ? t(item.i18nKey, { defaultValue: item.dictLabel })
                           : item.dictLabel;
```

`DictSelect` 同理。`i18nKey` 为 null（派生项目新增的、语言包里没有的字典项）→ 显示原始 `dictLabel`。

### 6.3.1 字典管理页必须锁住「有译文」的 label 输入

派生 key 会让**译文优先于库里的 `dict_label`**，于是管理员在字典管理页把 `sys_user_gender`/`1` 从「男」改成「男性」，保存成功、界面还是「男」，而且无法自查。这个问题**与租户数量无关，单租户下同样存在**（概要设计 §5.3 已记为已知代价）。

缓解方式是把约束摆在动作发生的地方，而不是让人事后困惑。前端本来就持有语言包，一句 `i18n.exists()` 就能判断：

```tsx
// pages/dict/DataFormModal.tsx
const { t, i18n } = useTranslation('dict');
// 该字典项的显示名是否由语言包接管
const managedByLocale = !!record?.i18nKey && i18n.exists(record.i18nKey, { ns: 'dict' });

<Form.Item
  name="dictLabel"
  label={t('dictMgmt:form.dictLabel')}
  extra={managedByLocale ? t('dictMgmt:form.dictLabel.localeManaged') : undefined}
>
  <Input disabled={managedByLocale} />
</Form.Item>
```

```json
// zh-CN/dictMgmt.json
{ "form.dictLabel.localeManaged": "该字典项的显示名由语言包管理，如需修改请改 locales/{lang}/dict.json" }
```

设计取舍：

| 取舍 | 理由 |
|------|------|
| 用 `i18n.exists()` 而非后端返回标记 | 语言包是唯一真源，且它在前端。后端不知道前端语言包里有什么，多加一个字段就多一处可能不一致 |
| **禁用**而非只给警告 | 允许保存一个不生效的值，等于制造一个必然被误认为 bug 的状态 |
| 只锁 `dictLabel`，不锁 `sort` / `remark` / `status` | 那些字段不参与 i18n，正常可改 |
| 字典**列表**列仍显示译文 | 与全站一致；列表和表单显示同一个值，不会自相矛盾 |

> 顺带一处清理：`components/common/DictTag.test.tsx` 现用 `dictType="vehicle_type"`（车辆类型），是从高精度定位平台带进来的业务概念残留，RBAC 脚手架里不该出现。改造这批文件时一并换成 `sys_user_gender`。

## 6.4 调用规范（写进 frontend-conventions）

| 规则 | 正例 | 反例 |
|------|------|------|
| 一律 `t()`，不写中文字面量 | `t('user:table.username')` | `'用户名'` |
| 组件顶层取 `t`，不在循环里调 `useTranslation` | `const { t } = useTranslation('user')` | 每行 map 里调 hook |
| 插值用命名参数，不用字符串拼接 | `t('common:total', { count })` | `` `共 ${count} 条` `` |
| 表格 columns 放进 `useMemo` 且依赖 `t` | `useMemo(() => [...], [t])` | 模块级常量数组（语言切换不更新） |
| **不把翻译结果存进 Zustand** | store 存 `{ name, i18nKey }` | store 存算好的 `label` |
| 常量枚举文案用 key 不用文案 | `{ value: 1, labelKey: 'common:enabled' }` | `{ value: 1, label: '启用' }` |

**「表格 columns 放进 useMemo 且依赖 t」这条是最高频的踩坑点**：现状很多页面把 columns 写成模块级常量，语言切换后表头不会变，且这个 bug 在中文环境下永远不会暴露。

# 八、状态管理设计

## 8.1 语言状态放在哪

**不新建 Zustand store。** i18next 实例自身就是语言的唯一真源，`useTranslation()` 已提供订阅与重渲染。再套一层 Zustand 会出现两个真源、需要双向同步。

| 状态 | 存放 | 理由 |
|------|------|------|
| 当前语言 | i18next 实例（`i18n.language`） | 唯一真源，自带订阅 |
| 语言持久化 | `localStorage['gentry_locale']` | 登录前可用 |
| 用户语言偏好 | `sys_user.language`（服务端） | 跨设备、供后端场景使用 |
| 菜单原始树 | `userStore.menus` | 已有，仅新增 `i18nKey` 字段 |

三处可能不一致，收敛规则：**登录/刷新时以服务端 `UserInfoVO.language` 为准**，覆盖 localStorage 与 i18next；**用户手动切换时以本地为准**，异步写回服务端。

## 8.2 userStore 约束

```ts
// stores/userStore.ts —— menus 只存原始数据
set({ token, userInfo, menus: userInfo.menus || [], isLoggedIn: true, ... });
```

现状写法已经是原样存，**不需要改，但必须加注释锁住这个行为**，防止后来者「优化」成预算 label。

# 九、迁移方案（531 条词条）

## 9.1 抽词与改写

全自动改写不可靠（模板串、拼接、注解式配置对象），采用**脚本产候选 + 人工过一遍 + codemod 应用**：

```
scripts/i18n/
├── extract.mjs      扫描 → 产出候选清单 candidates.json
│                    每条: { file, line, text, proposedNs, proposedKey, occurrences }
├── review.md        人工过 key 命名与 common/页面 归属（同词不同境在这一步定）
├── apply.mjs        按确认后的映射做 codemod：插入 useTranslation、替换字面量
└── translate.mjs    由 zh-CN 生成 en-US 骨架（机翻占位，标记 TODO 待校对）
```

### extract.mjs 算法

```
1. 遍历 src/**/*.{ts,tsx}，排除 pages/dev、*.test.*、e2e
2. 用与基线统计一致的正则提取引号内含 CJK 的字符串字面量：
   /['"`]([^'"`\n]*[\u4e00-\u9fff]+[^'"`\n]*)['"`]/g
3. 对每条候选计算：
   ├─ proposedNs   ← 文件路径映射（见下表）
   ├─ proposedKey  ← 按「所在语法位置」推断区域前缀 + 文案 slug
   └─ occurrences  ← 全仓出现次数（决定是否升格进 common）
4. occurrences >= 3 且语义唯一 → 候选 ns 改为 common
5. 输出 candidates.json + unresolved.txt
```

`proposedNs` 映射：

| 文件路径 | namespace |
|----------|-----------|
| `src/pages/user/**` | `user` |
| `src/pages/menu/**` | `menuMgmt` |
| `src/pages/dict/**` | `dictMgmt` |
| `src/pages/{x}/**` | `{x}` |
| `src/components/**` | `common` |
| `src/{services,utils,stores,hooks,types,config}/**` | `common` |

`proposedKey` 的区域前缀按语法位置推断：

| 出现位置 | 前缀 | 示例 |
|----------|------|------|
| `columns` 数组的 `title` | `table.` | `table.username` |
| `placeholder` 属性 | `form.{field}.placeholder` | `form.username.placeholder` |
| 校验 `rules` 的 `message` | `form.{field}.required` | `form.username.required` |
| `Modal.confirm` / `content` | `confirm.` | `confirm.disable` |
| `message.success` / `error` | `msg.` | `msg.saveSuccess` |
| `<Button>` 文本 | `action.` | `action.resetPwd` |
| 其余 | 无前缀 | `title` |

文案 slug 由拼音首字母或人工填写——**脚本只给建议，`review.md` 阶段人工定稿**。自动生成的 key 名不可信，这一步不能省。

`unresolved.txt` 收录两类正则抓不到的情况，必须人工过：

1. **含中文但整行没有 `t()`** 的行——模板串拼接（实测有 `共 ${t} 条` 4 处）、跨行字符串、`.join('、')` 这类分隔符
2. **中文出现在非字符串位置**——JSX 文本节点 `<span>用户名</span>`（正则抓不到引号外的中文）

第 2 类需要单独一遍 JSX 文本节点扫描（用 `@babel/parser` 走 AST，匹配 `JSXText` 节点）。这是纯正则方案的已知盲区，JeeSite 的抽词工具同样只能把「含中文又没包 `text()`」的行报给人看。

### apply.mjs 的改写动作

对每个确认的候选，codemod 执行三步：

```
① 确保文件顶部有 import { useTranslation } from 'react-i18next'
② 确保组件内有 const { t } = useTranslation('{ns}')
   ├─ 已有同 ns 的声明 → 跳过
   └─ 非组件（如 services/、utils/）→ 改用 import i18n from '@/locales'; i18n.t(...)
③ 字面量替换为 t('{ns}:{key}')，跨 ns 引用保留显式前缀
```

第 ② 步的 `services/` / `utils/` 分支很容易漏——那里没有 React 组件，不能用 hook，必须走 i18next 实例的静态 `t`。实测 `services` 有 7 条、`utils` 11 条、`stores`/`hooks`/`types`/`config` 各 2~3 条，共约 19 条走这条分支。

## 9.2 批次顺序

按「先高频、先框架、后页面」，每批可独立提交并跑绿测试：

| 批次 | 范围 | 词条量（去重） | 完成标志 |
|------|------|---------------|----------|

### 10.2.1 key 对账放在 E2E（原 F-02）

对账要回答的是「语言包里的 `menu.*` key 与**库里真实派生出来的** key 是否对得上」。Vitest 拿不到库，只能靠一个静态清单文件，而清单**谁生成、何时生成、如何防过期**没有干净答案：后端测试生成会造成「前端测试依赖后端测试先跑」的 CI 顺序耦合，手工维护则必然过期。所以这条放进 E2E —— 那里同时有真实后端和真实语言包。

```ts
// e2e/14-i18n.spec.ts
import fs from 'node:fs';

// Playwright 测试跑在 Node 里，可以直接读语言包源文件
const nav  = JSON.parse(fs.readFileSync('src/locales/zh-CN/nav.json', 'utf-8'));
const dict = JSON.parse(fs.readFileSync('src/locales/zh-CN/dict.json', 'utf-8'));

test('I18N-001 语言包里的每个 menu.* key 都能从库中派生出来', async ({ request }) => {
  // 用 SUPER_ADMIN(chenli) 的 Token —— 它能看到全部 71 条菜单
  const res = await request.get('/api/v1/users/me', { headers: { token: tokens.chenli } });
  const derived = new Set<string>();
  const walk = (nodes: any[]) => nodes.forEach((n) => {
    if (n.i18nKey) derived.add(n.i18nKey);
    if (n.children?.length) walk(n.children);
  });
  walk((await res.json()).data.menus);

  const orphans = Object.keys(nav).filter((k) => !derived.has(k));
  expect(orphans, `语言包里这些 key 已无对应菜单（permission 被改？菜单被删？）：${orphans}`)
    .toEqual([]);
});
```

**断言方向是单向的：语言包 → 库。反向不断言。** 两条理由：

1. **派生项目新增菜单不该红灯。** 它加一个业务菜单、暂时不加译文，回退显示 `name` —— 这是设计明确允许的。双向断言会让它每加一个菜单就红，那这个测试三天内就会被注释掉，防线归零。
2. **库里现在就有脏数据可以印证。** E2E 残留的 `测试按钮114393` / `permission=test:btn:114393` 会派生出 `menu.test.btn.114393`，语言包里当然没有。**双向断言此刻就是红的**，而它并不指示任何真实缺陷。

单向断言的覆盖范围：

| 场景 | 能否发现 |
|------|---------|
| 有人改了 `sys_menu.permission`，语言包里的旧 key 派生不出来 | ✅ 红灯（**首要目标**） |
| 脚手架自带菜单被删 | ✅ 红灯 |
| 语言包留了死条目 | ✅ 红灯 |
| 漏译某条脚手架菜单 | ❌ 由 I18N-002 兜（见下） |

漏译单靠 I18N-001 查不到，因为 `t(key, { defaultValue: name })` 会安静地回退成中文。补一条正面断言：

```ts
test('I18N-002 en-US 用户的侧边栏不含任何中文字符', async ({ page }) => {
  await loginAs(page, 'zhangsan');          // language = en_US，见 §12.3
  const text = await page.locator('[data-testid="sidebar"]').innerText();
  expect(text).not.toMatch(/[\u4e00-\u9fff]/);
});
```

漏译 → 回退显示中文 `name` → 侧边栏出现中文 → 红灯。**这条断言对脚手架成立（71/71 都有译文）**；派生项目若新增了未翻译的菜单，需把它改成白名单式（排除自己新增的那些 key），这个维护成本要写进 README 的「派生项目须知」。

# 十一、性能优化设计

| 优化项 | 手段 | 效果 |
|--------|------|------|
| 语言包体积 | `resourcesToBackend` + 动态 import 按 namespace 懒加载 | 首屏只加载 `common`/`nav`/`dict` |
| 切换语言 | 纯前端，零 API 往返 | 无网络等待 |
| 菜单重渲染 | 渲染时算 label，不预存 | 避免整树遍历重算（Soybean 需要那个遍历） |
| 表格 columns | `useMemo(() => [...], [t])` | 语言不变时不重建 columns |
| antd locale | 由 `i18n.language` 派生，不额外订阅 | 无多余渲染 |
| 落库请求 | fire-and-forget，不 await | 不阻塞 UI |

反模式清单：

- ❌ 启动时一次性加载所有语言的所有 namespace
- ❌ 在 `map`/`forEach` 内部调 `useTranslation()`
- ❌ 把 `t()` 结果存进 Zustand 或 TanStack Query 的缓存数据里
- ❌ 模块级常量数组承载文案（语言切换不生效）

## 12.3 E2E 验收（Playwright）

对应概要设计 §六 的硬门槛：

| 编号 | 场景 | 断言 |
|------|------|------|
| E-01 | `sys_user.language='en_US'` 用户登录 | 侧边栏全英文 |
| E-02 | 进入用户管理页 | 表头、查询/重置按钮、分页文案全英文 |
| E-03 | 故意提交空表单 | 校验提示为英文 |
| E-04 | 触发后端错误（删除不存在的角色） | 错误提示为英文 |
| E-05 | 全页文本正则扫描 | 不出现 `menu.` / `dict.` / `error.` / `{` 开头的裸 key |
| E-06 | 顶栏切换语言 | 菜单文案立即变化，且**网络监听确认未请求菜单接口** |
| E-07 | 切换语言后刷新页面 | 语言保持（localStorage + 落库都生效） |
| E-08 | 未登录状态在登录页切换语言 | 登录页文案变化，且未发起落库请求 |
| I18N-001 | 语言包 `nav.json` 的每个 key vs `/users/me` 返回菜单树派生的 key | 无孤儿 key（单向断言，见 §10.2.1） |
| I18N-002 | en-US 用户侧边栏文本 | 不含任何 CJK 字符（兜漏译） |

E-06 的网络监听是本设计「纯前端切换」这一决策的唯一直接证据，不能省。

**I18N-001/002 是原 F-02 对账防线的落地形态**（见 §10.2.1）。它放在 E2E 而非 Vitest，代价是**不在提交前的快速门禁里**——AGENTS.md 规定 `npm run test:e2e` 只在「动了页面或权限」时跑。而改 `sys_menu.permission` 恰恰属于「动了权限」，所以这条规则本身就覆盖了触发场景。为稳妥起见，建议在 `.kiro/steering` 的后端约定里补一句：**改动 `sys_menu` 的 `permission` / `path` 或增删菜单迁移后，必须跑一次 `npm run test:e2e`**。

### E2E 的英文账号必须另起，不能改 admin

登录接口有 IP 限流（10 次/60 秒），Token 由 `e2e/global-setup.ts` 预登录后落盘复用，**不要在 spec 里逐个 test 走真实登录**。现状：

```ts
const ACCOUNTS: Record<string, string> = {
  admin:  'Abc@123456',
  chenli: 'Chenli@2026',
};
```

13 个 spec、65 个用例全部复用这两个 Token。**因此绝对不能把 `admin` 的 `language` 改成 `en_US`** —— 那会让所有断言中文文案的既有用例全部失败。

方案：征用内置的第三个账号 `zhangsan`（ADMIN 角色，密码 `Abc@123456`，实测在 `e2e/` 下零引用）。

```ts
const ACCOUNTS = {
  admin:    'Abc@123456',
  chenli:   'Chenli@2026',
  zhangsan: 'Abc@123456',    // i18n 专用：language 固定 en_US
};
```

`global-setup` 用 zhangsan 自己的 Token 调 `PUT /api/v1/users/me/language` 设为 `en_US`（接口只能改自己的，正好合适），`global-teardown` 改回 `zh_CN`。

登录次数从 2 次增到 3 次，距限流阈值 10 次仍有余量。

> 造脏数据的用例必须显式清理——**`@Transactional` 在 E2E 场景不回滚**，这是已有实测结论。语言偏好属于持久化状态，必须在 teardown 里复原，否则第二次运行时 zhangsan 已是 en_US，虽然本套用例仍能通过，但会污染手工测试环境。

# 一、设计概述

后端在 i18n 中承担三件事，**不承担菜单与字典标签的翻译**：

1. **语言解析**：把「当前请求属于哪种语言」确定下来，写入 `LocaleContextHolder`
2. **自产文案本地化**：ErrorCode、Bean Validation 校验消息、Excel 表头与枚举、通知/短信模板；`@Log` 的 **module** 按中文当 key 译成 `moduleLabel`（title 仍中文，见概要设计 §4.8.1）
3. **B 类 key 派生**：为 `MenuTreeVO`、字典 VO、角色 VO 计算 `i18nKey` 并下发，交给前端翻译

## 2.2 核心类详细设计

### 2.2.1 UserContext 扩展

在既有四个 ThreadLocal 之外增加 `LANGUAGE`，与 `TENANT_ID` 完全同构，由同一处拦截器写入、同一处 `clear()` 清理。

```java
public class UserContext {

    private static final ThreadLocal<Long> USER_ID = new ThreadLocal<>();
    private static final ThreadLocal<Long> TENANT_ID = new ThreadLocal<>();
    private static final ThreadLocal<Long> DEPT_ID = new ThreadLocal<>();
    private static final ThreadLocal<Boolean> PLATFORM_ADMIN = new ThreadLocal<>();
    private static final ThreadLocal<String> LANGUAGE = new ThreadLocal<>();   // 新增

    /** 用户语言偏好，形如 zh_CN / en_US；未登录或未设置时为 null */
    public static void setLanguage(String language) { LANGUAGE.set(language); }
    public static String getLanguage() { return LANGUAGE.get(); }

    public static void clear() {
        USER_ID.remove();
        TENANT_ID.remove();
        DEPT_ID.remove();
        PLATFORM_ADMIN.remove();
        LANGUAGE.remove();          // 新增，漏了会造成线程复用后语言串台
    }
}
```

> **必须同时改 `clear()`**。线程池复用下漏清理的后果是「上一个 en_US 用户的语言泄漏给下一个 zh_CN 用户」，且只在高并发下偶发，极难排查。这条要进单元测试。

写入点与 `tenantId` 相同——`SaTokenConfig` 的拦截器从 Sa-Token Session 恢复上下文处。登录时 `AuthServiceImpl` 把 `language` 一并写入 Session。

### 2.2.1b 语言的设置时机（必须显式，不能依赖 Spring 的懒求值）

`UserContext` 由 `SaTokenConfig` 里的 `HandlerInterceptor.preHandle` 写入，而 Spring 的 `LocaleResolver` 由 `DispatcherServlet` 调用。**两者的先后顺序决定「①用户偏好优先」这条链是否成立**，必须查清而不能假定。Spring 主干源码：

```java
// DispatcherServlet
/**
 * ...The default implementation uses the dispatcher's LocaleResolver to obtain
 * the current locale, which might change during a request.
 */
@Override
protected LocaleContext buildLocaleContext(final HttpServletRequest request) {
    LocaleResolver lr = this.localeResolver;
    if (lr instanceof LocaleContextResolver localeContextResolver) {
        return localeContextResolver.resolveLocaleContext(request);        // 饿求值
    }
    else {
        return () -> (lr != null ? lr.resolveLocale(request) : request.getLocale());  // 懒求值
    }
}
```

结论分两种情况：

| 实现的接口 | 求值时机 | 对本设计的影响 |
|-----------|----------|---------------|
| `LocaleResolver` | 返回 lambda，**每次 `LocaleContextHolder.getLocale()` 才执行** | 拦截器早已跑完，`UserContext` 有值 → 能工作 |
| `LocaleContextResolver` | 在 `doService` 之前一次性求值 | 拦截器还没跑，`UserContext` 为空 → **`sys_user.language` 永久失效** |

只实现 `LocaleResolver` 确实能工作，但**这是靠懒求值侥幸成立，有两个不可接受的后果**：

1. **重复解析**：`resolveLocale` 会在每次 `getLocale()` 时重跑，也就是每次 `I18nUtil.getMessage()` 都要重新走一遍 `Locale.LanguageRange.parse()`。一个日志列表页 20 行 × 2 个 label = 40 次头解析
2. **静默回归风险**：将来谁为了加时区支持把它改成 `LocaleContextResolver`（JeeSite 就是语言与时区一起管，这个演进方向很自然），语言解析会**无声地**退回请求头，`sys_user.language` 失效且不报任何错

**因此：不依赖懒求值，在拦截器里显式设置。** 改造 `SaTokenConfig` 的第 2 个拦截器（那个已经在写 `UserContext` 的）：

```java
@Override
public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) {
    if (StpUtil.isLogin()) {
        SaSession session = StpUtil.getSession();
        ...
        UserContext.setPlatformAdmin(Boolean.TRUE.equals(platformAdmin));
        Object language = session.get("language");
        if (language instanceof String s) UserContext.setLanguage(s);
    }
    // 语言在此一次性定稿：登录用户走偏好，未登录走请求头，都取不到走默认。
    // 不放在 LocaleResolver 里做，是为了不依赖 DispatcherServlet 的懒求值时序。
    LocaleContextHolder.setLocale(localeResolver.resolve(UserContext.getLanguage(), request));
    return true;
}
```

`LocaleContextHolder` 的 ThreadLocal 由 Spring 的 `FrameworkServlet.processRequest` 在 finally 里 `resetContextHolders(...)` 恢复，**不需要在 `afterCompletion` 里手动清**；`UserContext.clear()` 仍要保留。

相应地 `GentryLocaleResolver` 的角色收窄：

- 对外仍注册为 `LocaleResolver` bean，**只服务未经过 `/api/**` 拦截器的请求**（如 `/actuator/**`、静态资源）
- 解析逻辑抽成公开的 `resolve(String userLanguage, HttpServletRequest request)`，供拦截器与 `resolveLocale` 共用，保证两条路径行为一致
- **明确禁止改成实现 `LocaleContextResolver`**，这条要写进类的 Javadoc 与 backend-conventions

### 2.2.2 GentryLocaleResolver

```java
package com.gentry.core.i18n;

@Component
public class GentryLocaleResolver implements LocaleResolver {

    private static final Locale DEFAULT = Locale.SIMPLIFIED_CHINESE;   // zh_CN
    private final Set<Locale> supported;
    private final Locale defaultLocale;

    public GentryLocaleResolver(I18nProperties props) {
        this.defaultLocale = parse(props.getDefaultLocale()).orElse(DEFAULT);
        this.supported = props.getSupportedLocales().stream()
                .map(GentryLocaleResolver::parse)
                .flatMap(Optional::stream)
                .collect(Collectors.toUnmodifiableSet());
    }

    /**
     * 三级解析。**唯一的解析实现**，由 SaTokenConfig 拦截器与 resolveLocale 共用，
     * 保证「已登录请求」与「未登录/非 /api 请求」两条路径行为一致。
     *
     * @param userLanguage 用户偏好，来自 UserContext；未登录传 null
     */
    public Locale resolve(String userLanguage, HttpServletRequest request) {
        // ① 用户级偏好（已登录时权威），白名单过滤
        Locale fromUser = parse(userLanguage).orElse(null);
        if (fromUser != null && supported.contains(fromUser)) {
            return fromUser;
        }
        // ② 请求头（登录前 / 未设置偏好时；前端由 localStorage 或 navigator 计算后带上）
        Locale fromHeader = matchHeader(request.getHeader(HttpHeaders.ACCEPT_LANGUAGE));
        if (fromHeader != null) {
            return fromHeader;
        }
        // ③ 兜底
        return defaultLocale;
    }

    /**
     * 仅服务未经过 /api/** 拦截器的请求（actuator、静态资源）。
     * 已登录请求的语言由 SaTokenConfig 拦截器显式设置，见 §2.2.1b。
     *
     * <p><b>禁止把本类改成实现 LocaleContextResolver</b>：那会让 DispatcherServlet
     * 改为饿求值，在拦截器写 UserContext 之前就定稿语言，导致 sys_user.language
     * 静默失效。要加时区支持请另开一个组件。</p>
     */
    @Override
    public Locale resolveLocale(HttpServletRequest request) {
        return resolve(UserContext.getLanguage(), request);
    }

    @Override
    public void setLocale(HttpServletRequest req, HttpServletResponse resp, Locale locale) {
        throw new UnsupportedOperationException(
            "语言偏好由 sys_user.language 持久化，不支持通过 LocaleResolver 临时设置");
    }

    /**
     * "zh_CN" / "zh-CN" / "en_US" / "en-us" 均可解析；非法值返回 empty 而非抛异常。
     * <p>只做格式解析，不判断是否受支持——白名单过滤由调用方做。</p>
     */
    static Optional<Locale> parse(String raw) {
        if (!StringUtils.hasText(raw)) {
            return Optional.empty();
        }
        String[] parts = raw.trim().replace('-', '_').split("_");
        try {
            Locale locale = switch (parts.length) {
                case 1 -> new Locale(parts[0].toLowerCase(Locale.ROOT));
                case 2 -> new Locale(parts[0].toLowerCase(Locale.ROOT),
                                     parts[1].toUpperCase(Locale.ROOT));
                default -> new Locale(parts[0].toLowerCase(Locale.ROOT),
                                      parts[1].toUpperCase(Locale.ROOT), parts[2]);
            };
            // 语言码必须是合法 ISO 码，否则视为非法输入
            return locale.getLanguage().isEmpty() ? Optional.empty() : Optional.of(locale);
        } catch (Exception e) {
            return Optional.empty();
        }
    }

    /**
     * 解析 Accept-Language 的 q 权重，按权重降序取第一个受支持的语言。
     * <p>直接复用 Spring 的 {@code Locale.LanguageRange} 解析，不自己写 q 值解析器。</p>
     * @return 匹配到的受支持语言；无匹配返回 null
     */
    private Locale matchHeader(String header) {
        if (!StringUtils.hasText(header)) {
            return null;
        }
        try {
            List<Locale.LanguageRange> ranges = Locale.LanguageRange.parse(header);
            for (Locale.LanguageRange range : ranges) {          // parse 已按 q 降序
                Locale candidate = parse(range.getRange()).orElse(null);
                if (candidate == null) {
                    continue;
                }
                // 先精确匹配 zh_CN，再退化为按语言匹配 zh
                for (Locale s : supported) {
                    if (s.equals(candidate)) {
                        return s;
                    }
                }
                for (Locale s : supported) {
                    if (s.getLanguage().equals(candidate.getLanguage())) {
                        return s;
                    }
                }
            }
        } catch (IllegalArgumentException e) {
            // 畸形头（如 "zh_CN;;q=abc"）：忽略，交由调用方退默认
            return null;
        }
        return null;
    }
}
```

两级匹配的必要性：浏览器可能只发 `Accept-Language: en`（无地区），精确匹配 `en_US` 会失败。退化为按语言匹配后 `en` → `en_US`，这是通行做法。反过来 `zh-TW` 在只支持 `zh_CN` 时也会命中 `zh_CN`——这是有意的，繁体用户看简体比看英文合理。

### 2.2.3 I18nProperties

```java
package com.gentry.core.i18n;

@ConfigurationProperties(prefix = "gentry.i18n")
public class I18nProperties {

    /** 总开关。false 时 GentryLocateResolver 不注册，行为回退到 Spring 默认 */
    private boolean enabled = true;

    /** 默认语言，解析失败时的最终兜底 */
    private String defaultLocale = "zh_CN";

    /** 支持语言白名单。加语言必须同步补资源文件，否则会全量走 defaultValue */
    private List<String> supportedLocales = List.of("zh_CN", "en_US");

    // getter / setter 省略
}
```

`enabled = false` 的用途：派生项目若确定单语言交付，关掉这个开关即可去掉语言解析开销，而不必删代码。此时 `I18nUtil` 仍可用（走 Spring 默认的 `AcceptHeaderLocaleResolver`），已有的 `operlog.type.*` 翻译不受影响。

设计要点：

| 要点 | 原因 |
|------|------|
| `supported` 白名单过滤 | 防止用户表里被写入 `xx_YY` 之类未提供语言包的值，导致全站回退到 key |
| `parse()` 非法值返回 `empty` 不抛异常 | 语言解析在请求最外层，抛异常会让整个请求 500，而语言错误应当降级不应中断 |
| 同时接受 `zh_CN` 与 `zh-CN` | 数据库存 Java 风格 `zh_CN`，HTTP 头是 BCP47 风格 `zh-CN`，两种都要认 |
| `setLocale` 直接抛异常 | 明确表态语言不可临时改。留空实现会让人误以为可以 |

### 2.2.4 I18nUtil 扩展

现状只有 `getMessage(key, defaultValue)` 和 `getOperLogTypeLabel(type)`。需要补两个能力：**参数化**与**显式 locale**。

```java
@Component
public class I18nUtil {

    private final MessageSource messageSource;

    /** 隐式 locale（取 LocaleContextHolder），找不到 key 时回退 defaultValue */
    public String getMessage(String key, String defaultValue) { ... }   // 现有，保留

    /** 隐式 locale + 参数化。用于「密码输入错误{0}次」这类模板 */
    public String getMessage(String key, String defaultValue, Object... args) {
        try {
            return messageSource.getMessage(key, args, defaultValue,
                                            LocaleContextHolder.getLocale());
        } catch (Exception e) {
            return defaultValue;
        }
    }

    /**
     * 显式 locale。**无请求上下文的场景必须用这个重载**：
     * 定时通知、异步短信、批量导出给指定收件人。
     * 这类场景 LocaleContextHolder 是空的或属于别的线程，
     * 必须由调用方从收件人的 sys_user.language 取值传入。
     */
    public String getMessage(String key, Locale locale, String defaultValue, Object... args) {
        try {
            return messageSource.getMessage(key, args, defaultValue, locale);
        } catch (Exception e) {
            return defaultValue;
        }
    }

    public String getOperLogTypeLabel(String type) { ... }   // 现有，保留
}
```

> 异步场景若用了 `TraceUtils.wrap(...)`，注意 `TraceUtils` 只传递 MDC，**不传递 `UserContext` 与 `LocaleContextHolder`**。异步任务里必须走显式 locale 重载，不能指望隐式。

### 2.2.5 ErrorCode 加 i18nKey()

枚举常量名本身就是现成的语义 key，机械派生即可，**36 个错误码零命名成本**：

```java
public enum ErrorCode {
    ROLE_NOT_FOUND(20015, "角色不存在"),
    ...

    /**
     * i18n key，由枚举名机械派生：ROLE_NOT_FOUND → error.role.not.found
     * <p>无需在每个枚举项手写 key，改名即改 key（IDE 重命名可同步）。</p>
     */
    public String i18nKey() {
        return "error." + name().toLowerCase(Locale.ROOT).replace('_', '.');
    }
}
```

`message` 字段保留，语义变为**兜底值**：语言包缺失时原样返回中文，界面不会露出裸 key。

对应资源文件（zh 那份由脚本从 `message` 字段生成，保证完整）：

```properties
# i18n/error_zh_CN.properties
error.role.not.found=角色不存在
error.user.not.found=用户不存在
error.tenant.code.exists=租户编码已存在

# i18n/error_en_US.properties
error.role.not.found=Role not found
error.user.not.found=User not found
error.tenant.code.exists=Tenant code already exists
```

### 2.2.6 GlobalExceptionHandler 改造

现状 `BizException` 直接把 `ErrorCode.message`（中文）放进响应，导致 `Accept-Language: en-US` 也返回「角色不存在」。改为经 `I18nUtil`：

```java
@ExceptionHandler(BizException.class)
public R<Void> handleBizException(BizException e) {
    ErrorCode ec = e.getErrorCode();
    String msg = (ec == null)
            ? e.getMessage()
            : i18nUtil.getMessage(ec.i18nKey(), ec.getMessage(), e.getArgs());
    return R.fail(ec == null ? ErrorCode.SYSTEM_ERROR.getCode() : ec.getCode(), msg);
}
```

**兜底链**：`目标语言 → zh_CN → ErrorCode.message`。三层都 miss 才可能露 key，而第三层是编译期常量，所以实际不可能露。

### 2.2.6b BizException 的第二参数：裸文案 → i18n key

实测发现 `BizException` 有**两种用法**，而 §2.2.5 的「枚举名机械派生」只覆盖了第一种：

```
throw new BizException(ErrorCode.ROLE_NOT_FOUND);                      25 处
throw new BizException(ErrorCode.PARAM_ERROR, "系统内置角色不可删除");    47 处 ← 三分之二
```

也就是说三分之二的异常消息是**裸中文字符串**，绝大多数复用 `PARAM_ERROR`，语义全靠那个 String 承载。

**决定：第二个参数的含义从「文案」改为「i18n key」，签名不变。** 47 处只改字符串内容：

```java
// 改造前
throw new BizException(ErrorCode.PARAM_ERROR, "系统内置角色不可删除");
// 改造后
throw new BizException(ErrorCode.PARAM_ERROR, "error.role.builtin.undeletable");
```

不给这 35 条（去重后）各分配一个 `ErrorCode` 的理由：

| 理由 | 依据 |
|------|------|
| 新增 40 个错误码没有消费者 | 实测前端只在 `code === 0` 和 `code === 30003` 上分支，从不按业务码分流 |
| 改动面小到近乎零风险 | 只改字符串内容，不动签名、不动 `code`、不动前端一行 |
| key 命名空间统一 | 这批 key 和 `ErrorCode` 派生的都是 `error.*`，仍是一份 `error_*.properties` |

`20001-20099` 段实测已用 22 个、还剩 77 个位置，容量上另一条路也走得通——不选它纯粹是因为**给每条业务提示编一个全局唯一码是过度设计**。

带动态内容的三处（`"角色不存在: " + missing` 之类）改走 args：

```java
throw new BizException(ErrorCode.ROLE_NOT_FOUND, "error.role.not.found.detail", missing);
// error_en_US.properties → error.role.not.found.detail=Role not found: {0}
```

**代价与必须配套的防线：**

1. handler 多一个分支——`resolveI18nKey()` 里显式 key 优先，否则 `ErrorCode.i18nKey()`
2. **没有编译期保障**，key 拼错只会显示 key 本身。必须配 C-01b 扫描测试：所有
   `BizException(ErrorCode.X, "...")` 的第二参数必须以 `error.` 开头且在中英文资源文件中都存在。
   **没有这个测试就不要采用本方案** —— 漏改一处只在切英文时暴露。

`@RateLimit` / `@RepeatSubmit` 注解上的 `message()` 同步改为「可选 i18n key」：为空时传 `null`，
由 `BizException` 退回 `ErrorCode.i18nKey()`。

### 2.2.7 BizException 增加参数支持

现状 `BizException` 只携带 `ErrorCode`，无法表达「密码输入错误 3 次，账户锁定 15 分钟」这类带参消息——现状代码只能拼字符串，而拼出来的字符串没法翻译。

```java
public class BizException extends RuntimeException {

    private final ErrorCode errorCode;
    private final Object[] args;          // 新增

    public BizException(ErrorCode errorCode) {
        this(errorCode, EMPTY_ARGS);
    }

    /** 带参构造。args 按 MessageFormat 的 {0} {1} 顺序对应 */
    public BizException(ErrorCode errorCode, Object... args) {
        super(errorCode.getMessage());
        this.errorCode = errorCode;
        this.args = (args == null) ? EMPTY_ARGS : args;
    }

    private static final Object[] EMPTY_ARGS = new Object[0];

    public ErrorCode getErrorCode() { return errorCode; }
    public Object[] getArgs() { return args; }
}
```

```properties
# error_zh_CN.properties
error.account.locked=密码输入错误{0}次，账户锁定{1}分钟
# error_en_US.properties
error.account.locked=Wrong password {0} times. Account locked for {1} minutes.
```

```java
throw new BizException(ErrorCode.ACCOUNT_LOCKED, retryCount, lockMinutes);
```

**注意 `MessageFormat` 的单引号陷阱**：`MessageFormat` 把单引号当转义符，译文里要显示一个单引号必须写两个。英文译文很容易踩到，例如 `Role doesn't exist` 中的 `'` 会让后面的 `{0}` 不再被替换。规则：**带参消息的英文译文里，撇号一律写成 `''`**，或改用不含撇号的措辞（`Role does not exist`）。这条要进 §7.2 的完整性测试——检测带 `{n}` 占位的译文中是否存在未成对的单引号。

现有 36 个错误码里 `ACCOUNT_LOCKED(20019, "账号已被锁定，请稍后再试")` 是唯一明显该带参的一条，其余无参。改造保持向后兼容：`new BizException(ErrorCode.X)` 的既有调用点一行都不用改。

### 2.2.8 Bean Validation 消息本地化

131 处校验注解（73 条去重）不需要自己接 `I18nUtil`，Bean Validation 原生支持 `{key}` 占位，只要把 Spring 的 `MessageSource` 接到 Validator 上：

```java
@Configuration
public class I18nConfig {

    @Bean
    public LocalValidatorFactoryBean validator(MessageSource messageSource) {
        LocalValidatorFactoryBean v = new LocalValidatorFactoryBean();
        v.setValidationMessageSource(messageSource);   // 关键一行
        return v;
    }
}
```

DTO 写法从字面量改为 key 引用：

```java
// 改造前
@NotBlank(message = "角色名称不能为空")
@Size(max = 50, message = "角色名称长度不能超过50")
private String name;

// 改造后
@NotBlank(message = "{valid.role.name.notBlank}")
@Size(max = 50, message = "{valid.role.name.size}")
private String name;
```

```properties
# i18n/validation_zh_CN.properties
valid.role.name.notBlank=角色名称不能为空
valid.role.name.size=角色名称长度不能超过50
# i18n/validation_en_US.properties
valid.role.name.notBlank=Role name is required
valid.role.name.size=Role name must not exceed 50 characters
```

key 命名规则 `valid.{领域}.{字段}.{约束}`，由抽词脚本从「类名首个大写词 + 字段名 + 注解名」机械生成。

#### 实测量与两条规则修正

```
带 message 的校验注解 = 120 处（全部含中文），去重文案 64 条，涉及 31 个 DTO
按注解: Size 31 | NotBlank 27 | Min 19 | NotNull 15 | Max 12 | Pattern 10 | Email 6
message 里含花括号的 = 0 条  ← 不会与 BV 属性插值冲突
```

**修正一：不带 `message` 的注解不要碰。** 例如 `@Size(max = 100)`（`ConfigCreateDTO` 里有 4 个），
它走 Hibernate Validator **自带的多语言 `ValidationMessages`**，本来就是国际化的。
把 `MessageSource` 接进 `LocalValidatorFactoryBean` 时要确认没把 HV 的兜底顶掉——
这是接 Validator 最容易踩坏的地方，由 `I18nApiIT` 的对应用例守住（断言英文出现
`size must be between`、中文与英文不同、且都不含裸占位符）。

**修正二：跨领域共用的文案收进 `valid.common.*`。** 「同一文案共用一个 key」天然去重（120 → 64），
但 key 名取自**首次出现**的类，于是 `valid.login.username.notBlank` 会被 `UserCreateDTO` 复用，
读代码的人会困惑。加一遍扫描：被 ≥2 个领域引用的 key 改名到 `valid.common.*`，实测 12 个：

```
valid.common.username.notBlank   ← login, user
valid.common.password.notBlank   ← login, user
valid.common.email.email         ← tenant, user
valid.common.phone.pattern       ← tenant, user
valid.common.remark.size         ← dict, role, tenant, user
valid.common.sort.{min,max,notNull}      valid.common.status.notNull
valid.common.pageNum.min   valid.common.pageSize.{min,max}
```

顺带暴露两处**既有文案不一致**（同义不同话）：`valid.dept.email.email`=「请输入正确的邮箱格式」
vs `valid.common.email.email`=「邮箱格式不正确」；手机号同理。本次按原样迁移不做统一，
以免改动用户可见的中文；要统一属于独立的文案 review。

同时发现 `valid.tenant.maxDevices.min`「最大设备数最小为1」——`sys_tenant.max_devices`
是高精度定位平台的业务字段，RBAC 脚手架的租户不该有「设备数」配额。列为待清理项。

> 注意：`{}` 是 Bean Validation 的占位语法。若消息文本本身要出现花括号，需转义 `\{`。另外 `@Size` 的 `{max}` 这类**约束属性插值**由 Bean Validation 自己完成，与 MessageSource 无关，可以在译文里直接写 `must not exceed {max} characters`。

### 2.2.9 MenuI18nKeyResolver

```java
package com.gentry.core.i18n;

/** 由菜单的既有编码列派生 i18n key。纯计算，不查库、不落库。 */
public final class MenuI18nKeyResolver {

    private MenuI18nKeyResolver() {}

    /**
     * permission 优先，为空时退 path；两者皆空返回 null（→ 前端回退显示 name）。
     *
     * system:user:add  → menu.system.user.add
     * /system          → menu.system
     * /monitor-center  → menu.monitor-center
     */
    public static String resolve(String permission, String path) {
        if (StringUtils.hasText(permission)) {
            return "menu." + permission.trim().replace(':', '.');
        }
        if (StringUtils.hasText(path)) {
            return "menu" + path.trim().replace('/', '.');
        }
        return null;
    }
}
```

实测覆盖率（2026-08-17，`gentry` 库 `sys_menu` 71 条）：

| type | 条数 | 有 permission | 有 path | 两者皆空 | 可派生 |
|------|------|---------------|---------|----------|--------|
| 1 目录 | 3 | 0 | 3 | 0 | 3/3 |
| 2 页面 | 12 | 12 | 12 | 0 | 12/12 |
| 3 按钮 | 56 | 56 | 0 | 0 | 56/56 |

`permission` 无重复，派生 key 无重复。派生样例：

```
menu.system              ← 系统管理（目录）
menu.system.user         ← 用户管理（页面）
menu.system.tenant.list  ← 查询（按钮）
menu.monitor.redis.info  ← Redis 监控
```

### 2.2.12 Excel 导入导出改造（硬约束）

`@ExcelProperty("用户名")` 的值是**注解常量**，运行时无法本地化。现状：

```java
// UserExportVO
@ExcelProperty("用户名") private String username;
// UserImportDTO
@ExcelProperty("用户名") private String username;
```

改造方案：**注解改为按列序绑定，表头运行时构建。**

```java
// UserExportVO —— 只保留列序，不再承载文案
@Data
public class UserExportVO {
    @ExcelProperty(index = 0) private String username;
    @ExcelProperty(index = 1) private String nickname;
    @ExcelProperty(index = 2) private String phone;
    @ExcelProperty(index = 3) private String email;
    @ExcelProperty(index = 4) private String gender;
    @ExcelProperty(index = 5) private String deptName;
    @ExcelProperty(index = 6) private String postName;
    @ExcelProperty(index = 7) private String status;
    @ExcelProperty(index = 8) private String createTime;

    /** 列序与上面字段严格对应，改一处必须改另一处 */
    public static final List<String> HEAD_KEYS = List.of(
        "export.user.username", "export.user.nickname", "export.user.phone",
        "export.user.email",    "export.user.gender",   "export.user.dept",
        "export.user.post",     "export.user.status",   "export.user.createTime");
}
```

```java
// Service 内导出
List<List<String>> head = UserExportVO.HEAD_KEYS.stream()
        .map(k -> List.of(i18nUtil.getMessage(k, k)))
        .toList();

EasyExcel.write(outputStream)
        .head(head)
        .sheet(i18nUtil.getMessage("export.user.sheet", "用户列表"))
        .doWrite(rows);
```

**导入必须同步改成按列序匹配**，这是本方案里最容易漏的一处缺陷：

> 现状 `UserImportDTO` 用 `@ExcelProperty("用户名")` 按**表头文本**匹配列。一旦导出表头被本地化，英文用户导出的 Excel 再导回来，表头是 `Username` 而 DTO 期待「用户名」，**列全部匹配不上，导入静默得到全 null**。

因此 `UserImportDTO` 一律改为 `@ExcelProperty(index = n)` + `.headRowNumber(1)`，让导入完全不依赖表头语言。导入模板下载接口生成的表头则按当前 locale 本地化，与导出一致。

`gender` 字段现状表头是 `性别(0未知1男2女)`，本地化后 key 为 `export.user.gender.hint`，译文 `Gender (0=Unknown,1=Male,2=Female)`。

### 2.2.13 `@Log` 与 `sys_oper_log`：module 已落地，title 仍不做

**决定：`@Log` 的 module 用中文字面量本身当 i18n key（`getMessage(value, value)`），读时写入 `moduleLabel`；title 仍中文直出。** 库表零 DDL。筛选链路必须与 module 翻译同批，见概要设计 §4.8.1。

`@Log` 注解保持原样，不要改成 `log.module.user` 这种 key：

```java

vo.setModuleLabel(i18nUtil.getMessage(entity.getModule(), entity.getModule()));
```

`type` 列继续走既有的 i18n（`operlog.type.INSERT`）。title 本增量不做。

`messages_en_US.properties` 收录 `@Log(module=…)` 的中文 key：

```

...
```

配套改动（必须同批）：`GET /api/v1/logs/operation/modules`、`LIKE`→`=`、前端下拉与列改 `moduleLabel`、E2E/IT。

### 2.2.14 通知与短信：脚手架里没有内置模板

**实测更正：本设计原假设有一批 `notify.*` / `sms.*` 内置模板要翻，实际没有。**

```
NotificationSender.send(Notification) 的唯一调用方 = NotificationController.publish
→ title / content 由管理员在通知发布页手填
→ 属 C 类「用户录入数据」，不翻译
定时任务只有 LogCleanTask（清日志），没有定时通知
```

所以本版本交付的是**能力**而非译文：

| 交付项 | 说明 |
|--------|------|
| `I18nUtil.getMessage(key, locale, default, args...)` | 显式 locale 重载（批次 2 已实现），无请求上下文场景必须用它 |
| `BizException.of(ErrorCode, args...)` | 静态工厂。写成工厂而非构造器 `BizException(ErrorCode, Object...)`，因为后者与 `BizException(ErrorCode, String)` 在传单个字符串时重载歧义 |
| `error.account.locked` 带 `{0}` | 真实存在的一处带参需求：原来抛无参的「账号已被锁定，请稍后再试」，用户看不到还要等几分钟 |

派生项目要发系统通知（如密码过期提醒）时按这个形状写，`notify.*` / `sms.*` 前缀留给它们：

```java
Locale locale = GentryLocaleResolver.parse(recipient.getLanguage())
                                    .orElse(Locale.SIMPLIFIED_CHINESE);
String title = i18nUtil.getMessage("notify.pwd.expiring.title", locale, "密码即将过期");
```

**按收件人分组翻译、落库存译文**（而非 key）：通知是给特定收件人的一次性消息，
收件人语言在发送时已唯一确定，可以定稿；这与 `sys_oper_log` 存 key 的结论相反，
但同出于一条原则——文本的语言由**阅读者**决定，见概要设计 §4.8。

# 三、接口设计

## 3.1 对外接口

### 语言偏好读写

| 操作 | 方法 | URL | 权限 | 说明 |
|------|------|-----|------|------|
| 读取（含在用户信息里） | GET | `/api/v1/users/me` | 登录即可 | `UserInfoVO.language` |
| 更新 | PUT | `/api/v1/users/me/language` | 登录即可 | 只能改自己的 |

```java
@PutMapping("/me/language")
@RepeatSubmit(interval = 1)
@Log(module = "个人中心", type = "UPDATE")   // 本版本 @Log 保持中文字面量
public R<Void> updateMyLanguage(@Valid @RequestBody LanguageUpdateDTO dto) {
    userService.updateLanguage(UserContext.getUserId(), dto.getLanguage());
    return R.ok();
}
```

```java
public class LanguageUpdateDTO {
    /**
     * 只做<b>格式</b>校验，不在注解里写语言白名单。
     * <p>注解常量无法读配置，若在此写 {@code ^(zh_CN|en_US)$}，
     * 加一门语言就得同时改 {@code gentry.i18n.supported-locales} 和这个正则，
     * 漏改一处的表现是「配置里加了语言但接口拒绝保存」。
     * 白名单校验交给 Service 用 {@code I18nProperties} 做，保持单一真源。</p>
     */
    @NotBlank(message = "{valid.user.language.notBlank}")
    @Pattern(regexp = "^[a-zA-Z]{2}(_[a-zA-Z]{2,4})?$", message = "{valid.user.language.pattern}")
    private String language;
}
```

设计取舍：

- **不设 `@SaCheckPermission`**：改自己的语言偏好不需要权限点，任何登录用户都应能改
- **不走 `/api/v1/users/{id}`**：避免管理员误改他人语言，也避免这个高频小接口占用用户更新的权限点
- **`@Pattern` 只校验格式，白名单在 Service 层查 `I18nProperties`**：注解常量读不到配置，把语言清单写进正则会造成「配置与注解两处维护」，漏改一处的表现是配置里加了语言却存不进去。语言白名单的单一真源是 `gentry.i18n.supported-locales`
- 更新成功后**当前请求不改变语言**（`UserContext` 已固定），前端负责本地立即切换

### 语言元数据（可选，供前端渲染语言下拉）

| 操作 | 方法 | URL | 说明 |
|------|------|-----|------|
| 支持语言列表 | GET | `/api/v1/i18n/locales` | 返回 `[{code:'zh_CN',label:'简体中文'},{code:'en_US',label:'English'}]` |

> **必须加进 `SaTokenConfig` 的 `excludePathPatterns`。** 登录页就要渲染语言选择器，
> 而登录校验拦截器覆盖 `/api/**` —— 只写 `@RestController`、不加权限注解**是不够的**，
> 未登录访问会拿到 401 + `code=30001`。实测踩过，已加用例
> `语言列表接口_未登录也可访问` 锁住。

`label` 用各语言的**自称**（简体中文 / English），不随当前 locale 翻译——语言选择器里显示自称是通行做法，否则英文用户看到「中文」反而不认识。

## 3.2 内部接口

### I18nUtil 契约

| 方法 | 何时用 | 注意 |
|------|--------|------|
| `getMessage(key, default)` | 有请求上下文的普通场景 | 最常用 |
| `getMessage(key, default, args...)` | 带参模板 | args 为 `MessageFormat` 参数 |
| `getMessage(key, locale, default, args...)` | **无请求上下文**：定时任务、异步通知、指定收件人导出 | locale 必须由调用方从收件人 `sys_user.language` 取 |

### key 派生契约

| 方法 | 输入 | 输出 | 空值语义 |
|------|------|------|----------|
| `MenuI18nKeyResolver.resolve(permission, path)` | 菜单的两个编码列 | `menu.*` 或 `null` | `null` = 无译文，前端回退 `name` |
| `DictI18nKeyResolver.resolveData(type, value)` | 字典项 | `dict.*` 或 `null` | 同上，回退 `dictLabel` |
| `DictI18nKeyResolver.resolveType(type)` | 字典类型 | `dict.type.*` 或 `null` | 同上，回退 `dictName` |

**契约约束（必须写进 backend-conventions）**：`sys_menu.permission` 与 `sys_dict_data.dict_value` 一旦成为 i18n key 的来源，改动它们会**静默**让译文退化为中文兜底（不报错、不抛异常）。`permission` 本来就与 `@SaCheckPermission` 硬绑不应改动，但这条依赖是隐式的，由 §7.2 的对账测试兜住。

# 四、流程设计

## 4.1 语言解析主流程

```
HTTP 请求
    │
    ├─ TraceIdFilter / RequestLogFilter / RateLimit / RepeatSubmit
    │
    ├─ Sa-Token 认证拦截器
    │      ├─ 未登录（如登录接口、验证码接口）
    │      │     └─ UserContext.LANGUAGE 保持 null
    │      └─ 已登录
    │            └─ 从 Sa-Token Session 取 language
    │                  └─ UserContext.setLanguage("en_US")
    │
    ├─ GentryLocaleResolver.resolveLocale(request)
    │      ├─ ① UserContext.getLanguage() 有值且在白名单 → 用它
    │      ├─ ② Accept-Language 头能匹配到受支持语言  → 用它
    │      └─ ③ 都不行                                 → defaultLocale (zh_CN)
    │            └─ LocaleContextHolder.setLocale(...)
    │
    ├─ Controller
    │      ├─ @Valid 失败
    │      │     └─ LocalValidatorFactoryBean → MessageSource → 本地化提示
    │      │           └─ MethodArgumentNotValidException
    │      │                 └─ GlobalExceptionHandler → R.fail(PARAM_ERROR, 本地化)
    │      └─ Service
    │            ├─ throw BizException(ROLE_NOT_FOUND)
    │            │     └─ GlobalExceptionHandler
    │            │           └─ I18nUtil.getMessage("error.role.not.found",
    │            │                                  "角色不存在")
    │            │                 └─ en_US → "Role not found"
    │            └─ 菜单树组装
    │                  └─ MenuI18nKeyResolver.resolve(...) → MenuTreeVO.i18nKey
    │
    └─ 请求结束
          └─ UserContext.clear()   ← 必须含 LANGUAGE.remove()
```

## 4.2 登录流程中的语言下发

```
POST /api/v1/auth/login
    │
    ├─ 此时 UserContext.LANGUAGE = null
    │   → GentryLocaleResolver 走 ② Accept-Language
    │   → 前端登录页发的是 localStorage 里的语言（或 navigator.language）
    │   → 所以「用户名或密码错误」也能按前端语言返回
    │
    ├─ 认证成功
    │   ├─ 查 sys_user（含 language）
    │   ├─ 写入 Sa-Token Session：userId / tenantId / deptId / platformAdmin / language
    │   └─ 组装 UserInfoVO
    │         ├─ language          = user.getLanguage()
    │         └─ menus[].i18nKey   = MenuI18nKeyResolver.resolve(...)
    │
    └─ 前端收到响应
          ├─ 若 UserInfoVO.language ≠ 当前 i18next 语言
          │     └─ i18next.changeLanguage(language) + 同步 localStorage
          └─ 用 menus 渲染侧边栏：label = t(i18nKey) ?? name
```

**为什么 `UserInfoVO` 要带 `language`**：登录页可能用的是浏览器默认语言，而用户偏好是另一种。不带这个字段，前端只能先按浏览器语言渲染再纠正，界面会闪。带上就能在跳转到首页之前切好。

## 4.3 无请求上下文场景（定时通知）

```
定时任务线程（无 HttpServletRequest，LocaleContextHolder 为空）
    │
    ├─ 查出待通知的收件人列表（含各自的 sys_user.language）
    │
    └─ 按收件人分组
          └─ for each 收件人
                ├─ Locale locale = parse(user.getLanguage())
                └─ String title = i18nUtil.getMessage(
                       "notify.password.expiring.title", locale, "密码即将过期", days);
```

关键：**必须走显式 locale 重载**。`TraceUtils.wrap(...)` 只传递 MDC，不传递 `UserContext` 与 `LocaleContextHolder`，异步线程里隐式取 locale 只会拿到默认值。

## 4.4 Excel 导出流程

```
GET /api/v1/users/export
    │
    ├─ locale 已由 GentryLocaleResolver 解析完成
    ├─ 查数据 → List<UserExportVO>（字段按 index 绑定，无文案）
    ├─ 构建表头：HEAD_KEYS.map(k -> i18nUtil.getMessage(k, k))
    ├─ sheet 名：i18nUtil.getMessage("export.user.sheet", "用户列表")
    ├─ 单元格枚举值：gender / status 走 dict key 或 i18n key 翻译后写入
    └─ EasyExcel.write(out).head(head).sheet(sheetName).doWrite(rows)

POST /api/v1/users/import
    │
    ├─ @ExcelProperty(index = n) 按列序匹配 —— 与表头语言无关
    ├─ .headRowNumber(1) 跳过表头行
    └─ 因此中英文任意语言导出的文件都能导回来
```

## 4.5 异常与降级

| 异常场景 | 行为 | 依据 |
|----------|------|------|
| `sys_user.language` 是非法值（如 `xx_YY`） | 白名单过滤掉 → 退 Accept-Language → 退 zh_CN | 语言错误不应中断请求 |
| 语言包缺 key | 返回 `defaultValue`（ErrorCode.message / 原始 name） | 界面绝不露裸 key |
| 资源文件整体缺失 | `I18nUtil` catch 住，全量走 defaultValue | 等价于退化成现状行为 |
| `Accept-Language` 头畸形 | `matchHeader` 返回 null → 退默认 | 不抛异常 |
| 派生 key 为 null（`permission` 与 `path` 皆空） | VO 的 `i18nKey` 为 null，前端回退 `name` | 概要设计 §4.3 |
| 线程池复用未清理 LANGUAGE | **这是缺陷不是降级**，由 `clear()` + 单测防住 | 见 §7.1 |

# 五、数据设计

## 5.1 配置项

```yaml
spring:
  messages:
    basename: i18n/messages,i18n/error,i18n/validation,i18n/export
    encoding: UTF-8
    fallback-to-system-locale: false
    cache-duration: 3600s

gentry:
  i18n:
    enabled: true
    default-locale: zh_CN
    supported-locales: zh_CN,en_US
```

| 配置 | 默认 | 说明 |
|------|------|------|
| `spring.messages.basename` | 见上 | 拆多个 basename，按用途分文件，避免单文件几百行 |
| `spring.messages.fallback-to-system-locale` | **必须 false** | 为 true 时找不到 key 会退到服务器系统语言，行为随部署环境漂移 |
| `spring.messages.cache-duration` | 3600s | 生产可设 -1（永久缓存）；开发期设短便于改文案即时生效 |
| `gentry.i18n.supported-locales` | `zh_CN,en_US` | 白名单，加语言时同步加资源文件 |

## 5.2 资源文件布局

```
gentry-core/src/main/resources/i18n/
├── messages.properties          ← 默认（= zh_CN 内容），必须存在
├── messages_zh_CN.properties
├── messages_en_US.properties
├── error.properties             ← 36 个 ErrorCode
├── error_zh_CN.properties
├── error_en_US.properties
├── validation.properties        ← 73 条校验消息
├── validation_zh_CN.properties
├── validation_en_US.properties
├── export.properties            ← 55 条导出表头与枚举（含枚举提示）
├── export_zh_CN.properties
└── export_en_US.properties
```

**不含 `menu` 与 `dict`**——那 92 个 key 的译文归前端（概要设计 §4.4）。

无后缀的 `xxx.properties` 必须存在且内容等于 zh_CN，用于 `fallback-to-system-locale: false` 下的最终兜底。

现状 `messages*.properties` 只有 7 个 `operlog.type.*` key，保留不动，仅新增其余文件。

## 5.3 缓存设计

| 对象 | 缓存方式 | TTL | 说明 |
|------|----------|-----|------|
| 资源包内容 | Spring `ResourceBundleMessageSource` 内置 | `cache-duration` | 无需自建缓存 |
| 派生的 i18n key | **不缓存** | — | 纯字符串运算（一次 `replace`），比查缓存还快 |
| 用户语言偏好 | Sa-Token Session（Redis） | 随 Token | 与 tenantId 同一份 Session，不额外增加 Redis Key |

**不新增任何 Redis Key**，因此无需登记到 `RedisKeyDefines`。

## 5.4 数据库变更

```sql
-- backend/gentry-start/src/main/resources/db/migration/common/V12__add_user_language.sql
-- 用户语言偏好。三态：NULL = 未设置（跟随浏览器 Accept-Language），
-- 'zh_CN' / 'en_US' = 用户显式选择过。
-- 必须可空：若 NOT NULL DEFAULT 'zh_CN'，三级解析链的第 ② 级（请求头）
-- 对已登录用户永远不会执行，英文浏览器用户一登录就被强制切回中文。
-- 可空列的 ADD COLUMN 三库均支持，故放 common/。
ALTER TABLE sys_user ADD COLUMN language VARCHAR(20) NULL;
```

| 项 | 说明 |
|----|------|
| 版本号 | `V12`（当前 `common/` 最大为 `V11__create_notification.sql`） |
| 目录 | `common/`——三库通用 |
| 可空性 | **NULL**（= 未设置偏好）。存量用户全部为 NULL，即跟随浏览器，无需 UPDATE |
| 长度 | `VARCHAR(20)` 足够容纳 `zh_Hant_TW` 之类 |
| 索引 | 不建。语言不作查询条件 |
| `sys_menu` / `sys_dict_data` | **零改动** |

三库兼容性说明：MySQL 8、PostgreSQL 14+、SQLite 3.35+ 均支持 `ALTER TABLE ... ADD COLUMN <col> <type> NULL`。选可空还额外绕过了 SQLite 对 `ADD COLUMN NOT NULL` 必须带常量默认值的限制。

## 5.5 key 命名规则总表

所有 key 必须可**机械派生**或**按固定模板拼写**，不允许自由命名——这是抽词脚本能自动化、对账测试能校验的前提。

| 前缀 | 归属 | 规则 | 派生自 | 示例 |
|------|------|------|--------|------|
| `error.*` | 后端 | `error.` + 枚举名小写、`_`→`.` | `ErrorCode` 枚举名 | `ROLE_NOT_FOUND` → `error.role.not.found` |
| `valid.*` | 后端 | `valid.{实体}.{字段}.{约束}` | 类名 + 字段名 + 注解名 | `RoleCreateDTO.name` + `@NotBlank` → `valid.role.name.notBlank` |
| 中文原文（`用户管理` 等 `@Log` module） | 后端 + 前端 | 字面量本身当 key，`getMessage(value, value)`；前端下拉 `t(key, {defaultValue: key})` | `@Log(module=…)` | `用户管理` → User Management |
| `operlog.type.*` | 后端 | `operlog.type.{类型码}` | `type` 列的值 | `operlog.type.INSERT`（**现存，勿改**） |
| `export.*` | 后端 | `export.{实体}.{列}` | `HEAD_KEYS` 常量 | `export.user.username` |
| `notify.*` / `sms.*` | 后端 | `notify.{场景}.{title\|content}` | 人工 | `notify.pwd.expiring.title` |
| `menu.*` | **前端** | `menu.` + permission 的 `:`→`.`；permission 空则 `menu` + path 的 `/`→`.` | `sys_menu.permission` / `path` | `menu.system.user.add` |
| `dict.*` | **前端** | `dict.{dict_type}.{dict_value}`、`dict.type.{dict_type}` | `sys_dict_data` / `sys_dict_type` | `dict.sys_user_gender.1` |

**前缀即归属**：`menu.*` 与 `dict.*` 的译文只存在于前端语言包，后端 `spring.messages.basename` 里没有这两个文件；其余前缀只存在于后端。这条不变式让「译文该去哪找」无需查表，也让 §7.2 的对账测试能按前缀切分校验范围。

唯一的例外是导出表头与前端表格表头这 ~30 条语义重复（`export.user.username` ↔ 前端 `user:table.username`），**key 不同、译文相同**，由 C-05 测试保证一致。

### 7.3.1 集成测试的两个基础设施坑（实测踩过）

**一、`MockMvc` 读响应默认按 ISO-8859-1，中文会变乱码。**

Spring 的 JSON 转换器按规范不在 `Content-Type` 里写 charset，而 `MockHttpServletResponse.getContentAsString()`
在没有 charset 时退回 ISO-8859-1 —— 断言中文会看到 `è§è²ä¸å­å¨` 这种输出。既有 12 个 `*ApiIT`
从没断言过中文文案，所以这个坑一直藏着。修法是在 `BaseApiIT.parse()` 里显式指定：

```java
result.getResponse().getContentAsString(StandardCharsets.UTF_8)
```

**二、`JdbcTemplate` 与 MyBatis 不在同一条连接上，测试里改库会死锁。**

`JdbcTemplate` 注入的是原始 `DataSource`，而 MyBatis-Flex 用 `FlexDataSource` 包装后才绑定
`@Transactional`。于是测试里用 `JdbcTemplate` 写库会**自成一个事务**，去撞测试事务持有的行锁，
报 `Lock wait timeout exceeded` 并白等 50 秒（实测两个用例把整类耗时从 12 秒拖到 116 秒）。

规范：**集成测试里改库一律走 Mapper，不用 `JdbcTemplate`**。另外更新条件要用主键——
`WHERE username = ?` 用不上 `uk_user_tenant_username`（最左列是 `tenant_id`），会全表扫描并锁住每一行。

I-01 与 I-10 是**回归现状缺陷**的两个用例：现状实测 `DELETE /api/v1/roles/999999999` 中英文都返回「角色不存在」。

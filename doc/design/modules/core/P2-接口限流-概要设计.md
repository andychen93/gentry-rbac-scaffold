# 一、设计目标（What & Why）

## 是什么（What）

接口限流是基于令牌桶算法的请求频率控制机制。通过自定义 `@RateLimit` 注解和 AOP 切面，在方法执行前检查请求频率，超过阈值的请求直接拒绝并返回错误提示，防止接口被恶意刷量或意外过载。

核心职责：

1. **频率控制**：限制单位时间内的请求次数，支持按 IP 或用户ID 两种维度
2. **令牌桶算法**：使用令牌桶算法实现平滑限流，允许短暂的突发流量
3. **注解驱动**：通过 `@RateLimit` 注解标记需要限流的接口，灵活配置限流参数
4. **本地缓存**：使用 Caffeine 存储令牌桶计数器，无需引入 Redis
5. **友好提示**：被限流的请求返回明确的错误码和提示信息，告知客户端何时可重试

## 为什么（Why）

1. **系统保护**：防止恶意用户或爬虫高频调用接口，消耗服务器资源。车联网平台的登录接口、验证码接口、设备查询接口都是高频攻击目标
2. **资源公平**：多租户环境下，防止某个租户过度使用资源影响其他租户
3. **成本控制**：涉及第三方 API 调用（如地图服务、短信服务）的接口需要控制调用频率，避免产生额外费用
4. **架构原则**："单机优先"原则下，使用 Caffeine 本地缓存实现限流，不引入 Redis 等外部依赖
5. **运维友好**：被限流时返回明确的 `429` 状态语义（通过 BizException + ErrorCode 表达），前端可据此展示提示并引导用户稍后重试

# 二、定位与上下文（Where & When）

## 在哪里（Where）

位于 `gentry-core` 模块的 `com.gentry.core.web` 包中，通过 AOP 切面在 Controller 方法执行前拦截。

在请求处理链路中的位置：

```
HTTP Request
  → TraceIdFilter
  → RequestLogFilter
  → Sa-Token Filter（认证）
  → DispatcherServlet
  → [RateLimitAspect]        ← 限流检查
    → 通过 → Controller → Service
    → 拒绝 → 抛出 BizException(RATE_LIMIT)
```

依赖关系：

- **被依赖方**：需要限流保护的 Controller 方法（登录、验证码、数据导出等）
- **依赖方**：
  - Spring AOP（`@Around` 切面）
  - Caffeine Cache（存储限流计数器）
  - `@RateLimit` 注解
  - `GlobalExceptionHandler`（捕获 `BizException` 并返回统一错误响应）
  - `UserContext`（获取用户ID）

## 在何时（When）

触发场景：

| 场景 | 限流维度 | 阈值 | 说明 |
|------|----------|------|------|
| 登录接口 | IP | 5次/分钟 | 防止暴力破解 |
| 验证码接口 | IP | 10次/分钟 | 防止短信轰炸 |
| 数据导出 | userId | 3次/分钟 | 导出消耗资源 |
| 全局默认 | userId | 100次/分钟 | 防止单用户过度请求 |
| 设备查询 | IP | 60次/分钟 | 防止爬虫 |

# 四、实现思路（How）

## 核心技术方案

### 4.1 @RateLimit 注解设计

```java
/**
 * 接口限流注解
 * 标注在 Controller 方法上，启用请求频率限制
 */
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
@Documented
public @interface RateLimit {

    /**
     * 限流维度
     * "ip" - 按客户端IP限流
     * "userId" - 按登录用户ID限流
     */
    String key() default "userId";

    /**
     * 时间窗口内允许的最大请求数
     */
    int count() default 100;

    /**
     * 时间窗口（秒）
     */
    int period() default 60;

    /**
     * 限流提示信息（可选，默认使用 ErrorCode.RATE_LIMIT.message）
     */
    String message() default "";
}
```

### 4.2 RateLimitAspect 切面实现

```java
@Aspect
@Component
@Slf4j
public class RateLimitAspect {

    // 令牌桶缓存：Key = 限流键（如 "ip:192.168.1.1" 或 "userId:42"）
    // Value = AtomicInteger 计数器
    private final Cache<String, AtomicInteger> rateLimitCache = Caffeine.newBuilder()
        .maximumSize(10000)
        .expireAfterWrite(60, TimeUnit.SECONDS)  // 最大时间窗口
        .build();

    @Around("@annotation(rateLimit)")
    public Object around(ProceedingJoinPoint point, RateLimit rateLimit) {
        // 1. 构建限流 Key
        String limitKey = buildKey(rateLimit);

        // 2. 获取或创建计数器
        AtomicInteger counter = rateLimitCache.get(limitKey, k -> new AtomicInteger(0));

        // 3. 原子递增并判断
        int current = counter.incrementAndGet();
        if (current > rateLimit.count()) {
            log.warn("接口限流触发 - key={}, current={}, limit={}",
                limitKey, current, rateLimit.count());
            throw new BizException(ErrorCode.RATE_LIMIT);
        }

        // 4. 通过限流，执行目标方法
        return point.proceed();
    }
}
```

### 4.3 限流 Key 构建规则

| key 参数 | Key 格式 | 示例 | 说明 |
|----------|----------|------|------|
| `ip` | `rate_limit:ip:{ip}:{method}` | `rate_limit:ip:192.168.1.1:login` | 按IP + 方法隔离 |
| `userId` | `rate_limit:userId:{userId}:{method}` | `rate_limit:userId:42:export` | 按用户 + 方法隔离 |

方法标识使用 `类名.方法名` 格式，确保不同方法独立计数。

### 4.4 令牌桶算法简化实现

本设计采用**固定窗口计数器**（简化版令牌桶），足够满足大部分场景：

- 每个限流 Key 维护一个 `AtomicInteger` 计数器
- 计数器通过 Caffeine 的 TTL 机制自动过期（TTL = period 秒）
- 请求到来时计数器 +1，超过 count 则拒绝
- TTL 到期后计数器自动清除，窗口重置

**与标准令牌桶的区别：**

| 特性 | 标准令牌桶 | 简化计数器 |
|------|-----------|------------|
| 突发流量 | 允许一定突发 | 窗口内均匀分布 |
| 实现复杂度 | 高 | 低 |
| 适用场景 | API 网关 | 单机应用 |
| 本项目选择 | - | 是 |

对于单机优先的车联网平台，简化计数器方案已足够。

### 4.5 与全局异常处理的配合

当限流触发时：

```java
throw new BizException(ErrorCode.RATE_LIMIT);
// ErrorCode.RATE_LIMIT = (40001, "请求过于频繁，请稍后重试")
```

`GlobalExceptionHandler` 捕获后返回：

```json
{
  "code": 40001,
  "message": "请求过于频繁，请稍后重试",
  "traceId": "abc123",
  "timestamp": 1712908800000
}
```

### 4.6 使用示例

```java
@RestController
@RequestMapping("/auth")
public class AuthController {

    @PostMapping("/login")
    @RateLimit(key = "ip", count = 5, period = 60)
    public R<LoginVO> login(@RequestBody LoginDTO dto) {
        // 登录逻辑
    }

    @PostMapping("/captcha")
    @RateLimit(key = "ip", count = 10, period = 60)
    public R<String> captcha() {
        // 验证码逻辑
    }
}

@RestController
@RequestMapping("/api/v1/vehicles")
public class VehicleController {

    @GetMapping("/export")
    @RateLimit(key = "userId", count = 3, period = 60)
    public void export(HttpServletResponse response) {
        // 导出逻辑
    }
}
```

# 五、预期效果与验收标准

## 性能指标

| 指标 | 目标值 | 说明 |
|------|--------|------|
| 限流检查耗时 | < 1ms | Caffeine 内存操作 |
| 内存占用 | < 10MB | 10000 个计数器约 10MB |
| 并发安全 | AtomicInteger 保证 | 原子操作，无线程安全问题 |

## 功能验收标准

| 编号 | 验收项 | 验证方式 |
|------|--------|----------|
| R-001 | 按 IP 限流生效 | 同一IP快速请求6次登录接口，第6次被拒绝 |
| R-002 | 按用户ID限流生效 | 同一用户快速请求4次导出接口，第4次被拒绝 |
| R-003 | 不同IP独立计数 | 两个不同IP各自请求5次登录接口，均正常 |
| R-004 | 不同用户独立计数 | 两个不同用户各自请求3次导出，均正常 |
| R-005 | 时间窗口到期后重置 | 被限流后等待60秒，再次请求恢复正常 |
| R-006 | 限流返回标准错误码 | 验证响应 code = 40001 |
| R-007 | 限流响应包含 traceId | 验证限流响应包含 traceId |
| R-008 | 无注解接口不限流 | 未标注 @RateLimit 的接口不限流 |
| R-009 | 限流事件被记录到日志 | 查看日志，确认限流事件被记录为 WARN |

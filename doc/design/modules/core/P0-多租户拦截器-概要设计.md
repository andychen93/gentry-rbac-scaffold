# 一、设计目标（What & Why）

## 是什么（What）

多租户拦截器是平台数据隔离的核心机制。基于 MyBatis-Flex 的 `TenantFactory` 体系，通过 SQL 拦截实现自动化的租户数据隔离——在 SELECT 语句自动追加 `WHERE tenant_id = ?` 条件，在 INSERT 语句自动填充 `tenant_id` 字段，在 UPDATE/DELETE 语句自动追加 `WHERE tenant_id = ?` 条件，确保租户之间数据完全隔离，业务代码无需手动处理租户过滤。

核心职责：

1. **查询隔离**：SELECT 自动追加 `tenant_id` 条件，防止跨租户数据泄露
2. **写入隔离**：INSERT 自动填充 `tenant_id` 字段，开发无需手动设置
3. **更新隔离**：UPDATE/DELETE 自动追加 `tenant_id` 条件，防止误操作跨租户数据
4. **白名单机制**：通过 `@IgnoreTenant` 注解或配置忽略表，使特定场景（如登录、租户管理）绕过租户过滤
5. **上下文传递**：从 `UserContext`（ThreadLocal）获取当前用户租户ID，传递给 SQL 拦截器

## 为什么（Why）

1. **数据安全**：多租户 SaaS 平台最基本的要求是租户间数据隔离。缺少拦截器意味着任何一条漏了 `WHERE tenant_id = ?` 的查询都可能导致租户 A 看到租户 B 的数据，造成严重的数据泄露
2. **开发效率**：如果每条 SQL 都要手动加 `tenant_id` 条件，开发成本高且容易遗漏。拦截器实现"一次配置，全局生效"
3. **代码简洁**：业务 Service 层代码无需关心租户隔离逻辑，保持业务逻辑的纯净
4. **审计合规**：集中式的租户隔离比分散在各处的手动过滤更容易审计和验证
5. **架构原则**：CLAUDE.md 明确要求"全局强制 tenant_id"和"租户隔离"

# 二、定位与上下文（Where & When）

## 在哪里（Where）

位于 `gentry-core` 模块的 `com.gentry.core.tenant` 包中，作为 MyBatis-Flex 的 SQL 执行拦截器，在 Mapper 层与数据库之间生效。

在系统架构中的位置：

```
Controller → Service → Mapper → [GentryTenantManager] → SQL 执行 → Database
                                  ↑
                            自动追加 tenant_id
```

依赖关系：

- **被依赖方**：所有包含数据库读写的业务模块均依赖此拦截器进行租户隔离
- **依赖方**：
  - MyBatis-Flex `TenantFactory`（框架提供的租户管理接口）
  - `UserContext`（`com.gentry.core.security.UserContext`）—— 获取当前租户ID
  - `@IgnoreTenant` 注解（自定义注解）—— 标记忽略租户过滤的方法或类

## 在何时（When）

触发场景：

| 触发场景 | SQL 类型 | 拦截行为 |
|----------|----------|----------|
| 查询业务数据 | SELECT | 自动追加 `WHERE tenant_id = ?` |
| 新增业务数据 | INSERT | 自动填充 `tenant_id` 字段 |
| 更新业务数据 | UPDATE | 自动追加 `WHERE tenant_id = ?` |
| 删除业务数据 | DELETE | 自动追加 `WHERE tenant_id = ?` |
| 登录认证 | SELECT | **不拦截**（登录时尚无租户上下文） |
| 租户管理 | SELECT/INSERT/UPDATE/DELETE | **不拦截**（系统级操作，跨租户） |
| 系统表查询 | SELECT | **不拦截**（如 sys_menu、sys_dict 等公共数据） |

# 三、主要用户与交互方（Who）

## 面向谁（Who）

| 角色 | 关注点 |
|------|--------|
| **后端开发** | 正常编写 SQL/Mapper，无需关心租户隔离；特殊场景使用 `@IgnoreTenant` |
| **系统管理员** | 租户管理接口跨租户操作，依赖 `@IgnoreTenant` 注解 |
| **安全审计** | 验证所有 SQL 均经过租户过滤，无遗漏 |
| **DBA** | 确认 SQL 执行计划合理，tenant_id 条件走索引 |

## 与其他组件的交互

| 交互组件 | 交互方式 | 说明 |
|----------|----------|------|
| `UserContext` | 读取 tenantId | 从 ThreadLocal 获取当前用户的租户ID |
| `TenantFactory`（MyBatis-Flex） | 实现/注册 | MyBatis-Flex 的租户管理扩展点 |
| `@IgnoreTenant` | 注解标记 | 方法或类级别标记，跳过租户过滤 |
| `GlobalExceptionHandler` | 异常捕获 | 当 tenantId 为空时抛出异常，由全局异常处理捕获 |
| 数据库索引 | 依赖 | `tenant_id` 字段需有索引保障查询性能 |

# 四、实现思路（How）

## 核心技术方案

基于 MyBatis-Flex 1.11.6 的 `TenantManager` 机制实现。

### 4.1 GentryTenantManager 实现

MyBatis-Flex 提供了 `TenantManager` 接口用于租户隔离，核心实现思路：

1. **注册 TenantFactory**：通过 `TenantManager.setTenantFactory()` 注册租户ID获取逻辑
2. **配置忽略表**：实现 `ignoreTables()` 方法返回不需要租户过滤的表名集合
3. **自定义忽略注解**：通过 `@IgnoreTenant` 注解 + AOP 切面判断当前操作是否需要忽略租户过滤

### 4.2 租户ID获取链路

```
请求进入
  → Sa-Token 拦截器解析 Token
  → StpUtil.getLoginIdAsString()
  → 查询用户信息（含 tenantId）
  → UserContext.setTenantId(tenantId)  ← 写入 ThreadLocal
  → Controller → Service → Mapper
  → GentryTenantManager.getTenantId()    ← 从 ThreadLocal 读取
  → 自动追加 SQL 条件
```

### 4.3 @IgnoreTenant 注解设计

```java
/**
 * 标记方法或类跳过多租户拦截
 * 适用于：登录认证、租户管理、系统级操作
 */
@Target({ElementType.METHOD, ElementType.TYPE})
@Retention(RetentionPolicy.RUNTIME)
@Documented
public @interface IgnoreTenant {
    /**
     * 忽略租户过滤的原因说明（仅用于文档目的）
     */
    String value() default "";
}
```

### 4.4 忽略表配置

以下表不需要（也不应该）追加租户过滤条件：

| 表名 | 原因 |
|------|------|
| `sys_tenant` | 租户表本身是系统级数据，跨租户访问 |
| `sys_menu` | 菜单是系统级公共数据，不按租户区分 |
| `sys_role_menu` | 角色-菜单关联表，通过角色间接隔离 |
| `sys_dict_type` | 字典类型是系统级公共数据 |
| `sys_dict_data` | 字典数据是系统级公共数据 |

业务表（`biz_*` 前缀）全部纳入租户隔离。

### 4.5 异常场景处理

| 场景 | 处理方式 |
|------|----------|
| 未登录（UserContext 无 tenantId） | 降级为默认租户 `TenantConstants.DEFAULT_TENANT_ID`（不抛异常，兼容定时任务等非请求线程） |
| 租户已过期 | 在 `UserContext` 设置时校验，过期则拒绝 |
| 租户被禁用 | 在 `UserContext` 设置时校验，禁用则拒绝 |
| 系统级操作 | 标记 `@IgnoreTenant`，跳过租户过滤 |

# 五、预期效果与验收标准

## 性能指标

| 指标 | 目标值 | 说明 |
|------|--------|------|
| SQL 拦截耗时 | < 1ms | 仅追加条件，无额外 IO |
| ThreadLocal 读写 | < 0.01ms | 内存操作，可忽略 |
| 索引命中率 | 100% | `tenant_id` 字段必须在所有业务表上有索引 |

## 功能验收标准

| 编号 | 验收项 | 验证方式 |
|------|--------|----------|
| T-001 | SELECT 自动追加 tenant_id 条件 | 查看SQL日志，确认 WHERE 子句包含 tenant_id |
| T-002 | INSERT 自动填充 tenant_id | 新增数据后查询，确认 tenant_id 正确 |
| T-003 | UPDATE 自动追加 tenant_id 条件 | 更新数据后确认不影响其他租户数据 |
| T-004 | DELETE 自动追加 tenant_id 条件 | 删除数据后确认不影响其他租户数据 |
| T-005 | @IgnoreTenant 跳过租户过滤 | 租户管理接口正常查询所有租户数据 |
| T-006 | 忽略表不被拦截 | 查询 sys_menu 无 tenant_id 条件 |
| T-007 | 未登录时查询业务表使用默认租户 | 无 Token 访问业务接口，使用 DEFAULT_TENANT_ID |
| T-008 | 租户A看不到租户B的数据 | 用租户A的Token查询，验证无租户B数据 |
| T-009 | 租户隔离不影响SQL性能 | 对比有/无 tenant_id 条件的执行计划，确认走索引 |

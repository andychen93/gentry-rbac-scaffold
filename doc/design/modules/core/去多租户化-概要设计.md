## 一、动机（Why）

### 1.1 多租户在这个仓库里解决的是一个不存在的问题

多租户（`tenant_id` 行级隔离）解决的场景是：**一次部署、一份数据库，同时服务多个互不信任的客户组织**。

但本仓库（`AGENTS.md` 第三章「新项目接入」）的消费方式是**引依赖**：每个消费方都是
`mvn install` 到自己的仓库、自己起服务、自己连自己的数据库。也就是说，**任何一个具体部署里，
都不存在"租户 A 和租户 B 共享同一个数据库"的场景**。行级隔离防的是一个在这个部署模型下
根本不会发生的风险，却要为它背下面第 1.2 节列的全部成本。

隔离粒度（数据库内一行）与实际部署粒度（整个数据库）不匹配，细粒度的那层是纯负债。

### 1.2 已经实际发生的成本

- 上一轮修的越权漏洞（`平台级权限隔离/详细设计.md`）——"租户管理员能不能跨租户""哪些
  权限点该标 `is_platform`"——这整套问题只因为存在多租户才存在。单组织系统里不存在
  "谁的权限该被谁挡住"这个维度。
- `is_platform` 判断不是修一次就完的：每加一个新功能（这次是菜单管理）都要人工过一遍
  "这个权限点该不该收成平台级"，忘一次就是一个洞。
- `GentryTenantManager.getIgnoreTables()` 是死代码——没有生产代码调用它，真正生效的是
  "实体继承 `BaseEntity` 还是 `TenantEntity`"。文档说的三层跳过机制与代码实际路径不一致，
  这类分裂本身就是多租户系统的常见坑。
- 每个新 Mapper 要想"会不会漏 `tenant_id`"，每个定时任务要想"要不要 `@IgnoreTenant`"，
  这些心智负担在单组织系统里不存在。
- 测试成本翻倍：建租户的 helper（`createTenant()`、`superAuth()`、租户级 token）、
  `PlatformPermissionIsolationApiIT` 整个类、`UserManagementIntegrationTest` 里几乎
  每条 SQL 带的 `tenant_id` 条件。

### 1.3 判断标准回顾

问过的问题是："未来会不会有一次部署、一个数据库、同时服务多个互不信任客户组织的场景？"
——结论是不会：本仓库的定位是给独立部署的项目引依赖用的脚手架，RBAC 本身（角色、菜单
权限点、部门数据权限五档）已经能覆盖"一个组织内部多业务单元"的隔离需求，不需要
`tenant_id` 这层。

### 1.4 现在做比以后做便宜

这还是个脚手架，没有真实客户数据在生产跑。retrofit 多租户到已上线系统是出了名的痛
（迁移数据、审计所有查询路径）；反过来现在拿掉，只是删掉一个维度，风险小得多。

## 二、范围（What）

### 2.1 要删除的机制（按层）

| 层 | 删除对象 |
|----|---------|
| 数据库 | `sys_tenant` 表；8 张业务表的 `tenant_id` 列（`sys_user`/`sys_role`/`sys_user_role`/`sys_dept`/`sys_dict_type`/`sys_dict_data`/`sys_notification`/`sys_email_token`）；`sys_oper_log`/`sys_login_log` 的 `tenant_id` 列；`sys_menu.is_platform` 列 |
| core | `GentryTenantManager`、`IgnoreTenant`/`IgnoreTenantAspect`、`TenantConstants`；`UserContext` 的 `tenantId`/`platformAdmin` 字段；`AutoFillHandler` 的 tenantId 兜底；`MybatisFlexConfig` 的 `TenantManager.setTenantFactory` 注册；`SaTokenConfig` 里 tenantId/platformAdmin 的 session 恢复 |
| rbac-starter | `com.gentry.rbac.tenant` 整包（controller/service/mapper/entity/dto/vo）；`Menu.isPlatform` 及相关 Mapper 方法；`RoleServiceImpl.assignMenus` 的平台级校验；`ErrorCode.PLATFORM_MENU_FORBIDDEN`；`LoginDTO.tenantCode`；`AuthServiceImpl` 的 `resolveTenantId`/`platformAdmin` 判定；`UserInfoVO.platformAdmin` |
| 前端 | `pages/tenant/` 整个目录；`services/tenantApi.ts`；登录页租户 Tab；`PermissionPage` 的 `isPlatform` 过滤；`userStore` 的 `platformAdmin`；`locales/*/tenant.json` |
| 测试 | `GentryTenantManagerTest`、`TenantApiIT`、`PlatformPermissionIsolationApiIT`、E2E 的 `08-tenant-management.spec.ts`/`15-platform-permission-isolation.spec.ts`；`UserManagementIntegrationTest` 里租户隔离相关用例 |

### 2.2 明确保留、不受影响

- `@DataScope` 五档数据权限机制（全部/本部门及子部门/本部门/仅本人/自定义）——已确认
  只依赖 `deptId`/`userId`，`UserDataScopeResolver`/`DeptChildrenProvider` 接口里的
  `tenantId` 参数是死参数，顺手一并简化但不改行为。
- `gentry-monitor-spring-boot-starter`——与租户机制无耦合，不涉及。
- `sys_config`（全局参数配置表）——本来就不带 `tenant_id`，不受影响。
- Sa-Token JWT + Redis Session、Token 黑名单——去掉的只是 session 里的
  `tenantId`/`platformAdmin` 两个字段，认证机制本身不变。

## 三、关键决策

### 3.1 角色体系：SUPER_ADMIN 与 ADMIN 合并为单一管理员角色

现状 `SUPER_ADMIN`（平台超管，70 个菜单）与 `ADMIN`（租户管理员，57 个菜单，V15 后）
的区分理由是"谁能跨租户管理租户本身"。这个理由消失后，两个角色没有存在的必要——
系统里只应该有一种"最高权限"。

**决策：合并成一个角色，沿用 `ADMIN` 这个编码**（不沿用 `SUPER_ADMIN`，因为
"超级"这个修饰词描述的正是"高于其他租户"这件事，去掉多租户后语义不再准确）。
合并后的 `ADMIN` 拥有全部菜单（原 70 个减去被删除的租户管理 6 个按钮 + 1 个目录，
再减去菜单管理相关的平台级标记——即恢复到"全部现存菜单"）。

被否决的备选：**删除 `SUPER_ADMIN` 角色连带删除 `chenli` 账号**。否决理由是这个改动
的目标是"删除多租户机制"，不是"删除某个账号"；账号删除是更大的破坏性操作，且会牵连
所有引用 `chenli` 登录的既有测试（不只是租户相关的那些），改动面无必要扩大。

**决策：`chenli` 账号保留，角色关联从 `SUPER_ADMIN` 改为合并后的 `ADMIN`。**
`chenli`/`admin`/`zhangsan` 三个种子账号权限从此完全相同，密码不变。

### 3.2 迁移策略：只追加，不改历史

`database-migration` 约定铁律"已发布的迁移文件不可修改"在此同样适用——即便本仓库
还没有真实生产部署，遵守这条约定本身也是在验证"脚手架的迁移机制经得住删除大动作"。

**决策：新增 `V17__drop_multi_tenancy.sql`**（common/，紧接当前最大版本 V16），
内容：
1. 角色数据合并：把 `SUPER_ADMIN`（role_id=-1）的用户关联迁到 `ADMIN`（role_id=1），
   删除 `SUPER_ADMIN` 这一行 `sys_role`
2. 菜单数据清理：删除 101/1011~1016（租户管理目录及其 6 个按钮）对应的 `sys_role_menu`
   与 `sys_menu` 行
3. `DROP COLUMN sys_menu.is_platform`
4. 8 张业务表 `DROP COLUMN tenant_id`（连带重建不含 `tenant_id` 的唯一索引，
   如 `uk_user_tenant_username` → `uk_user_username`）
5. `sys_oper_log`/`sys_login_log` `DROP COLUMN tenant_id`
6. 最后 `DROP TABLE sys_tenant`

三库方言差异（索引重建的写法）按 `database-migration` 约定分方言处理。

### 3.3 `TenantConstants.PLATFORM_TENANT_ID` 等预留概念一并删除

该常量本身标注"预留，当前未使用"，且它存在的前提（"完整 SaaS 多租户"）已经被
第一章的分析否定，不需要保留这个预留位。

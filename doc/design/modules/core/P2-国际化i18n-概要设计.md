# 一、设计目标（What & Why）

## 是什么（What）

国际化是让同一套代码按使用者的语言偏好呈现不同文案的能力。本设计覆盖三类文本，**三类的处理方式完全不同，混为一谈是本领域最常见的设计错误**：

| 类别 | 定义 | 例子 | 处理方式 |
|------|------|------|----------|
| **A 类：界面文案** | 写死在代码里的文本 | 按钮「新增」、表头「状态」、错误提示「角色不存在」 | 资源包（properties / JSON）+ 语义 key |
| **B 类：系统自带但存数据库** | 长得像数据、实际是界面元素 | `sys_menu.name`、`sys_dict_data.dict_label` | 由既有编码列**派生** key，资源包翻译 |
| **C 类：用户录入数据** | 租户/用户自己填的业务数据 | 用户昵称「张三」、租户自建的部门名 | **不翻译**，原样显示 |

核心职责：

1. **语言解析**：确定当前请求应使用哪种语言（用户偏好 → 请求头 → 默认）
2. **A 类翻译**：后端 `MessageSource`、前端 react-i18next，双方各持一份不重叠的语言包
3. **B 类 key 派生**：由 `sys_menu.permission` / `path`、`sys_dict_data.dict_type + dict_value` 派生稳定语义 key，**不改任何表结构**
4. **C 类保护**：明确禁止为用户录入字段增加 `xxx_en` 之类的多语言列
5. **防线**：ESLint 拦截新增硬编码文案 + key 对账测试防止译文与库脱节

## 为什么（Why）

1. **脚手架定位**：本仓库是所有派生项目的起点。i18n 若不在脚手架层做完，每个派生项目都要各自补完一遍，成本 ×N 且各自实现不一致
2. **避免返工**：i18n 是典型的「越晚做越贵」的横切关注点。现在 727 条词条，业务代码堆上来之后是几千条
3. **纠正错误直觉**：「给姓名加中文名/英文名字段」是最容易走上的错路。英文界面显示「张三」是**正确行为**（C 类不翻译），而 `sys_user.name_en` 解决不了 B 类的任何一条
4. **现状是摆设**：`spring.messages.basename` 已配置、`I18nUtil` 已存在、三个语言文件已就位，但**全项目只有 7 个 key，`I18nUtil` 只在 `LogServiceImpl` 一处被调用**。这是「留了门但没人走」的活证据，必须给出可验收的终点

# 二、定位与上下文（Where & When）

## 在哪里（Where）

后端位于 `gentry-core` 的 `com.gentry.core.i18n` 包；前端位于 `frontend/src/locales`。

```
┌─ 前端 ────────────────────────────────────────────────┐
│  react-i18next                                        │
│    ├── locales/{lang}/common.json   ← 高频通用词条      │
│    ├── locales/{lang}/menu.json     ← B 类:菜单 key    │
│    ├── locales/{lang}/dict.json     ← B 类:字典 key    │
│    ├── locales/{lang}/role.json     ← B 类:内置角色名  │
│    └── locales/{lang}/{page}.json   ← 按 pages/ 子目录 │
│  antd ConfigProvider locale ← 组件内置文案              │
└───────────────────────────────────────────────────────┘
             ↑ i18nKey (派生, 不落库)
┌─ 后端 ────────────────────────────────────────────────┐
│  GentryLocaleResolver → LocaleContextHolder            │
│  MessageSource (i18n/error, validation, log, export)   │
│  MenuI18nKeyResolver / DictI18nKeyResolver / RoleI18nKeyResolver │
└───────────────────────────────────────────────────────┘
```

请求流水线中的位置（插在 Sa-Token 认证之后、Controller 之前）：

```
TraceIdFilter → RequestLogFilter → RateLimit → RepeatSubmit
→ Sa-Token 认证 → [UserContext 写入 language] → [GentryLocaleResolver]
→ Controller → Service → ... → GlobalExceptionHandler（译错误码）
→ Jackson 序列化
```

## 在何时（When）

| 触发场景 | 语言来源 | 翻译方 |
|----------|----------|--------|
| 已登录用户访问接口 | `sys_user.language`（经 UserContext） | 后端 |
| 登录页 / 认证前 | `localStorage` → 浏览器 `navigator.language` → `zh_CN` | 前端 |
| 侧边栏菜单渲染 | 前端当前 locale | **前端**（后端只发 `i18nKey`） |
| 字典标签渲染 | 前端当前 locale | **前端**（后端只发 key） |
| 内置角色名渲染（ADMIN/USER） | 前端当前 locale | **前端**（后端只发 `i18nKey`，自建角色回退 `roleName`） |
| 校验失败提示 | 请求 locale | 后端 |
| 业务异常（ErrorCode） | 请求 locale | 后端 |
| Excel 导入/导出表头 | 请求 locale | 后端 |
| 定时通知 / 短信 | 收件人 `sys_user.language`（显式传入） | 后端 |
| 应用日志 `log.xxx()` | **不参与 i18n** | 固定英文 |

**登录前无用户 → 拿不到 `sys_user.language`**，这是用户级语言偏好方案的必然缺口，登录页只能用前端兜底语言。这不是妥协，任何把语言存在用户表的系统都有这个缺口。

# 三、主要用户与交互方（Who）

## 面向谁（Who）

| 角色 | 关注点 |
|------|--------|
| **前端开发** | 一律 `t('ns:key')`，禁止写中文字面量；ESLint 会报 error |

# 四、实现思路（How）

## 核心技术方案

七条决策，逐条给出结论与依据。

### 4.1 多语言的适用范围：租户为语言边界

采用「**不同租户各用一种语言**」，同时为「单租户内多语言用户共存」留门（语言存在用户级，天然支持后者）。

**不做**「单租户内同一条数据要同时有多语言名称」。那要求所有可维护名称字段都上翻译副表，而租户实际不会填，结果是满库空值加一堆回退逻辑。

### 4.2 语言来源：用户级偏好 + 前端兜底

解析优先级：

```
① UserContext.getLanguage()   ← 来自 sys_user.language，已登录时权威
② Accept-Language 请求头       ← 前端从 localStorage / navigator 计算后带上
③ zh_CN                       ← 兜底
```

| `language` 取值 | 含义 | 行为 |
|---|---|---|
| `NULL` | 用户从未选择过 | 跟随 `Accept-Language`（即前端的 localStorage → `navigator.language`） |
| `'zh_CN'` / `'en_US'` | 用户显式选择过 | 固定，跨设备一致 |

**必须允许 NULL**，否则三级解析链是假的：一旦所有存量用户被填上 `zh_CN`，第 ① 级恒命中，第 ② 级（请求头）对已登录用户永远不执行——浏览器是英文的用户在登录页看到英文、一登录就被切回中文，而他没做过任何选择。

`PUT /me/language` 不支持传 `null`「重置为跟随浏览器」：没有真实需求，加了还要设计 UI。

选用户级而非纯请求头，硬需求是**导出文件与定时通知要用用户语言**——这两个场景一个在后端组装 Excel、一个根本没有前端请求上下文，靠请求头拿不到。现状基线里「其他」那 63 处中文（`用户名`/`昵称`/`男`/`女`/`用户导入模板`/`全部数据`…）正是这个需求的物理载体。

### 4.3 B 类表示法：由既有编码列派生 key，零 DDL

**不新增列、不建翻译副表、不用 JSONB。** 派生规则：

| 表 | 规则 | 实例 |
|----|------|------|
| `sys_menu`（permission 非空） | `menu.` + `permission` 的 `:` 换 `.` | `system:user:add` → `menu.system.user.add` |
| `sys_menu`（permission 空，取 path） | `menu` + `path` 的 `/` 换 `.` | `/system` → `menu.system` |
| `sys_dict_data` | `dict.{dict_type}.{dict_value}` | → `dict.sys_data_scope.1` |
| `sys_dict_type` | `dict.type.{dict_type}` | → `dict.type.sys_user_gender` |
| `sys_role`（内置角色） | `role.` + `role_code` 小写 | `ADMIN` → `role.admin` |

> **内置角色 vs 自建角色**：`RoleI18nKeyResolver` 对任意 `role_code` 都会派生 key，但语言包只收录脚手架内置的 `ADMIN` / `USER`。运营自建角色的 `roleName` 是任意文本（C 类），派生 key 必然 miss，前端 `makeRoleLabel` 用 `defaultValue: roleName` 回退——与字典管理页「语言包接管内置项、自建项显示库里的 label」同构，不是 bug。

> **字典派生 key 的前提与重新评估条件（重要）**
>
> `sys_dict_data` / `sys_dict_type` 是**租户级表**（继承 `TenantEntity`，有 `tenant_id`）。对它们派生全局 key 成立的前提是**当前系统未启用多租户**（AGENTS.md：默认单租户形态，所有用户 `tenant_id = 1`；实测 21 条字典数据全在 `tenant_id = 1`）。
>
> **派生项目一旦真正启用多租户，必须重新评估**：届时租户 B 若建出相同的 `(dict_type, dict_value)`（例如 `sys_user_post` / `CEO` 但含义不同），派生 key 会撞上平台语言包，租户填的 label 被平台译文覆盖。处置方案二选一——把字典整体降为 C 类不翻，或给 `sys_dict_data` 加 `is_system` 标记只对内置项派生。这条要进多租户启用检查清单。
>
> `sys_menu` 无此问题（实测无 `tenant_id` 列，是全局表）。

**可行性已实测**（2026-08-17，MySQL `gentry` 库）：

```
type | 条数 | 有 permission | 有 path | 两者都空
  1  |   3  |      0        |    3    |    0
  2  |  12  |     12        |   12    |    0
  3  |  56  |     56        |    0    |    0

permission 重复: 0 条    派生 key 重复: 0 条
sys_dict_data: 21 条，全部有 dict_type + dict_value
```

**71/71 菜单 + 21/21 字典 = 92/92 全部可派生且无冲突。**

派生不出 key（`permission` 与 `path` 都为空）→ `i18nKey` 为 `null` → 前端回退显示库里的 `name`，回退是零行业务代码。

> **`sys_menu` 是全局表**（实测无 `tenant_id` 列），所以不存在「租户各自的菜单」。回退机制的真实用途是**派生项目新增的菜单还没补语言包条目**时优雅降级，而不是服务租户自建内容。
>
> 由此引出一条**已知行为**必须写清：脚手架自带的 71 条菜单，若有人在菜单管理页把 `name` 改掉（ADMIN 有 `system:menu:edit` 权限），因为 key 挂在 `permission` 上，界面仍显示语言包里的旧译文，改名不生效。正确做法是改语言包。**派生项目新增的菜单没有语言包条目，回退 `name`，改名立即生效**，不受此影响。

### 4.4 谁执行翻译：菜单/字典前端翻，后端自产文案后端翻

分工线：

| 翻译方 | 翻什么 | 量（去重） |
|--------|--------|-----------|
| **前端语言包** | 界面写死文案 + 菜单名 + 字典标签 + 内置角色名 | 531 + 92 key + 2 条角色 |
| **后端语言包** | ErrorCode、校验消息、导出表头与枚举、通知/短信模板 | 196 |

菜单/字典由后端**派生 key 并随 VO 下发**，前端渲染时才 `t()`。好处：

1. **纯前端切语言，零 API 往返**（后端译好成品则必须重拉菜单接口）
2. **key 类型安全**：前端语言包是 TS，key 写错编译期报错
3. **菜单名与页面内文案同源**，风格不会漂

后端自产文案后端翻，因为**导出 Excel、定时通知、短信没有前端**，后端语言包无论如何都得存在。

**两份语言包的 key 空间基本不重叠，唯一例外是导出表头 ↔ 表格表头约 30 条**（「用户名」「昵称」「状态」「创建时间」既是 Excel 表头又是页面表头）。决定：**接受这份重复，并加对账测试保证两边译文一致**。导出必须留在后端（有导入模板、有大数据量场景），把表头文案随请求传给后端会让 API 变丑。

### 4.5 前端库：react-i18next

需要 namespace（按页面拆 JSON，否则单文件几千行）、插值（实测有 `共 ${t} 条` 这类模板串 4 处）、懒加载、以及 i18n Ally 插件支持（对 531 条词条的迁移与 review 是刚性提效）。

namespace 按 `pages/` 子目录一一对应，外加 `common` / `menu` / `dict`：

```
locales/zh-CN/{common,menu,dict,user,role,tenant,dept,menu-mgmt,dict-mgmt,config,log,monitor,profile,home,login}.json
locales/en-US/... 同构
```

antd 组件内置文案由 `ConfigProvider locale` 负责，与 react-i18next 并行不冲突。

### 4.6 覆盖范围：统一全翻，不分档

**全部 727 条统一翻译**，唯一排除 `src/pages/dev/**`（`/dev/style` 样式对照页，AGENTS.md 已特批可写死）。

不采用「框架层全翻、业务页面留中文」的分档方案。原因是 `pages/` 里装的是租户/用户/角色/菜单/字典/部门/参数/日志/监控/个人中心/登录/工作台——**这些不是业务页面，这就是 RBAC 脚手架本身**，派生项目会原样保留。而且半翻的代码库里两种写法并存，规则变得不可学、review 无法机械判断，ESLint 也只能开成 warn 而 warn 是不会被消灭的。

### 4.7 后端边界：除 `log.xxx()` 全翻

36 处应用日志语句**不参与 i18n，改写为固定英文**。理由是确定性：日志的读者是运维，`log.info("用户 {} 登录成功")` 若参与 i18n，grep 日志得先知道当时哪个 locale 生效。

Swagger 注解实测 0 处中文，无需处理。

### 4.8 持久化文本：按「阅读者是否唯一确定」决定存 key 还是存译文

持久化文本的语言归属，判据只有一条：

> **文本的语言应由阅读者决定。阅读者在写入时唯一确定就存译文，不确定就存 key。**

| 场景 | 阅读者 | 结论 | 本版本 |
|------|--------|------|--------|
| 通知 / 短信内容 | 特定收件人，写入时已确定 | 存**译文**，按收件人 `sys_user.language` 定稿 | ✅ 做 |
| `sys_oper_log.module` | 任意管理员，写入时未知 | 库里仍存中文；读时把该中文当 key 译成 `moduleLabel` | ✅ module 已落地 |
| `sys_oper_log.title` | 任意管理员，写入时未知 | 仍中文直出 | ❌ **title 仍推迟** |

### 4.8.1 为什么 `@Log` 的 module 没进 i18n 首个版本（后续增量已落地 module，title 仍不做）

按判据它该存 key，但**落地成本远超那 52 条译文本身**，本版本划出翻译清单（后端 248 → 196）。三条实测依据：

```java
// OperLogMapper.xml —— 模糊匹配
AND module LIKE CONCAT('%', #{query.module}, '%')
```

```tsx
// OperLogPage.tsx
{ title: '操作模块', dataIndex: 'module', ... }                     // 直接显示原始值，未用 moduleLabel
{ name: 'module', label: '模块', node: <MenuTableSelect /> }         // 从菜单表选中文名当筛选值
<Descriptions.Item label="模块">{detail.module}</Descriptions.Item>  // 同样原始值
```

1. **现状筛选靠一个隐式字符串巧合工作**：`@Log(module="用户管理")` 的字面量恰好等于 `sys_menu.name`，`MenuTableSelect` 选出中文名去 LIKE 匹配日志表。这层跨表耦合没有任何文档或测试保护
2. **module 存 key 会同时打断显示与筛选**：前端用的是 `module` 不是 `moduleLabel`，会显示裸 `log.module.user`；筛选传中文匹配不上 key
3. **加 `module_key` 列也救不了筛选**：菜单名一旦翻译，英文用户在 `MenuTableSelect` 里看到并提交的是 "User Management"，LIKE 匹配中文 `用户管理` 照样失败。**只要菜单名翻译了，这个筛选对英文用户就是坏的，与 module 存什么无关**

也就是说要做对，必须连带重构操作日志的筛选链路（新增 module 枚举接口、筛选组件换掉 `MenuTableSelect`、`LIKE` 改 `=`、前端列改 `moduleLabel`），并改 `e2e/12-log-filters.spec.ts`。这是一次独立的功能重构，不该塞进 i18n 的首个版本。

**本增量的处理（2026-09-03）**：`@Log(module="用户管理")` 保持中文字面量入库，该字面量同时充当 i18n key。读时 `moduleLabel = getMessage(module, module)`。筛选改为精确匹配 + 自有下拉，不再用 `MenuTableSelect`。title 仍中文直出。

落地时**不把库里的中文改成 `log.module.user` 这类 key**。`@Log(module="用户管理")` 的字面量本身当 i18n key（`getMessage(value, value)`）：历史行零迁移，查不到 key 就显示原文。这与 §5.2 否决「中文原文当 UI key」不冲突——否决针对的是「操作」这种高频多语义词；`@Log` 的 module 是**互不重复的模块名**（用户管理 / 角色管理 / …），一词一境。

| # | 改动 | 状态（2026-09-03 同批合入） |
|---|------|-------------------|
| 1 | 新增 `GET /api/v1/logs/operation/modules`（`SELECT DISTINCT module`） | ✅ |
| 2 | 前端筛选把 `<MenuTableSelect />` 换成自有下拉，`label = t(key, {defaultValue: key})`、`value = key` | ✅ |
| 3 | `OperLogMapper.xml` 的 `module LIKE …` 改 `module = #{}` | ✅ |
| 4 | 前端列与详情 `dataIndex` 从 `module` 改 `moduleLabel` | ✅ |
| 5 | 后端 `messages*.properties` 收录 `@Log(module=…)` 的中文 key → 英文译文 | ✅ |
| 6 | 改 `e2e/12-log-filters.spec.ts`；新接口补 API IT | ✅ |

**合入门禁**：1～6 一次提交。禁止先推后端一半——`LIKE` 改 `=` 后前端仍靠菜单名模糊筛，行为会悄悄变窄且没有新下拉可用。

# 五、方案选型论证（含被否决方案）

本节记录调研到的开源实现与否决理由，避免后来者重复讨论。

## 5.1 开源实现调研

| 项目 | 对「数据库存的菜单名」的做法 | 实证 |
|------|------------------------------|------|
| **RuoYi**（~50k★） | **完全不做**。仓库只有一个 `messages.properties`，无 `_en` 文件，所有 value 是中文（`not.null=* 必须填写`）。`sys_menu.menu_name` 存中文直出 | 拉取 `ruoyi-admin/src/main/resources/i18n/messages.properties` |
| **JeeSite**（专业版） | **中文原文当 key + 全局译文表**。静态文案走 `i18n/{模块}/i18n_{lang}.properties`（内容 `您好=Hello`）；动态数据（菜单名/字典）走数据库表 `js_sys_lang(module_code, lang_code, lang_text, lang_type)`，后台在线维护。查不到 key 原样输出中文。附抽词 SQL 与源码扫描器 | `jeesite.com/docs/i18n-locale/` |
| **Soybean Admin** | **后端发 key、前端翻译**。`RouteMeta` 同时有 `title: string` 与 `i18nKey?: I18nKey \| null`（注释：设了 i18nKey 就忽略 title）；`shared.ts` 里 `const label = i18nKey ? $t(i18nKey) : title!`；另有 `updateLocaleOfGlobalMenus()` 专为切语言时在内存重算 label、不重请求后端 | `src/typings/router.d.ts`、`src/store/modules/route/shared.ts` |
| **Vben Admin**（~28k★） | **后端翻译**。`RouteMeta` 只有 `title: string`，无 key 通道；代码路由用 `title: $t('page.home.title')`；对后端数据的方案是请求自动带 `Accept-Language`，由服务端国际化数据 | `doc.vben.pro` locale / route 文档 |
| **Ant Design Pro** | **菜单不进数据库**，路由在 `config/routes.ts`，locale key 如 `menu.list.table-list`。B 类问题降级为 A 类 | Pro i18n 文档 |
| **Odoo** | 14/15 用 `ir_translation(model, res_id, field, lang, value)` 副表；**16 起废弃副表，改为把译文存成该列的 JSONB** | Odoo issue #107599 提到列在 varchar 与 jsonb 之间转换；第三方模块说明需同时兼容两种存储 |
| **JeecgBoot** | 现状**未**提供译文入库，社区 issue #2230 请求恢复老 JEECG 的「译文存数据库、可在线修改」 | GitHub issue #2230 |

## 5.2 被否决的方案

| 方案 | 否决理由 |
|------|----------|
| **给 C 类加 `name_en` 之类的列**（用户原始设想） | 方向性错误。英文界面显示「张三」是正确行为；且 `sys_user.name_en` 解决不了 B 类的任何一条 |
| **纯 key 入库**（`sys_menu.name = 'menu.system.user'`） | 运维打开 `sys_menu` 一片 key 无法排查；且派生项目通过菜单管理页新增菜单时没有 key 可填 |
| **翻译副表**（`sys_menu_i18n`） | 92 条静态记录不值一张表 + 一次 join，而菜单树在登录关键路径上。Odoo 16 已主动放弃这个拓扑 |
| **并列列**（`name` + `name_en`） | 加第三门语言要改表；`name_en` 为空时的回退逻辑会散落到每个查询点 |
| **新增 `i18n_key` 可空列** | 方向对（Soybean 就是这个语义），但**没必要落库**——既有 `permission`/`path`/`dict_type` 已是稳定编码，派生即可，零 DDL |
| **中文原文当 key**（JeeSite 式） | 「操作」实测出现 13 次，在表头是 Action、在日志里是 Operation，同词不同境无解；改文案即换 key 会让所有译文失效。且省下的成本没那么大：`ROLE_NOT_FOUND(20015, "角色不存在")` 这类枚举名已是现成语义 key，机械转换即可 |
| **后端译好菜单成品下发** | 切语言必须重拉菜单接口，Soybean 用一个 `i18nKey` 字段证明这个代价可以不付 |
| **分档翻译**（框架层全翻、业务页留中文） | 基于「派生项目会删掉 pages」的错误前提。实测 `pages/` 里除 `dev/` 全是脚手架自身的系统管理页 |
| **自撸极简 `t()`** | 插值、复数、namespace、类型生成会一个个补回来，最后是个残缺的 i18next |

## 5.3 已知代价（必须显性化）

| 代价 | 缓解 |
|------|------|
| `permission`/`path` 成为**隐式 i18n key**，改动会静默让译文退化为中文 | 加 key 对账测试；在 backend-conventions 里写明这条依赖 |
| zh 语言包必须写全（不能像 JeeSite 那样免写），因为 `error.role.not.found` 不能露给用户 | zh 包由抽词脚本从现有中文字面量**生成**，由构造保证完整；回退链 `目标语言 → zh_CN → key` |
| 导出表头与表格表头约 30 条译文双份维护 | 对账测试保证两边一致 |
| 登录页拿不到 `sys_user.language` | localStorage + `navigator.language` 兜底 |
| EasyExcel `@ExcelProperty("用户名")` 是注解常量，运行时翻不了 | 改为运行时构建表头（见后端详细设计 4.4） |
| 抽词依赖正则，会漏（字符串拼接、动态构造、JSX 文本节点） | 扫描脚本同时输出「含中文但未包 `t()`」的行清单供人工过，JSX 文本节点走 AST 单独扫一遍；ESLint 作为长期防线 |
| `MessageFormat` 把单引号当转义符，英文译文里的撇号会让 `{0}` 不被替换（静默 bug） | 带参译文的撇号一律写 `''` 或改措辞；由后端 C-07 测试检测未成对单引号 |
| **操作日志 `title` 列英文用户仍看中文**（`@Log` 的 title 本增量不做） | 有意接受。module 已按 §4.8.1 同批落地 |
| **管理员改了内置角色 ADMIN/USER 的 `roleName`，界面不生效**（派生 key 命中 `role.json`，译文优先） | 与菜单改名、字典改 label 同一类代价。自建角色无语言包条目，改名立即生效 |
| **管理员在字典管理页改了内置字典项的 label，界面不生效**（派生 key 命中语言包，译文优先）。此问题**与租户数量无关，单租户下同样存在** | 字典管理页对「语言包中存在该 key」的字典项**禁用 label 输入并给出提示**，把约束摆在动作发生处。前端持有语言包，`i18n.exists(i18nKey)` 即可判断，零后端改动。详见前端详细设计 §6.3 |
| 多租户启用后字典 key 会跨租户撞车 | 见 §4.3 的重新评估条件，列入多租户启用检查清单 |
| 前端 `columns` 若写成模块级常量，切语言表头不更新，且中文环境永不暴露 | 规范要求 `useMemo(..., [t])`；组件测试断言切语言后表头变化 |

# 六、预期效果与验收标准

## 性能指标

| 指标 | 目标 | 说明 |
|------|------|------|
| 语言解析开销 | < 0.1ms | ThreadLocal 读取，无 IO |
| 菜单树接口耗时增量 | < 1ms | 仅字符串派生，无额外查询、无 join |
| DDL 影响 | 仅 `sys_user` 加一列 | `sys_menu` / `sys_dict_data` 零改动 |
| 前端语言包体积 | 单 namespace < 20KB | 按 namespace 懒加载，切语言只拉需要的包 |
| 切换语言响应 | 无 API 往返即完成 UI 重渲染 | 落库请求异步进行，不阻塞界面 |

## 功能验收标准

| 编号 | 验收项 | 判定方式 |
|------|--------|----------|
| A-1 | `sys_user.language='en-US'` 的用户登录后，侧边栏菜单全英文 | E2E 断言 |
| A-2 | 同上，用户管理页表头、查询/重置按钮、分页文案全英文 | E2E 断言 |
| A-3 | 故意触发表单校验失败，提示为英文 | E2E 断言 |
| A-4 | `DELETE /api/v1/roles/{不存在的id}` 返回英文 message（现状中英文都返回「角色不存在」） | 集成测试 |
| A-5 | 界面上不出现任何裸 key（`menu.` / `error.` / `dict.` 前缀） | E2E 正则断言 |
| A-6 | 新增一条 `permission` 与 `path` 均为空的菜单，英文界面显示其原始 `name`，不显示 key、不报错 | 集成测试 |
| A-7 | 导出 Excel 表头随 `sys_user.language` 变化 | 集成测试 |
| B-1 | 语言包中 `menu.*` / `dict.*` 的每个 key 都能从库中派生出来（单向） | **E2E** I18N-001，孤儿 key 即红灯（前端详细设计 §10.2.1） |
| B-1b | en-US 用户侧边栏不含 CJK 字符（兜漏译） | **E2E** I18N-002 |
| B-2 | `src/components/**` 与 `src/pages/**`（除 `dev/`）无中文字面量 | ESLint `no-literal-string` = error |
| B-3 | 前后端重复的 ~30 条导出/表头译文两边一致 | 对账测试 |
| B-4 | 切换语言后菜单文案立即变化，且**未发起菜单接口请求** | E2E 断言（监听网络） |

**验收的硬门槛是 A-1 ~ A-5 的 E2E 用例**。「基础设施就绪」不是可验收的说法；这套用例绿了，i18n 就是真通的，红了或不存在就是摆设。

# 七、配置项

## 后端

```yaml
spring:
  messages:
    basename: i18n/messages,i18n/error,i18n/validation,i18n/export
    encoding: UTF-8
    fallback-to-system-locale: false      # 关键：避免服务器 Locale 干扰
    cache-duration: 3600s

gentry:
  i18n:
    enabled: true
    default-locale: zh_CN
    supported-locales: zh_CN,en_US
```

`fallback-to-system-locale: false` 必须显式设置，否则找不到 key 时会退到服务器系统语言，行为随部署环境漂移。

## 前端

```ts
// locales/config.ts
export const SUPPORTED_LOCALES = ['zh-CN', 'en-US'] as const;
export const DEFAULT_LOCALE = 'zh-CN';
export const LOCALE_STORAGE_KEY = 'gentry_locale';
```

## 数据库

```sql
-- common/V12__add_user_language.sql
ALTER TABLE sys_user ADD COLUMN language VARCHAR(20) NULL;   -- NULL = 未设置，跟随浏览器
```

可空列的 `ADD COLUMN` 三库均支持，放 `common/`。当前 `common/` 最大版本为 `V11`。

# 一、设计目标（What & Why）

## 是什么（What）

重复提交防护是防止用户在短时间内对同一接口发起多次相同请求的保护机制。通过自定义 `@RepeatSubmit` 注解和 AOP 切面，在方法执行前检查是否在指定时间窗口内已提交过相同请求，如果是则直接拒绝，避免产生重复数据或重复操作。

核心职责：

1. **请求指纹生成**：基于用户ID + 请求方法 + 请求路径 + 请求参数生成唯一的请求指纹
2. **时间窗口控制**：在指定时间窗口内（默认 3 秒），相同指纹的请求被视为重复提交
3. **注解驱动**：通过 `@RepeatSubmit` 注解标记需要防重的接口，灵活配置间隔时间
4. **本地缓存**：使用 Caffeine 存储请求指纹，TTL 到期自动清除
5. **仅写操作**：默认仅对 POST/PUT/DELETE 请求生效，GET 查询不防重

## 为什么（Why）

1. **数据一致性**：用户快速双击"提交"按钮，可能创建两条相同的车辆记录、两条相同的报警处理记录等。数据库层面的唯一约束虽然能防住一部分，但错误提示不友好
2. **操作幂等性**：网络抖动导致前端重试、用户手动刷新页面、移动端手势误触等场景都可能导致重复提交
3. **用户体验**：相比数据库报"唯一约束冲突"错误，在应用层提前拦截并给出"请勿重复提交"的友好提示，体验更好
4. **资源保护**：避免重复的写操作消耗数据库连接、网络带宽等资源
5. **低成本实现**：基于 Caffeine 本地缓存 + AOP 注解，无需引入 Redis，实现简单

# 二、定位与上下文（Where & When）

## 在哪里（Where）

位于 `precision-core` 模块的 `com.precision.core.web` 包中，通过 AOP 切面在 Controller 方法执行前拦截。

在请求处理链路中的位置：

```
HTTP Request
  → TraceIdFilter
  → RequestLogFilter
  → Sa-Token Filter（认证）
  → [RateLimitAspect]（限流）
  → DispatcherServlet
  → [RepeatSubmitAspect]      ← 重复提交检查
    → 首次提交 → Controller → Service
    → 重复提交 → 抛出 BizException(REPEAT_SUBMIT)
```

依赖关系：

- **被依赖方**：需要防重保护的写操作 Controller 方法
- **依赖方**：
  - Spring AOP（`@Around` 切面）
  - Caffeine Cache（存储请求指纹）
  - `@RepeatSubmit` 注解
  - `GlobalExceptionHandler`（捕获 `BizException` 并返回统一错误响应）
  - `UserContext`（获取用户ID）
  - `HttpServletRequest`（获取请求方法、路径、参数）

## 在何时（When）

触发场景：

| 触发场景 | 说明 | 防重效果 |
|----------|------|----------|
| 用户双击提交按钮 | 快速连续两次点击"保存" | 第二次请求被拦截 |
| 前端重试 | 网络超时后前端自动重试 | 重试请求被拦截 |
| 页面刷新 | POST 请求后用户刷新页面 | 浏览器重发请求被拦截 |
| 移动端误触 | 手指快速点击两次 | 第二次请求被拦截 |
| API 工具重发 | Postman 等工具重复发送 | 重复请求被拦截 |

不触发场景：

- GET 请求（查询操作，重复无副作用）
- 未标注 `@RepeatSubmit` 注解的方法
- 时间窗口过后再次提交（正常提交）
- 不同参数的提交（指纹不同）

# 三、主要用户与交互方（Who）

## 面向谁（Who）

| 角色 | 关注点 |
|------|--------|
| **后端开发** | 在写操作接口上加 `@RepeatSubmit` 注解，无需手动实现防重逻辑 |
| **前端开发** | 收到 REPEAT_SUBMIT 错误码时，展示"请勿重复提交"提示，禁用按钮 |
| **用户** | 双击提交按钮时看到友好提示，而非系统错误 |
| **DBA** | 减少数据库层面的重复数据，降低唯一约束冲突频率 |

## 与其他组件的交互

| 交互组件 | 交互方式 | 说明 |
|----------|----------|------|
| `@RepeatSubmit` | AOP 拦截 | 标注了此注解的方法会被切面拦截 |
| Caffeine Cache | 读写 | 存储请求指纹 |
| `UserContext` | 读取 | 获取用户ID（构建指纹的一部分） |
| `HttpServletRequest` | 读取 | 获取请求方法、路径、参数 |
| `GlobalExceptionHandler` | 异常捕获 | 重复提交异常由全局异常处理统一返回 |
| `RequestLogFilter` | 日志关联 | 被拒绝的请求仍被记录到请求日志 |
| `RateLimitAspect` | 链式协作 | 限流在防重之前执行 |

# 四、实现思路（How）

## 核心技术方案

### 4.1 @RepeatSubmit 注解设计

```java
/**
 * 重复提交防护注解
 * 标注在 Controller 方法上，防止短时间内重复提交
 */
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
@Documented
public @interface RepeatSubmit {

    /**
     * 防重间隔时间（毫秒）
     * 默认 3000 毫秒（3秒）
     */
    int interval() default 3000;

    /**
     * 提示信息（可选）
     */
    String message() default "请勿重复提交";
}
```

### 4.2 RepeatSubmitAspect 切面实现

```java
@Aspect
@Component
@Slf4j
public class RepeatSubmitAspect {

    // 请求指纹缓存：Key = 指纹字符串，Value = 提交时间戳
    private final Cache<String, Long> submitCache = Caffeine.newBuilder()
        .maximumSize(50000)
        .expireAfterWrite(3, TimeUnit.SECONDS)  // 最大防重间隔
        .build();

    @Around("@annotation(repeatSubmit)")
    public Object around(ProceedingJoinPoint point, RepeatSubmit repeatSubmit) {
        // 1. 仅对 POST/PUT/DELETE 生效
        HttpServletRequest request = getCurrentRequest();
        String method = request.getMethod();
        if (!"POST".equals(method) && !"PUT".equals(method) && !"DELETE".equals(method)) {
            return point.proceed();
        }

        // 2. 构建请求指纹
        String fingerprint = buildFingerprint(request, point);

        // 3. 检查是否重复
        long now = System.currentTimeMillis();
        Long lastSubmitTime = submitCache.getIfPresent(fingerprint);

        if (lastSubmitTime != null && (now - lastSubmitTime) < repeatSubmit.interval()) {
            log.warn("重复提交拦截 - fingerprint={}, interval={}ms",
                fingerprint, repeatSubmit.interval());
            throw new BizException(ErrorCode.REPEAT_SUBMIT);
        }

        // 4. 记录本次提交
        submitCache.put(fingerprint, now);

        // 5. 执行目标方法
        return point.proceed();
    }
}
```

### 4.3 请求指纹生成

指纹组成：

```
MD5(userId + method + path + body/params)
```

| 指纹部分 | 来源 | 说明 |
|----------|------|------|
| userId | UserContext.getUserId() | 区分不同用户 |
| method | request.getMethod() | 区分请求方法 |
| path | request.getRequestURI() | 区分不同接口 |
| params | 请求参数 | 区分不同参数的请求 |

参数获取策略：

| 请求类型 | 参数来源 | 说明 |
|----------|----------|------|
| POST + JSON Body | request body 的 MD5 | 相同请求体视为重复 |
| POST + Form | request parameter 排序拼接 | 相同表单数据视为重复 |
| PUT + JSON Body | request body 的 MD5 | 同上 |
| DELETE | path + query string | URL 相同视为重复 |

指纹生成流程：

```
1. 获取 userId（已登录）或 sessionId（未登录）
2. 获取 HTTP Method（POST/PUT/DELETE）
3. 获取请求路径（URI）
4. 获取请求参数：
   - Content-Type: application/json → 读取 body
   - Content-Type: application/x-www-form-urlencoded → 读取 parameter map
   - 其他 → 读取 query string
5. 拼接为字符串：userId:method:path:params
6. 计算 MD5 摘要作为指纹
```

### 4.4 缓存 TTL 策略

Caffeine 缓存的 TTL 设置为注解中 `interval` 的最大值。由于 Caffeine 不支持每个条目独立的 TTL，采用以下策略：

**方案一：固定最大 TTL**

```java
// 缓存 TTL 设为最大防重间隔（如 10 秒）
// 每个条目同时存储提交时间戳
// 检查时额外判断 now - lastSubmitTime < interval
private final Cache<String, Long> submitCache = Caffeine.newBuilder()
    .maximumSize(50000)
    .expireAfterWrite(10, TimeUnit.SECONDS)  // 大于所有可能的 interval
    .build();
```

此方案简单可靠，推荐采用。

### 4.5 使用示例

```java
@RestController
@RequestMapping("/api/v1/vehicles")
public class VehicleController {

    @PostMapping
    @RepeatSubmit(interval = 3000)
    public R<VehicleVO> create(@RequestBody VehicleCreateDTO dto) {
        // 创建车辆
    }

    @PutMapping("/{id}")
    @RepeatSubmit(interval = 2000)
    public R<VehicleVO> update(@PathVariable Long id, @RequestBody VehicleUpdateDTO dto) {
        // 更新车辆
    }

    @DeleteMapping("/{id}")
    @RepeatSubmit(interval = 1000)
    public R<Void> delete(@PathVariable Long id) {
        // 删除车辆
    }

    @GetMapping
    // GET 请求不需要 @RepeatSubmit
    public R<Page<VehicleVO>> list(VehicleQuery query) {
        // 查询车辆列表
    }
}
```

### 4.6 特殊场景处理

| 场景 | 处理方式 | 说明 |
|------|----------|------|
| 文件上传（multipart） | 仅使用文件名+大小作为参数指纹 | 不读取文件内容 |
| 大请求体（> 10KB） | 仅对前 10KB 计算 MD5 | 避免大文件影响性能 |
| 未登录用户 | 使用 sessionId 代替 userId | 登录/注册接口使用 |
| 批量操作 | 不同参数视为不同请求 | 批量创建 3 台车辆可正常提交 |

# 五、预期效果与验收标准

## 性能指标

| 指标 | 目标值 | 说明 |
|------|--------|------|
| 防重检查耗时 | < 2ms | MD5 + Caffeine 读写 |
| 内存占用 | < 20MB | 50000 个指纹条目约 20MB |
| MD5 计算耗时 | < 1ms | 对于 10KB 以内的请求体 |

## 功能验收标准

| 编号 | 验收项 | 验证方式 |
|------|--------|----------|
| S-001 | 相同请求在间隔内被拦截 | 快速连续两次提交相同数据，第二次被拒绝 |
| S-002 | 不同参数的请求不被拦截 | 连续提交不同参数的请求，均正常 |
| S-003 | 不同用户的请求独立 | 两个用户同时提交相同数据，均正常 |
| S-004 | 间隔过后可正常提交 | 被拦截后等待间隔时间，再次提交成功 |
| S-005 | GET 请求不防重 | 快速连续 GET 请求，均正常 |
| S-006 | POST 请求防重 | 快速连续 POST 请求，第二次被拒绝 |
| S-007 | PUT 请求防重 | 快速连续 PUT 请求，第二次被拒绝 |
| S-008 | DELETE 请求防重 | 快速连续 DELETE 请求，第二次被拒绝 |
| S-009 | 返回标准错误码 | 验证响应 code = 40002 |
| S-010 | 响应包含 traceId | 验证防重响应包含 traceId |
| S-011 | 无注解接口不防重 | 未标注 @RepeatSubmit 的 POST 接口不防重 |
| S-012 | 文件上传接口防重 | 上传文件时快速重发，第二次被拒绝 |

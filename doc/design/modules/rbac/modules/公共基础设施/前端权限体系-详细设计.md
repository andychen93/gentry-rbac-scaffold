# 一、概述

## 1.1 设计目标

建立前端权限管理体系，使得：

1. **权限数据流**：后端返回权限列表 → 前端存储在 userStore → 组件通过 hook/Provider 消费
2. **权限渲染规范**：制定统一的权限判断方式（菜单级、按钮级、页面级）
3. **权限隔离**：菜单权限（功能权限）与数据权限分离，数据权限留给后端处理
4. **开发便捷**：提供易用的 API，让开发者只需调用 `hasPermission()` 或 `<RowActions>` 即可
5. **性能优化**：权限数据在 userStore 中缓存，不需要每次都查询后端

## 1.2 权限的三个层级

| 层级 | 职责 | 实现方式 | 示例 |
|------|------|---------|------|
| **菜单权限（功能权限）** | 控制用户能否访问某个页面 | 后端返回菜单树，前端动态路由生成 | 隐藏「用户管理」菜单 |
| **按钮权限** | 控制用户能否执行某个操作（新增/编辑/删除） | 后端返回权限字符串列表，前端按钮条件渲染 | 隐藏「删除」按钮 |
| **数据权限** | 控制用户只能看到自己有权限的数据 | 后端在 SQL 中追加 WHERE 条件，前端无需处理 | 普通员工只看自己创建的订单 |

**本文档重点：前两个层级的前端实现；数据权限由后端 @DataScope 处理**。

# 二、架构设计

## 2.1 权限数据流

```
登录
  ↓
后端返回 LoginVO
  ├─ token: JWT token
  ├─ userInfo: {
  │   ├─ userId
  │   ├─ username
  │   ├─ roles: [ { roleCode, dataScope }, ... ]
  │   ├─ permissions: [ "system:user:add", "system:user:edit", ... ]
  │   ├─ menus: [ { path, name, i18nKey, permission, ... }, ... ]
  │   └─ language: 用户语言偏好
  │ }
  │ └─ passwordExpired: 密码是否过期
  │
  ↓ (authApi.login)
  
userStore 存储
  ├─ token → localStorage
  ├─ userInfo → memory
  ├─ menus → memory
  ├─ isLoggedIn → true
  │
  ↓ (刷新恢复 or 路由生成)
  
页面渲染
  ├─ 菜单：AppSidebar 读 userStore.menus，menuMapper 转换
  ├─ 按钮：RowActions / 手写判断 + hasPermission()
  ├─ 页面级：ProtectedRoute / LazyPage
  │
  └─ (后端自动处理数据权限) ← @DataScope 拦截器
```

## 2.2 权限 Provider 模式

```typescript
// App.tsx 顶层包裹
<PermissionProvider can={useUserStore(s => s.hasPermission)}>
  {/* 所有子组件可通过 usePermission() 访问权限判断 */}
  <Routes>...</Routes>
</PermissionProvider>
```

**为什么这样设计？**

- `@gentry/kit` 不依赖 `userStore`（kit 是可复用库，应用层才有 userStore）
- 但 Pro 组件需要做权限判断（如 RowActions 的条件渲染）
- 通过 Provider 注入 `can` 函数，kit 组件通过 `usePermission()` 调用，实现解耦

# 三、数据模型

## 3.1 UserInfo 完整定义

```typescript
interface UserInfo {
  userId: number;
  username: string;
  nickname: string;
  avatar: string;
  deptId: number;
  deptName: string;
  roles: {
    id: number;
    roleCode: string;
    roleName: string;
    dataScope: number;  // 1=全部 / 2=本部门及子部门 / 3=本部门 / 4=仅本人 / 5=自定义
  }[];
  permissions: string[];  // ["system:user:add", "system:user:edit", ...]
  menus: MenuNavItem[];
  language?: string;  // 用户语言偏好: "zh_CN" | "en_US"
}
```

## 3.2 权限字符串格式规范

权限标识遵循 `{module}:{entity}:{action}` 格式：

| 权限示例 | 含义 |
|--------|------|
| `system:user:list` | 系统 - 用户 - 查看列表 |
| `system:user:add` | 系统 - 用户 - 新增 |
| `system:user:edit` | 系统 - 用户 - 编辑 |
| `system:user:delete` | 系统 - 用户 - 删除 |
| `system:user:export` | 系统 - 用户 - 导出 |
| `system:role:*` | 系统 - 角色 - 所有操作（超级管理员） |
| `*` | 所有权限（平台管理员专用） |

**后端对应**：`sys_menu.permission` 字段

# 四、核心 API 设计

## 4.1 userStore.hasPermission(perm)

**用途**：判断当前用户是否拥有某个权限

**签名**：
```typescript
hasPermission: (perm: string) => boolean
```

**实现**：
```typescript
hasPermission: (perm: string) => {
  const { userInfo } = get();
  if (!userInfo) return false;
  return userInfo.permissions.includes(perm);
}
```

**使用示例**：

```typescript
// 在组件中判断权限
const { hasPermission } = useUserStore();

if (hasPermission('system:user:delete')) {
  // 显示删除按钮
}

// 或在状态选择器中
const canDelete = useUserStore(s => s.hasPermission('system:user:delete'));
```

## 4.2 usePermission() hook（来自 @gentry/kit）

**用途**：在组件内获取权限判断函数（通过 Context）

**签名**：
```typescript
usePermission: () => (perm: string) => boolean
```

**实现**：
```typescript
const PermissionContext = createContext<(perm: string) => boolean>(() => true);

export const usePermission = () => useContext(PermissionContext);
```

**使用示例**：

```typescript
// 在 Pro 组件内部使用
const can = usePermission();

const visible = items.filter(item => 
  !item.perm || can(item.perm)  // 无权限要求 or 有权限
);
```

## 4.3 PermissionProvider（来自 @gentry/kit）

**用途**：在顶层注入权限判断函数，供所有子组件的 usePermission() 调用

**签名**：
```typescript
const PermissionProvider = ({
  can,
  children,
}: {
  can: (perm: string) => boolean;
  children: React.ReactNode;
}) => ...
```

**使用示例**：

```typescript
// App.tsx
export default function App() {
  const hasPermission = useUserStore(s => s.hasPermission);
  
  return (
    <PermissionProvider can={hasPermission}>
      <Routes>...</Routes>
    </PermissionProvider>
  );
}
```

# 五、权限控制规范

## 5.1 菜单级权限（路由级）

**场景**：用户无权限访问某个页面，该页面对应的菜单应隐藏

**实现方式**：后端返回的菜单树中只包含用户有权限的菜单

**流程**：

```
后端 /getUserInfo
  → 查询用户的所有菜单（基于 user_role → role_menu → sys_menu）
  → 返回菜单列表（仅包含有 permission 且用户有权的菜单）
  
前端 menuMapper.ts
  → COMPONENT_MAP 将菜单 path 映射到页面组件
  → toRouteConfigs(menus) 生成动态路由
  
访问 /system/users
  → 如果菜单列表中有 path="/system/users" → 路由可访问
  → 如果菜单列表中无该路由 → 访问时自动跳到首页
```

**特殊情况**：

- **子菜单全无权限**：父菜单也应隐藏
  - 实现：后端返回时已过滤，前端无需额外处理
  
- **用户刷新页面**：
  - 实现：`App.tsx` 的 `useEffect` 检测到 token 存在但 userInfo 丢失时，调用 `fetchUserInfo()` 重新获取
  
- **权限变更后的菜单更新**：
  - 实现：菜单变更由后端管理员操作，下次登录自动更新；在线用户可触发「重新加载菜单」（可选功能）

## 5.2 按钮级权限

**场景**：表格行操作按钮（编辑、删除）根据用户权限条件渲染

### 方案 A：使用 Pro 组件 RowActions

**适用**：表格行尾的操作按钮集合

**实现**：

```typescript
import { RowActions } from '@gentry/kit';
import { EditOutlined, DeleteOutlined } from '@ant-design/icons';

function UserTable() {
  return (
    <Table
      columns={[
        // ...
        {
          title: '操作',
          render: (_, record) => (
            <RowActions
              items={[
                {
                  key: 'edit',
                  label: '编辑',
                  icon: <EditOutlined />,
                  perm: 'system:user:edit',
                  onClick: () => handleEdit(record),
                },
                {
                  key: 'delete',
                  label: '删除',
                  icon: <DeleteOutlined />,
                  perm: 'system:user:delete',
                  danger: true,
                  onClick: () => handleDelete(record),
                },
              ]}
            />
          ),
        },
      ]}
    />
  );
}
```

**RowActions 行为**：

- 无 `perm` 属性的项：始终显示
- 有 `perm` 属性且用户无权限：隐藏（不占位）
- 有 `perm` 属性且用户有权限：显示

### 方案 B：手写权限判断

**适用**：单个按钮或非表格操作

```typescript
function UserDetail() {
  const hasPermission = useUserStore(s => s.hasPermission);

  return (
    <div>
      {hasPermission('system:user:edit') && (
        <Button type="primary" onClick={handleEdit}>
          编辑
        </Button>
      )}
      {hasPermission('system:user:delete') && (
        <Button danger onClick={handleDelete}>
          删除
        </Button>
      )}
    </div>
  );
}
```

### 方案 C：条件渲染组件

**适用**：整块功能模块的权限控制

```typescript
function OrderDetail() {
  const hasPermission = useUserStore(s => s.hasPermission);

  if (!hasPermission('business:order:view')) {
    return <AccessDenied />;
  }

  return (
    <div>
      {hasPermission('business:order:edit') && <EditSection />}
      {hasPermission('business:order:export') && <ExportButton />}
    </div>
  );
}
```

## 5.3 页面级权限

**场景**：用户访问 URL 时，检查是否有权限访问该页面

**实现方式**：

```typescript
// 方案 A：ProtectedRoute 包裹
// 已在 App.tsx 中使用
<ProtectedRoute>
  <AppLayout>
    <Routes>
      {/* 动态路由已由菜单过滤，这里是双保险 */}
    </Routes>
  </AppLayout>
</ProtectedRoute>

// 方案 B：页面组件内自己判断
if (!hasPermission('required:permission')) {
  return <AccessDenied />;
}
```

# 六、开发指南与最佳实践

## 6.1 新增权限点的步骤

### Step 1：后端定义权限点

在菜单管理页面新增菜单：

```
菜单名称：删除用户
菜单类型：按钮
权限标识：system:user:delete  ← 注意命名规范
所属角色：选择哪些角色有此权限
```

此时后端 SQL：
```sql
INSERT INTO sys_menu (name, path, permission, type, status)
VALUES ('删除用户', NULL, 'system:user:delete', 3, 1);

INSERT INTO sys_role_menu (role_id, menu_id) VALUES (?, ?);
```

### Step 2：前端使用权限点

```typescript
const hasDeletePerm = useUserStore(s => 
  s.hasPermission('system:user:delete')
);

if (hasDeletePerm) {
  // 显示删除按钮
}
```

### Step 3：验证

1. 登录账号 A（有权限）→ 看到删除按钮
2. 登录账号 B（无权限）→ 看不到删除按钮
3. 修改账号 B 的角色，添加删除权限 → 重新登录 → 看到删除按钮

## 6.2 权限命名规范

**必须遵循**：`{module}:{entity}:{action}`

### 常见 action 列表

| action | 含义 | 对应按钮 |
|--------|------|---------|
| `list` | 查看列表 | （菜单权限） |
| `view` 或 `detail` | 查看详情 | 详情按钮 |
| `add` 或 `create` | 新增 | 新增按钮 |
| `edit` 或 `update` | 编辑 | 编辑按钮 |
| `delete` | 删除 | 删除按钮 |
| `export` | 导出 | 导出按钮 |
| `import` | 导入 | 导入按钮 |
| `approve` | 审批 | 审批按钮 |
| `reject` | 驳回 | 驳回按钮 |

### 模块命名规范

| 模块 | 权限前缀 |
|------|---------|
| 系统管理 | `system:` |
| 业务-订单 | `business:order:` |
| 业务-设备 | `business:device:` |
| 业务-车辆 | `business:vehicle:` |
| 运维监控 | `monitor:` |

### 完整示例

```
system:user:list        → 用户列表页菜单
system:user:add         → 新增按钮
system:user:edit        → 编辑按钮
system:user:delete      → 删除按钮
system:user:export      → 导出按钮
system:role:approve     → 审批按钮
```

## 6.3 权限测试检查清单

新增权限点后，必须做以下验证：

| 检查项 | 验证方法 |
|--------|---------|
| 权限标识正确 | 后端 sys_menu.permission 与前端代码完全一致 |
| 超级管理员拥有 | 超级管理员账号登录能看到功能 |
| 普通用户无权限 | 普通账号登录看不到功能 |
| 权限变更生效 | 修改账号的角色权限后，重新登录能立即生效 |
| 菜单权限隐藏菜单 | `type=2`（菜单）且用户无权，该菜单应在侧栏隐藏 |
| 按钮权限隐藏按钮 | `type=3`（按钮）且用户无权，该按钮应隐藏 |
| 刷新页面保留状态 | 刷新后权限状态不变 |

# 七、常见问题与陷阱

## 7.1 权限不生效？

**现象**：代码里判断权限了，但按钮还是显示或隐藏错误

**排查清单**：

1. **权限字符串拼错了？**
   ```typescript
   // ❌ 错误
   hasPermission('system:user:delete')  // 但后端是 system:user:del
   
   // ✅ 正确
   hasPermission('system:user:delete')  // 与后端 sys_menu.permission 一致
   ```

2. **权限点没关联到用户的角色？**
   ```sql
   -- 检查 sys_role_menu 是否有关联记录
   SELECT * FROM sys_role_menu 
   WHERE menu_id = (SELECT id FROM sys_menu WHERE permission = 'system:user:delete')
     AND role_id IN (SELECT role_id FROM sys_user_role WHERE user_id = ?);
   ```

3. **userInfo 还没加载？**
   ```typescript
   // ❌ 错误（登录瞬间可能还没拿到 userInfo）
   const hasPermission = useUserStore(s => s.hasPermission);
   if (hasPermission('...')) { ... }  // userStore.userInfo 可能为 null
   
   // ✅ 正确
   const isLoggedIn = useUserStore(s => s.isLoggedIn);
   const hasPermission = useUserStore(s => s.hasPermission);
   if (isLoggedIn && hasPermission('...')) { ... }
   ```

4. **权限点是菜单权限还是按钮权限？**
   ```sql
   -- 检查 sys_menu.type
   SELECT id, name, type, permission FROM sys_menu WHERE permission = 'system:user:delete';
   
   -- type=1: 目录  (在侧栏显示，无权限)
   -- type=2: 菜单  (页面级权限)
   -- type=3: 按钮  (按钮级权限)
   ```

## 7.2 刷新页面后权限丢失？

**现象**：按钮显示正常，刷新页面后突然隐藏或出错

**根因**：`userStore` 是内存存储，刷新后丢失；token 还在 localStorage，但 userInfo 丢失

**解决**：`App.tsx` 已处理，但如果发生说明：

```typescript
useEffect(() => {
  if (token && !userInfo) {
    // 恢复登录态：重新获取 userInfo（包含权限）
    fetchUserInfo().catch(() => { /* token 过期 */ });
  }
}, [token, userInfo, fetchUserInfo]);
```

检查是否调用了此逻辑。

## 7.3 超级管理员权限不生效？

**现象**：超级管理员（role_code = `super_admin`）应该看到所有功能，但某些按钮还是隐藏

**根因**：前端没有特殊处理超级管理员

**解决**：需要在前端加一行判断

```typescript
// 方案 A：在 hasPermission 里处理
hasPermission: (perm: string) => {
  const { userInfo } = get();
  if (!userInfo) return false;
  
  // 超级管理员拥有所有权限
  const isSuperAdmin = userInfo.roles?.some(r => r.roleCode === 'super_admin');
  if (isSuperAdmin) return true;
  
  return userInfo.permissions.includes(perm);
}

// 方案 B：后端保证
// 让后端的 StpInterfaceImpl.getPermissionList() 对超级管理员返回 ["*"]
// 前端判断 permissions.includes('*') 时也要放行
```

**建议**：交由后端处理（StpInterfaceImpl 的 getPermissionList 已这样做），
前端只需按正常权限判断即可。

## 7.4 权限粒度太细或太粗？

**太细**（每个字段都一个权限）：
- ❌ 维护成本高，容易遗漏
- ✅ 改为：`{module}:{entity}:edit` 一个权限，所有字段可编辑

**太粗**（整个模块一个权限）：
- ❌ 无法细粒度控制
- ✅ 改为：`{module}:{entity}:add/edit/delete` 分开

**推荐**：按上面的 action 列表分粒度（list/add/edit/delete/export/import）

# 八、前端权限体系与后端数据权限的区别

| 维度 | 前端权限（功能权限） | 后端数据权限 |
|------|-------------------|------------|
| **定义** | 用户能否访问某个页面/按钮 | 用户能看到什么范围的数据 |
| **控制方式** | 前端渲染时判断 `hasPermission()` | 后端 SQL 自动追加 WHERE 条件 |
| **规范** | `system:user:add` 等字符串 | `data_scope` 字段（1=全部/2=本部门及子部门/3=本部门/4=仅本人/5=自定义） |
| **绕过难度** | 容易（打开浏览器开发者工具修改权限） | 难（需要修改 SQL 或数据库） |
| **安全性** | 低（只是 UI 隐藏） | 高（服务端强制执行） |
| **举例** | 普通员工看不到「删除用户」按钮 | 普通员工即使有删除权限，也只能删除自己创建的订单 |

**结论**：前端权限是"礼貌的隐藏"（减少用户困惑），数据权限是"真正的限制"（保护数据安全）。
两层都需要，不能只靠前端。

```
  3. 在表格行尾查看操作按钮
预期：
  看不到「删除」按钮（或按钮被禁用）
```

### 用例 3：权限变更生效

```
场景：为用户新增权限后，权限立即生效
步骤：
  1. 账号 A 登录（无 system:user:delete 权限）
  2. 进入用户管理，确认看不到删除按钮
  3. 管理员修改账号 A 的角色，添加 system:user:delete 权限
  4. 账号 A 重新登录
  5. 进入用户管理，查看操作按钮
预期：
  现在能看到「删除」按钮
```

### 用例 4：菜单权限隐藏菜单

```
场景：用户无菜单权限，菜单应隐藏
步骤：
  1. 登录账号 user1（无 system:role:list 权限）
  2. 查看左侧菜单
预期：
  「角色管理」菜单应隐藏或不可点击
```

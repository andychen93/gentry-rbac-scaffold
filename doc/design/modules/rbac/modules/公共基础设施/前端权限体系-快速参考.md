## 权限三层级

| 层级 | 实现方式 | 示例 | 后端 |
|------|---------|------|------|
| **菜单权限** | 后端返回过滤后的 menus | 隐藏「用户管理」菜单 | 返回菜单树 |
| **按钮权限** | `hasPermission()` 或 `<RowActions perm="...">` | 隐藏「删除」按钮 | 权限字符串 |
| **数据权限** | 后端 @DataScope 拦截器处理 | 只能看自己部门的数据 | 追加 WHERE |

---

## 权限命名规范

```
{module}:{entity}:{action}

module:  system / business:order / business:device / monitor
entity:  user / role / menu / order / device / vehicle
action:  list / view / add / edit / delete / export / import / approve / reject

示例：
  system:user:delete          (系统-用户-删除)
  business:order:export       (业务-订单-导出)
  business:device:approve     (业务-设备-审批)
```

## 快速使用 API

### 判断权限

```typescript
// 方式 1：在组件中直接判断（推荐用于手写逻辑）
const canDelete = useUserStore(s => s.hasPermission('system:user:delete'));

// 方式 2：RowActions（推荐用于表格行操作）
<RowActions items={[
  {
    key: 'delete',
    label: '删除',
    icon: <DeleteOutlined />,
    perm: 'system:user:delete',
    onClick: () => handleDelete(record),
  }
]} />

// 方式 3：在 Pro 组件内部（库内用）
const can = usePermission();
const visible = items.filter(i => !i.perm || can(i.perm));
```

### 条件渲染

```typescript
// 方式 A：单个按钮
{canDelete && <Button danger onClick={handleDelete}>删除</Button>}

// 方式 B：整块功能
{canEdit && <EditForm />}

// 方式 C：表格行操作（推荐）
<RowActions items={[...]} />
```

## 新增权限 3 步

### 1️⃣ 后端菜单管理新增

```
菜单名称: 删除订单
权限标识: business:order:delete  ← 关键
类型: 按钮 (type=3)
角色: 选择哪些角色有权
```

### 2️⃣ 前端代码使用

```typescript
<RowActions items={[
  {
    key: 'delete',
    perm: 'business:order:delete',  ← 与后端一致
    label: '删除',
    onClick: () => handleDelete(),
  }
]} />
```

### 3️⃣ 测试验证

```
✓ 有权账号：看到按钮
✓ 无权账号：看不到按钮
✓ 权限变更：重新登录后生效
✓ 后端校验：直接调 API 返回 403
```

## 权限判断流程图

```
用户访问页面
    ↓
有权限的菜单？
    ├─ 否 → 隐藏菜单 → 无法访问
    └─ 是 → 进入页面
         ↓
    查看按钮
         ├─ 有权限 → 显示按钮
         └─ 无权限 → 隐藏按钮
         ↓
    点击按钮调用 API
         ↓
    后端 @SaCheckPermission 再次校验
         ├─ 通过 → API 执行
         └─ 不通过 → 返回 403
```

## 常见问题速查

| 问题 | 原因 | 解决 |
|------|------|------|
| 按钮没隐藏 | `perm` 拼错或为空 | 检查 permission 字符串是否与后端一致 |
| 权限始终 false | userInfo 未加载 | 在 isLoggedIn=true 后再判断 |
| 重新登录后权限还是旧的 | 浏览器缓存 | 清除 localStorage 或 token 过期 |
| 超级管理员无法使用功能 | super_admin 未配置权限 | 后端需要返回 `["*"]` 权限 |
| 刷新页面权限丢失 | 正常现象，会自动恢复 | App.tsx 会调 fetchUserInfo()，不用管 |

## 权限类型（type）

```
type=1: 目录      (菜单树的分类，如「系统管理」)
type=2: 菜单      (页面级权限，如「用户管理」页面)
type=3: 按钮      (操作权限，如「删除」按钮)
```

## 权限变更时间线

```
管理员修改菜单权限
    ↓ (数据库更新)
在线用户 A：看不到变更，需要重新登录
用户 B 新登录：立即看到新权限
    ↓ (可选：提供「刷新权限」功能)
用户 A 点击「刷新」：调用 fetchUserInfo() → 权限更新
```

## 权限安全性

| 防线 | 位置 | 能否绕过 |
|------|------|---------|
| 1️⃣ 菜单隐藏 | 前端 | ✅ 可以（修改代码） |
| 2️⃣ 按钮隐藏 | 前端 | ✅ 可以（调试工具） |
| 3️⃣ 后端校验 | 后端 @SaCheckPermission | ❌ 不可以（必须通过） |
| 4️⃣ 数据权限 | 后端 @DataScope | ❌ 不可以（SQL 强制执行） |

**结论**：前端权限是「礼貌的隐藏」，后端权限是「真正的保护」。两层都要有。

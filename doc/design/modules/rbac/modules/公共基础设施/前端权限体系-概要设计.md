# 一、设计目标（What & Why）

## 是什么（What）

前端权限体系是一套统一的权限数据管理和权限判断机制。包含：

1. **权限数据存储**：后端返回的权限列表在 `useUserStore()` 中缓存
2. **权限判断接口**：提供 `hasPermission()` 和 `usePermission()` 两套 API
3. **权限渲染规范**：菜单级、按钮级、页面级权限的标准实现方式
4. **Pro 组件集成**：RowActions 等 Pro 组件的权限条件渲染

## 为什么（Why）

1. **用户体验**：隐藏用户无权限的菜单和按钮，避免"点了没反应"
2. **开发便捷**：统一的权限 API，开发者只需调用 `hasPermission()`，不用手写权限逻辑
3. **代码一致性**：所有权限判断遵循同一规范，易于审查和维护
4. **性能优化**：权限列表在内存中缓存，不需要每次都查后端
5. **安全性**：虽然前端权限可绕过（打开开发者工具修改），但后端会校验 `@SaCheckPermission`，前端只是"礼貌的隐藏"

# 二、定位与上下文（Where & When）

## 在哪里（Where）

前端权限体系分为两层：

| 层 | 位置 | 职责 |
|----|------|------|
| **应用层** | `src/stores/userStore.ts`、`src/App.tsx` | 权限数据存储、应用级权限判断 |
| **库层** | `@gentry/kit/components/pro/permission.ts` | 权限 Provider、usePermission hook、Pro 组件集成 |

权限流程与后端的关系：

```
后端 StpInterface.getPermissionList()
  ↓ 返回权限列表
前端 userStore.permissions
  ↓ 存储在内存
应用各处
  ├→ hasPermission() 判断
  ├→ RowActions 条件渲染
  └→ 菜单 / 路由生成
```

## 在何时（When）

触发场景：

| 场景 | 时机 | 处理方式 |
|------|------|---------|
| 用户登录 | 登录成功返回 userInfo | `useUserStore.login()` 保存权限到内存 |
| 页面刷新 | App 挂载时检测 token 存在但 userInfo 丢失 | `App.useEffect` 调用 `fetchUserInfo()` 恢复权限 |
| 权限变更 | 管理员修改用户角色 / 菜单权限 | 用户重新登录时生效；在线用户需手动「重载页面」 |
| 查看菜单 | 进入应用后 AppSidebar 渲染 | 从 userStore.menus 读取（已过滤无权限菜单） |
| 查看按钮 | 在组件中调用 hasPermission() | 实时判断权限列表 |

# 三、主要用户与交互方（Who）

## 面向谁（Who）

| 角色 | 关注点 |
|------|--------|
| **前端开发** | 在组件中使用 `hasPermission()` 或 `<RowActions>`，无需关心权限数据来源 |
| **后端开发** | 在接口上标注 `@SaCheckPermission`，后端会自动校验；前端权限只是 UI 隐藏 |
| **系统管理员** | 通过菜单管理、角色管理配置权限，用户登录后自动生效 |
| **测试人员** | 验证不同角色用户能否看到对应的菜单和按钮 |

## 与其他组件的交互

| 交互方 | 交互方式 | 说明 |
|--------|---------|------|
| 后端 `/getUserInfo` | 调用 API 获取权限列表 | 登录和刷新时触发 |
| userStore | 读写权限数据 | 存储 token、userInfo、permissions、menus |
| PermissionProvider | Provider 注入权限函数 | 库层组件通过 Context 消费 |
| usePermission hook | 在组件内读取权限函数 | Pro 组件（RowActions 等）使用 |
| 菜单映射 menuMapper | 菜单树 → 动态路由 | 已过滤的菜单列表转换为可访问的路由 |
| 多语言 i18next | 翻译菜单文案 | 菜单名称、按钮文案支持中英切换 |

# 四、核心设计

## 4.1 权限数据流

```
用户登录
  │
  ├─ 前端 POST /login → 后端验证身份
  │   ↓
  │   后端查询用户的权限列表
  │   (user_id → user_role → role_menu → menu.permission)
  │   ↓
  │   返回 LoginVO {
  │     token: "jwt...",
  │     userInfo: {
  │       userId,
  │       username,
  │       roles: [...],
  │       permissions: ["system:user:add", "system:user:edit", ...],
  │       menus: [{ path, name, i18nKey, ... }, ...],
  │       language: "zh_CN"
  │     }
  │   }
  │
  ├─ 前端接收 userInfo
  │   ↓
  │   userStore.login() 存储：
  │   - token → localStorage（跨会话保持）
  │   - userInfo → memory（内存存储）
  │   - permissions 从 userInfo 中提取
  │   - menus 从 userInfo 中提取
  │
  ├─ 应用层使用权限
  │   ├─ 菜单：AppSidebar 从 userStore.menus 读取（已过滤）
  │   ├─ 按钮：hasPermission('system:user:delete') 判断
  │   └─ 路由：menuMapper 根据 menus 生成动态路由
  │
  └─ 后端同步验证
      └─ 每个 Controller 方法上的 @SaCheckPermission 注解
         再次校验权限（即使前端放行，后端也会校验）
```

## 4.2 权限三个层级

### 菜单权限（功能权限）

- **定义**：用户能否看到某个菜单 / 访问某个页面
- **实现**：后端返回的 menus 中已过滤；前端通过动态路由生成
- **示例**：「用户管理」菜单只在有 `system:user:list` 权限的用户侧栏显示

### 按钮权限

- **定义**：用户能否执行某个操作（新增 / 编辑 / 删除 / 导出）
- **实现**：前端 `hasPermission()` 判断，条件渲染按钮
- **示例**：「删除」按钮只有拥有 `system:user:delete` 权限的用户才能看到

### 数据权限

- **定义**：用户只能看到自己有权访问的数据范围
- **实现**：**后端处理**（@DataScope 拦截器），前端无需关心
- **示例**：普通员工即使有「查看订单」权限，也只能看到自己部门的订单

## 4.3 权限判断的两套 API

### API #1：应用层

```typescript
// userStore 中的方法
hasPermission: (perm: string) => boolean
```

**适用**：组件中直接判断权限

```typescript
const canDelete = useUserStore(s => s.hasPermission('system:user:delete'));
```

### API #2：库层（@gentry/kit）

```typescript
// 在 PermissionProvider 内的组件中
const can = usePermission();
const hasPermission = can('system:user:delete');
```

**适用**：Pro 组件（RowActions、其他库组件）通过 Context 消费权限

# 五、实现思路（How）

## 5.1 数据存储

**userStore** 使用 Zustand，存储：

```typescript
interface UserStore {
  token: string | null;              // JWT token（localStorage 备份）
  userInfo: UserInfo | null;         // 用户完整信息
  menus: MenuNavItem[];              // 菜单树（已过滤）
  isLoggedIn: boolean;               // 登录状态
  
  hasPermission: (perm: string) => boolean;
  // ... 其他方法
}
```

## 5.2 权限提供者

**PermissionProvider**（@gentry/kit）通过 React Context 注入权限判断函数：

```typescript
// App.tsx
<PermissionProvider can={useUserStore(s => s.hasPermission)}>
  <Routes>...</Routes>
</PermissionProvider>
```

**好处**：
- Kit 包不依赖应用层的 userStore
- Pro 组件通过 `usePermission()` hook 获取权限函数
- 解耦：库与应用独立演进

## 5.3 权限渲染规范

| 场景 | 实现方式 | 代码示例 |
|------|---------|---------|
| 菜单隐藏 | 后端返回已过滤的 menus | 前端无需处理 |
| 按钮隐藏（Pro 组件） | `<RowActions perm="...">`  | 组件内部通过 usePermission() 判断 |
| 按钮隐藏（手写） | `{hasPermission(...) && <Button>}` | 开发者自己判断 |
| 页面隐藏 | 路由不包含无权菜单 | 访问无权路由时重定向 |

# 六、关键设计决策

| 决策 | 方案 | 理由 |
|------|------|------|
| 权限数据存在哪 | 内存（userStore）+ localStorage（token） | token 需要跨会话保持；userInfo 只在会话内用，无需持久化 |
| 刷新页面权限恢复 | App 层检测 token 存在但 userInfo 丢失时调 fetchUserInfo() | 自动恢复，用户无感知 |
| 权限判断交由谁 | 前端 + 后端双层 | 前端 UI 隐藏（体验好），后端 @SaCheckPermission 强制校验（安全） |
| PermissionProvider 谁负责 | 应用层在 App.tsx 注入 | 库层 Pro 组件无法拿到 userStore，通过 Provider 注入解决 |
| 菜单权限与按钮权限分离 | 菜单由后端返回决定，按钮由前端根据 permissions 列表判断 | 菜单是导航结构（少），按钮是操作点（多），分离便于管理 |

# 七、预期效果与验收标准

## 性能指标

| 指标 | 目标值 | 说明 |
|------|--------|------|
| 权限判断耗时 | < 1ms | 内存查找，无 I/O |
| 菜单树生成耗时 | < 50ms | 后端返回后前端转换，一次性 |
| 权限缓存命中率 | 100% | 登录后权限不变，每次判断都走缓存 |

## 功能验收标准

| 编号 | 验收项 | 验证方式 |
|------|--------|----------|
| A-001 | 用户无菜单权限时菜单隐藏 | 无权限账号登录，检查侧栏是否隐藏该菜单 |
| A-002 | 用户无按钮权限时按钮隐藏 | 无权限账号登录，检查表格行操作是否隐藏按钮 |
| A-003 | 超级管理员看到全部权限 | super_admin 账号能看到所有菜单和按钮 |
| A-004 | 权限变更后下次登录生效 | 修改账号权限，重新登录后权限生效 |
| A-005 | 页面刷新权限不丢失 | 刷新页面后权限状态保持不变 |
| A-006 | 后端再次校验权限 | 前端绕过权限（直接调 API），后端返回权限不足错误 |
| A-007 | RowActions 权限条件渲染 | 有/无权限时按钮正确显示/隐藏 |
| A-008 | 手写权限判断正确 | `hasPermission()` 返回值准确 |

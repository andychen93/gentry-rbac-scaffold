## 一、缺陷

在真机上建第二个租户做验证时发现：**新租户的 admin 可以列出、新增、修改、删除所有租户，包括默认租户。**

```
POST /api/v1/tenants            → 建租户 probe002，返回其 admin 初始密码
POST /api/v1/auth/login         → 用 probe002/admin 登录
GET  /api/v1/tenants            → 200，返回 2 条（probe002 + default）
GET  /api/v1/auth/user-info     → permissions 含 system:tenant:{list,add,edit,remove,detail,config}
```

数据隔离本身是好的（新租户只看到自己的 1 用户 / 1 部门 / 1 角色），**问题出在权限基线**。

### 1.1 为什么一直没被发现

种子数据里的 ADMIN（`role_id=1`）是**正确**的：70 个菜单里它只有 61 个，恰好不含租户管理。
E2E 的 `T-003 ADMIN 无租户管理权限` 测的就是它，一直是绿的。

而「建租户」这条路径给出的权限完全不同 —— 两条路径的结果不一致，测试只覆盖了对的那条。

### 1.2 两个独立的缺陷

| # | 位置 | 问题 |
|---|------|------|
| **D-1** | `TenantServiceImpl.create` 第 5 步 `assignAllMenusToRole(roleId)` | 注释写着「分配**所有**菜单权限给管理员角色」，新租户 ADMIN 拿到全部 70 个菜单 |
| **D-2** | `RoleServiceImpl.assignMenus` | 只校验 `menuId` **存在**，不校验调用者**有权分配**它 |

**只修 D-1 是安全剧场。** 租户 ADMIN 握有 `system:role:assignMenu`，即使新建时不给租户管理权限，
它也能自己在「角色管理 → 权限」里把 `system:tenant:*` 勾给自己。D-2 才是承重的那个。

## 二、「平台级」的判据

### 2.1 用 `sys_menu.is_platform` 标记

新增列 `sys_menu.is_platform SMALLINT NOT NULL DEFAULT 0`：

- `1` = 平台级，只有平台超管（`SUPER_ADMIN`）可持有与分配
- `0` = 租户级，租户管理员默认全给

理由：**`sys_menu` 本来就是权限点注册表**，「这个权限点是平台级的」是权限点自身的属性，
不是任何角色的属性。派生项目新增自己的平台级模块时，在自己的迁移里标一下即可，不用改 core 的代码。

它同时让两个角色的定义变得可推导，而不是靠人肉维护两张清单：

```
SUPER_ADMIN   = 全部菜单
租户 ADMIN     = 全部 is_platform = 0 的菜单     ← 「租户下的最高权限」
```

### 2.2 被否决的备选

| 方案 | 否决理由 |
|------|---------|
| 复制种子 ADMIN（`role_id=1`）的菜单集合作为基线 | **那个角色是能通过界面改的。**「角色管理 → 权限」点几下就会改变所有未来租户的安全基线；更糟的是如果有人把租户管理勾给了默认 ADMIN，这个洞就自己长回来了。运行时可变数据不能当规格用 |
| 在 Java 里硬编码平台级 permission 前缀清单 | 注解常量读不到配置，派生项目加自己的平台模块必须改 `gentry-core`。而这条知识天然属于「权限点」这个数据 |
| 给角色加 `role_level`（平台角色 / 租户角色） | 换了个地方存同一个判断，但仍然答不出「哪些权限点是平台级」——分配时还是没有判据 |

### 2.3 哪 9 个是平台级

**取种子数据已经withheld 的那 9 个**，不自己另发明一套。它们背后是两个不同的理由，结论相同：

| 权限点 | 为什么不给租户管理员 |
|--------|-------------------|
| `system:tenant` + `:list/add/edit/remove/detail/config` | 管理租户本身，天然跨租户 |
| `monitor:redis:key:delete` | Redis 是所有租户**共用一个实例**，删 Key 会影响其他租户 |
| `monitor:redis:slowlog:reset` | 同上，属平台运维动作 |

注意 Redis 只挡**写**：`monitor:redis:info` 与只读的 Key 查询仍留给租户管理员，
这是种子数据里既有的意图（租户管理员可以看共享基础设施，不能改它）。

## 三、改动

| 层 | 动作 |
|----|------|
| 迁移 V14 | `sys_menu` 加 `is_platform`；把上表 9 行置 1 |
| 实体 / VO | `Menu.isPlatform`；`MenuTreeVO` / `MenuVO` 下发该字段（前端要据此隐藏） |
| Mapper | `selectTenantScopedMenuIds()`、`selectPlatformMenuIds()` |
| D-1 | `TenantServiceImpl` 的 `assignAllMenusToRole` → `assignTenantScopedMenusToRole` |
| D-2 | `RoleServiceImpl.assignMenus`：`!UserContext.isPlatformAdmin()` 时，提交的 menuIds 含平台级 → `BizException` |
| 错误码 | 新增 `PLATFORM_MENU_FORBIDDEN`（安全段 40000+）+ 中英文案 |
| 前端 | 权限分配树对非超管隐藏 `isPlatform` 节点（不给点，也就不会撞守卫） |

### 3.1 D-2 的守卫为什么放 Service 而不是注解

`@SaCheckPermission` 只能表达「调用者有没有 X 权限」，表达不了「调用者**提交的数据**里有没有越权内容」。
这类校验属于业务规则，必须在 Service 里做。

判据用 `UserContext.isPlatformAdmin()` —— 它在登录时由 `AuthServiceImpl` 按
`roleCodes.contains("SUPER_ADMIN")` 算好写进 Session，已是既有机制，不新增概念。

### 3.2 菜单管理收归平台级（V15）

`sys_menu` 是**全局表** —— 无 `tenant_id`，且在 `GentryTenantManager.IGNORE_TABLES`
里，菜单不做多租户。一份菜单树被所有租户共用，所以改菜单是平台动作：
按「租户下的最高权限」这条定义，它不属于租户级。

种子数据原本把 `system:menu:{add,edit,remove}` 给了 ADMIN（`role_id=1`），
那是 V14 之前没有平台级/租户级之分时的遗留，不是有意的产品决策。V15 收回。

**取舍：`system:menu:list` 必须保留。** 这是本项唯一需要小心的地方 ——
前端「角色管理 → 权限」页（`PermissionPage`）靠 `GET /api/v1/menus` 拉整棵菜单树
才能画出勾选框，而该接口的守卫是 `system:menu:list`。把 list 一起收走，租户管理员
就再也分配不了任何权限，等于把一个越权缺陷换成一个功能缺陷。

于是切法是**树能读、页面进不去、内容改不了**：

| 权限点 | id | 用途 | V15 |
|--------|-----|------|-----|
| `system:menu` | 104 | 菜单项本身，决定侧边栏是否出现「菜单管理」 | → 平台级 |
| `system:menu:add` | 1042 | 写 | → 平台级 |
| `system:menu:edit` | 1043 | 写 | → 平台级 |
| `system:menu:remove` | 1044 | 写 | → 平台级 |
| `system:menu:list` | 1041 | 树查询 + 详情，**权限分配树的依赖** | **保留租户级** |

`system:menu`（104）不是任何 `@SaCheckPermission` 的串（接口守卫全落在
`:list`/`:add`/`:edit`/`:remove`），它纯粹控制页面在侧边栏可见性 ——
与 V14 处理 `system:tenant` 目录项的方式一致。

回归覆盖：`PlatformPermissionIsolationApiIT` 的 `V15_租户管理员不能增删改菜单_菜单是全局表`
与 `V15_菜单树查询仍是租户级_否则权限分配功能会废掉`。后者专门防止后来者顺手把 list 也收走。

另一条路（**未采纳**）：给 `sys_menu` 加 `tenant_id`，让每个租户自定义菜单。
那是另一个量级的改动 —— 菜单是权限点注册表，加租户维度意味着权限点本身按租户分叉，
`@SaCheckPermission` 的串与菜单数据的对应关系会从一对一变成一对多。

## 四、验证

| 项 | 方式 |
|----|------|
| D-1 | 后端 IT：建租户 → 查其 ADMIN 角色的菜单 → 不含任何 `is_platform=1` 的菜单 |
| D-2 | 后端 IT：租户 ADMIN 调 `assignMenus` 带平台级菜单 → 报错；平台超管同样调用 → 成功 |
| 端到端 | E2E：建租户 → 用新 admin 登录 → 租户管理接口 403 / 菜单里看不到租户管理 |
| 不回退 | 既有 `T-003 ADMIN 无租户管理权限` 与 `MON-REDIS-004/006` 必须仍绿 |

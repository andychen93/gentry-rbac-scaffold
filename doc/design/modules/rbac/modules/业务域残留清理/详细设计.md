## 一、背景

本仓库派生自一个高精度车辆定位平台，改造成通用 RBAC 脚手架时有三处业务概念没清干净。
i18n 全量落地过程中逐条撞到，当时记为待清理项：

| # | 残留 | 撞到的场景 |
|---|------|-----------|
| 1 | 租户配置里的「视频 / 报警 / 报表」开关、「最大设备数」、「地图服务商（天地图/高德/百度）」、`sys_tenant.device_limit` 列 | 前端批次 6 要给这些字段建 20+ 条词条 —— 给计划删掉的东西写译文 |
| 2 | `sys_user.post_name` 存的是**中文 label**（「经理」）而不是字典码 | 职务下拉的 value 必须与库里一致，导致英文界面下该下拉仍是中文，且 `dictEnum.POST_NAMES` 成了 i18n 防线的豁免项 |
| 3 | 字典 `sys_user_post` 里的「司机 / Driver」 | RBAC 脚手架的内置职务清单里不该有「司机」 |

三项的共同点：**都要动数据模型**，所以当时统一推迟，不混进 i18n 批次（那会让批次无法独立验证）。
本文档是它们的落地设计。

## 二、清理 1：租户配置去掉车辆监控字段

### 2.1 现状

`sys_tenant.config` 是 `TEXT` 列存 JSON（Java 侧是裸 `String`，Service 自行解析），
字段清单由 `TenantConfigDTO` 定义：

```
maxDevices  dataRetentionDays  videoEnabled  alarmEnabled  reportEnabled  mapProvider  maxUsers
```

除 `maxUsers` 外全是车辆监控概念。另有一个**真实列** `sys_tenant.device_limit`
（`NOT NULL DEFAULT 1000`），以及 `TenantDetailVO.deviceLimit` → 详情弹窗的「设备限额」。

### 2.2 改动

| 层 | 动作 |
|----|------|
| 迁移 | `ALTER TABLE sys_tenant DROP COLUMN device_limit`；`UPDATE sys_tenant SET config = NULL` |
| DTO | `TenantConfigDTO` 只留 `maxUsers` |
| Service | `updateConfig` 改**白名单写入**；`create` 不再 `setDeviceLimit`；`toDetailVO` 不再回填 |
| Entity/VO | `Tenant.deviceLimit`、`TenantDetailVO.deviceLimit` 删除 |
| 校验消息 | 删 `valid.tenant.maxDevices.min`、`valid.tenant.dataRetentionDays.min`（三份 properties） |
| 前端 | `TenantConfigModal` 只留「最大用户数」；`TenantDetailModal` 去掉设备限额；`tenantApi.TenantConfigDTO`、`tenant.json` 同步 |

### 2.3 取舍

**`config` 直接置 NULL，而不是从 JSON 里逐键删。** `config` 是 TEXT 存 JSON，
跨 MySQL / PostgreSQL / SQLite 三库改 JSON 文本要三份方言 SQL（`JSON_REMOVE` /
`jsonb - key` / SQLite 的 `json_remove`），而 `V2__init_data.sql` **建内置租户时根本没写
config**，全新安装该列就是 NULL。唯一可能有内容的是「有人在配置弹窗里点过保存」的开发库，
里面存的又恰好全是本次要删的键。置 NULL 的信息损失为零，省掉三份方言。

**`updateConfig` 从「合并」改成「白名单写入」。** 原实现是 `existingConfig` 上做增量 put，
好处是不认识的键不会丢；坏处是**删掉一个字段后，历史 JSON 里的旧键会永久留着**并通过
`TenantDetailVO.config` 继续下发给前端。白名单写入让「代码里没有的字段」在下一次保存时
自动消失，这正是清理想要的语义。

**`device_limit` 用 `DROP COLUMN` 而不是留着不用。** 留着的成本是每个读这张表的人都要
问一次「这列干什么的」，而 `ALTER TABLE ... DROP COLUMN` 在三库语法一致
（SQLite 自 3.35 起支持，正是 AGENTS.md 要求的最低版本），且该列不参与任何索引或唯一键。

## 三、清理 2：`post_name` 改存字典码

### 3.1 问题的准确表述

`post_name`（职务）**本身不是业务残留** —— 通用后台都有这个字段。问题在于它
**存展示文案而不是稳定标识**：

```
sys_user.post_name = '经理'          -- 现状：中文 label
sys_dict_data      = ('Manager', '经理')   -- 字典里 code 与 label 都在
```

由此产生的连锁后果：

1. 职务下拉的 `value` 必须是「经理」（否则提交上去与库里对不上），所以**下拉文案无法翻译**
2. 前端不得不维护一份中文常量 `POST_NAMES`，成为 i18n 防线的豁免项
3. 字典里改 label（「经理」→「部门经理」）会让已存数据变成孤值，查不到对应字典项

### 3.2 改动

**数据迁移**（`V13`，三库通用 SQL）：

```sql
UPDATE sys_user SET post_name = CASE post_name
    WHEN '首席执行官' THEN 'CEO'
    ...
    ELSE post_name END
WHERE post_name IS NOT NULL;
```

`ELSE post_name` 是刻意的：认不出的值原样留下，而不是置 NULL。派生项目可能已经自己往
这一列写了别的东西，静默清空是最坏的迁移行为。

`V2__init_data.sql` 已发布，不能改（AGENTS.md：已发布迁移不可修改），所以种子用户的
中文职务由 V13 的 `UPDATE` 一并转换 —— 全新安装的顺序是 V2 插中文 → V13 转码，
与增量升级的结果一致。

**后端导出**：`toExportVO` 把码翻成当前 locale 的 label。
**后端导入**：职务列**同时接受 label 与 code**（见 §3.4）。
**前端**：职务下拉改成 `dictOptions(t, DICT_TYPES.userPost)`，value 是码、label 走
`dict.sys_user_post.{code}`。`POST_NAMES` 删除，i18n 防线的豁免项随之删掉。

### 3.3 导出为什么要在后端再放一份译文

Excel 是后端生成的，而字典 label 的译文按既有决策放在**前端**语言包
（`locales/{lang}/dict.json`，见 i18n 前端详细设计 §6.3）。后端拿不到它。

三个选项：

| 选项 | 结果 | 判断 |
|------|------|------|
| 导出写码（`Manager`） | 中文用户打开 Excel 看到英文码 | ✗ 导出是给人看的报表 |
| 导出查 `sys_dict_data.dict_label` | 永远是中文，英文用户拿到中文 | ✗ 等于没做 i18n |
| **后端 `export_*.properties` 加 `export.user.post.{code}`** | 双语正确 | ✓ 代价是同一句话有两份 |

选第三个，并用一条测试把「两份」变成**构造上不可能漂移**：
`frontend/src/locales/exportDictParity.test.ts` 断言

```
backend/gentry-core/.../i18n/export_{zh_CN,en_US}.properties  的 export.user.post.*
  ==（逐条相等）
frontend/src/locales/{zh-CN,en-US}/dict.json                  的 dict.sys_user_post.*
```

放在前端 Vitest 侧是因为 Node 解析 `.properties` 只是纯文本处理，比在 JUnit 里读前端
JSON 更省事；约束本身是双向的，放哪边都成立。

### 3.4 顺带修一个既有缺陷：导出的文件导不回来

`UserImportDTO` 的类注释写着「中英文任意语言导出的文件都能导回来」，理由是按列序
（`@ExcelProperty(index=n)`）而不是按表头文本匹配。**但性别那列不成立**：

| | 性别列 |
|---|-------|
| `UserExportVO.gender` | `String`，写「男」/`Male` |
| `UserImportDTO.gender` | `Integer` |

导出的文件导回去，性别列拿不到 `Integer`，静默变成 null。这是本次勘察发现的、
与三项清理无关的既有缺陷 —— 但 `postName` 正要走同一条路（导出 label、导入 code），
不一起修就是再造一遍同样的坑。

修法：导入侧的性别与职务都改成 `String` 收，再用一个共用解析器归一：

```
gender:   "男" | "Male" | "1"        -> 1
postName: "经理" | "Manager" | "Manager"(码) -> "Manager"
```

规则是「**先按码精确匹配，再按任一语言的 label 匹配，都不中则报错**」。
于是三种来源都能导：模板里手填的码、中文导出的文件、英文导出的文件。

> 导入模板的性别表头本来就是「性别(0未知1男2女)」，说明模板的设计意图是让人填码。
> 改成「码与 label 都认」之后，模板提示可以保留不变。

## 四、清理 3：删字典「司机」

一条 `DELETE FROM sys_dict_data WHERE dict_type = 'sys_user_post' AND dict_value = 'Driver'`，
外加前端 `dict.json` 删 `dict.sys_user_post.Driver`（两种语言）、`dictEnum.DICT_VALUES`
去掉 `'Driver'`。

**必须两边同时删**：E2E 的 `I18N-008` 会对账「语言包 key → 库里派生的 key」，
只删库不删语言包会立刻以孤儿 key 报出来。这条测试正好在此处起到它设计时预期的作用。

删除方式用 `DELETE` 而不是 `deleted = 1` 逻辑删除：字典数据表的唯一约束含 `deleted`，
逻辑删除会让派生项目想重新添加 `Driver` 时撞上历史行；而这是一条**从未被业务引用**的
种子数据（`post_name` 里没有任何用户是「司机」），物理删除没有引用完整性风险。

| 项 | 方式 |

## 五之二、实施中发现的既有缺陷：用户导出在真机上一直是 500

真机验证（不是 MockMvc）时发现 `GET /api/v1/users/export` 返回 500：

```
java.lang.IllegalStateException: getWriter() has already been called for this response
    at ...UserServiceImpl.exportUsers(UserServiceImpl.java:494)   ← response.getOutputStream()
```

### 根因

`LogAspect` 要把方法参数序列化进操作日志：

```java
String params = objectMapper.writeValueAsString(sanitizeParams(joinPoint.getArgs()));
```

而 `exportUsers(UserQueryDTO query, HttpServletResponse response)` 的参数里有
`HttpServletResponse`。**Jackson 序列化它时会去调它的 bean getter，其中包括 `getWriter()`**，
把 Catalina `Response.usingWriter` 置成 true；业务代码随后 `getOutputStream()` 必抛。

两层因素让它藏了很久：

| 因素 | 效果 |
|------|------|
| 那段序列化包在 `try { … } catch (Exception ignored) {}` 里 | Jackson 自己的异常被吞掉，日志里什么都不留，**但对 response 的副作用留下来了** |
| `MockHttpServletResponse` 允许先 `getWriter()` 再 `getOutputStream()` | 所有 MockMvc 导出用例（含 i18n 批次新增的表头本地化断言）一路绿灯 |

影响面是「`@Log` + 参数含 `HttpServletResponse`」的所有下载接口。当前只有用户导出命中：
导入模板下载没有 `@Log`，操作日志导出的 `@Log` 加在别的方法上。

### 修法与防线

`sanitizeParams` 先把 `HttpServletResponse` / `HttpServletRequest` / `MultipartFile`
换成类型占位符（`<HttpServletResponse>`），再交给 Jackson。
`RepeatSubmitAspect.isSerializable` 早就这么过滤了，这里是漏掉的那一处。

防线是 `LogAspectSanitizeParamsTest`，它**直接断言 `getWriter()` 从未被调用**
（Mockito `verify(never())`），而不是断言某个 HTTP 状态码 —— 后者在 MockMvc 下永远是绿的，
测不出这个缺陷。

> 教训值得单独记一句：**下载类接口不能只靠 MockMvc 验收。**
> `MockHttpServletResponse` 对 writer/outputStream 的互斥比真实容器宽松，
> 这类缺陷只有真机会暴露。
